# Kit API 的 catch 值按 BusinessError 取 message 与 code，code 先 Number() 归一再比较错误码

ID：`lesson-b19162077a2ab886d809` · 版本：2

[本主题](index.md)

## 何时使用

规格提取与服务实现阶段，迁移源端按异常类型分类、以 getMessage() 记录详情的 catch 分支时；按 SDK @throws 错误码为 Kit 调用编写异常分支判别时

## 适用情境

目标 catch 到的是网络、文件、数据库、定位等 Kit API 抛出或拒绝的 BusinessError（含 code、message 的普通对象，不是 Error 实例）；源端按 IllegalArgumentException、SocketTimeoutException、UnknownHostException 等异常类型分支；@ohos.net.http 的失败码为 2300000 加 libcurl 码。也包括依据 d.ts @throws 列出的数值错误码（如定位开关关闭）决定等待、重试或失败，而 d.ts 把 BusinessError.code 声明为 number。

## 原因

按 instanceof Error 取消息会把 BusinessError 记成“[object Object]”；按 Java 异常类名或英文消息关键词分类，会让所有失败落入通用 IO 错误。d.ts 的 code: number 只是声明，部分 Kit 抛出的 BusinessError.code 运行时是字符串（例：geoLocationManager 在定位开关关闭时同步抛出的 code 为 "3301100"），与数值常量严格相等永不成立，分支静默落空。

## 做法

1. 公共层建一个取消息函数（Error 取 message，否则读 BusinessError 的 message 与 code，都没有才字符串化），各 catch 统一调用，不在每处写 instanceof Error ? message : String()。
2. 错误分类优先比较 code：@ohos.net.http 为 2300000 加 libcurl 码（3 URL 格式错误、6 无法解析主机、28 超时、60/77 证书校验），消息匹配只作兜底并先用目标平台实际消息核对；规格的错误码表写出这一目标判据，依据取 SDK 声明的 @throws 或网络错误码表。
3. 比较错误码前先归一：Number((err as BusinessError).code) === 常量（或同时接受数值与字符串形式），各分支共用同一判别函数；沿用已有代码的错误码判别时同样改为归一比较。

## 可选检查

- 日志或提示出现 [object Object]、或失败分类全部相同时，用不可达地址、坏域名、非法 URL 各触发一次核对
- 错误码分支决定用户可见行为（如开关关闭时等待还是失败）时，在设备上触发该错误，用 hilog 打印 JSON.stringify(err) 核对 code 的实际类型与值，确认分支命中
