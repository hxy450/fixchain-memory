# 不能编译的生成或修复批次，写后把引用的常量、this 成员、跨文件导入名与 $r 资源键逐一对照声明、导出和资源定义；源端局部派生值改为经持有对象访问

ID：`lesson-e04e26f1f98116275982` · 版本：3

[本主题](index.md)

## 何时使用

实现或修复阶段，在禁止编译的条件下一次写出大型 ArkTS 页面，或新建工具文件并在其他文件接线，并做写后自检时

## 适用情境

整页由一次写入生成，常量区与状态区由写者自拟；源码在方法里用局部派生值（如 isX = current instanceof Y）控制菜单显隐，目标把该对象建模为可空状态；设计里决定的尺寸以具名常量在调用点引用。也包括把 Kotlin object 或 Java 静态工具类改写为 ArkTS 顶层 export function，又在基类等其他文件按源端 ClassName.method 写法导入调用。 也包括页面转换先按源值预估的键清单向共享 element/*.json 追加资源，再写组件里的 $r('app.float|color|string.*') 引用；同一容器各方向的 padding/margin 可能用到清单之外的键。

## 原因

一次生成大文件时，调用点引用的具名常量可能从未写进常量区，源端局部变量名也可能被写成组件成员 this.isX；括号平衡、禁用词、装饰器版本、占位登记这类自检都查不出未声明标识符，错误要到首次编译才出现。来源两处缺陷都在首次写入里，不是后续编辑被截断。 资源追加先于组件写入时，组件实际引用的键可能不在追加清单里，悬空 $r 引用同样只在编译或资源审计时暴露；来源中“布局字面量均已资源化”的自检没有查键是否存在。

## 做法

1. 写后提取文件中所有 this.<名> 与大写常量引用，与 const、@Local/@Param/private 等声明做差集；差集非空就补定义或改引用。
2. 源端局部派生值迁到模型字段后，每个使用点写成经空值判断的持有对象访问（this.<对象> !== null && this.<对象>.<字段>），或显式声明同名 getter；不把源局部变量名直接当成组件成员。
3. 设计中决定用具名常量表示的尺寸（如按钮命中区），在写调用点的同一次写入里加入常量区。
4. 改写工具类的导出形态时同步全部调用处：顶层 export function 用具名导入 { fn } 并去掉类名前缀；要保留 ClassName.method 写法就导出 class 或 namespace；跨文件接线后 grep '^export' 核对被导入名确实导出。
5. 组件写完后，从文件中实际出现的 $r('app.<type>.<name>') 提取键清单，到 resources/base/element/*.json（media 键对 media 目录）逐个查定义，缺失就补；从源布局抽尺寸时把同一容器各方向的内外边距一并列入，不只按写组件前预估的数值清单追加。
