# 规划业务模块拆分时按页面归属建表，不把功能编号或源端包分组一对一当作模块边界

ID：`lesson-99b35920e77ae01076ea` · 版本：1

[本主题](index.md)

## 何时使用

架构重构规划阶段，确定业务模块划分及各页面、模型、服务、ViewModel 的归属时；执行搬迁时判断页面去向时

## 适用情境

目标工程要从单模块拆成多个业务模块；基线功能清单或源工程按历史包名分组，同一业务对象（列表、新增、详情、编辑与数据层）分散在不同功能组或包里，详情页只经路由从另一业务的列表进入。

## 原因

功能编号与包名反映历史分组，不等于业务归属；一对一映射会把同一业务对象的详情和数据层划进另一个模块，执行搬迁时又按“当前 import 了哪个模块”继续沿用，修复期只能再整体迁回。来源中规划者读到“按页面归属拆业务”的规范和功能清单，仍把一个功能编号直接写成一个模块，没有逐页归属表，依赖模拟也只用手写骨架。

## 做法

1. 推导模块前逐页列出入口调用方（路由、Tab、跳转来源）及所用模型、VM、服务，形成“页面 → 归属业务”表；同一业务对象的列表、新增、详情、编辑与数据层放进同一模块或同一纵向目录，源端包名只当线索。
2. 跨功能组出现的同一业务对象要显式标出并作归属决定；跨业务依赖模拟用当前代码的真实 import 与路由关系。
3. 搬迁阶段判断页面去向以入口调用方和业务语义为准，不以页面当前 import 的模块决定；发现同一业务对象被拆到两个模块时回到规划补决策。
