# 迁移深链 intent-filter 时同时声明 module.json5 的 skills（actions、entities、uris，App Links 加 domainVerify），并用隐式 Want 验收

ID：`lesson-d77baa7494930d485425` · 版本：4

[本主题](index.md)

## 何时使用

入口与导航接线阶段，把源端 Activity 的 VIEW/BROWSABLE intent-filter 迁成 UIAbility 的 Want 接收与路由解析时；以及规格提取阶段描述深链映射时

## 适用情境

源 AndroidManifest 在启动 Activity 上声明 VIEW+BROWSABLE、http/https 与固定 host 的 intent-filter；目标 module.json5 的入口 Ability skills 仍是脚手架默认的 HOME 一项。 也包括 intent-filter 带 android:autoVerify="true"（App Links），或决策写明 https 由域名校验的 App Linking 承载。也包括导航图 navDeepLink 的 uriPattern 或分享/复制链接由常量拼接（如 "$baseUrl/item/{id}"），深链规格的源码锚点没有列入 AndroidManifest。

## 原因

只在 onCreate/onNewWant 里解析 want.uri，系统不会把外部链接路由到该 Ability；用 aa start -b/-a 显式拉起会绕过 skills 匹配，把缺声明误判为通过。来源中实现者读到了 Manifest 与深链清单，只写了解析代码；派生规格也只写“启动后解析 URL”；验证用显式启动把这条验收判为通过。带 autoVerify 的链接还要在承载 https 的 skill 中声明 domainVerify；把它与 AGC 域名关联、服务器校验文件一起推到部署期，应用侧声明就缺了这一项，只核 uris 条数的验收拦不住。规格未展开 uriPattern 中的常量、又不以 intent-filter 为依据时，会写出源中不存在的自定义 scheme 并漏掉源中声明的 scheme（如 http），下游按规格注册多余入口、缺少真实入口。

## 做法

1. 把 intent-filter 的 action、category、data 映射到同一 Ability 的 skills：actions 加 ohos.want.action.viewData，entities 加 entity.system.browsable，每个 scheme 一条 uris（scheme、host、pathStartWith 或 pathRegex）；与 want.uri 解析在同一步完成。源 intent-filter 带 autoVerify="true" 或决策要求 App Linking 时，在承载 https 的 skill 中同时写 "domainVerify": true；AGC 域名关联与服务器端校验文件属于部署期，domainVerify 属于应用侧声明。
2. 应用内解析按源端 uriPattern 锚定 scheme、host、路径段和参数类型，不匹配时清空待处理状态。
3. 验收用隐式 Want：aa start -A ohos.want.action.viewData -U <url>，不带 -b/-a，或从外部应用点击链接。
4. 规格描述深链时同时写平台声明（skills.uris，App Links 另写 domainVerify）与运行时解析两部分，并把 AndroidManifest 的 intent-filter 列入锚点：scheme（如 http 与 https 各一项）、host、path 与 autoVerify 只取自 intent-filter；uriPattern 或分享链接由常量拼接时展开常量写出完整 URI，展开不了就保留原表达式并标待核，不自拟自定义 scheme。核验时把源 intent-filter 的属性逐项对到 skill 字段（action→actions、BROWSABLE→entities、data→uris、autoVerify→domainVerify）。
