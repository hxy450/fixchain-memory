# 源端靠依赖注入或全局静态工具就绪的基础设施改成需显式 init 的封装后，在入口 onCreate 最早处调用，并确认启动期读写都晚于初始化

ID：`lesson-8a881c2e07f80f83447c` · 版本：1

[本主题](index.md)

## 何时使用

网络、键值存储等基础设施实现与入口接线阶段：新建必须先 init 才能用的封装，或改写 EntryAbility.onCreate、宣告基础层完成时

## 适用情境

源端网络 baseUrl 由 DI 模块在注入时带上、键值工具（SpUtils/MMKV 一类）全局静态可用，Application.onCreate 里看不到对应的初始化；目标端改为静态 HttpClient（baseUrl 默认空串）加 NetworkConfig.init()、偏好封装需先传入上下文；入口 Ability 由编排会话维护，Flutter 插件 onAttachedToEngine 等回调里也能拿到上下文。

## 原因

迁移把“注入即就绪”改成“调用 init 才就绪”，调用义务是新产生的，源端没有可对照的调用点。实现者写了 init 却不接入口，或把唯一的 init 放进较晚的回调，启动期的请求和读写就会拿到空 baseUrl 或空偏好；这类封装在未初始化时常静默返回默认值，表象是网络错误或数据丢失。来源两例：网络层实现者读到参考文档“在 EntryAbility 中初始化”，写了 init 却没改入口，回报还写“无待接线项”，编排者据此认定网络层完成，自己改写入口时也没接；偏好存储的唯一 init 挂在 Flutter 插件 attach 上，未 init 时读写直接返回默认值、不打日志。

## 做法

1. 新建需显式 init 的封装时，在同一任务里把调用写进 UIAbility.onCreate（或 AbilityStage.onCreate），早于任何请求和读写；派工不许改入口文件时，在回报里单列待接线项，写明文件、生命周期方法和调用语句。
2. 列出启动期所有读写方（入口里的网络初始化、闪屏的状态恢复、通道回调等），逐个确认晚于初始化；写冷启动即发请求的流程前先确认这一点，以后在 onCreate 新增读写方时再核一次。
3. 未初始化就被调用时抛出或打出明确的错误日志（例如 baseUrl 为空时报“网络层未初始化”），不静默返回默认值，也不把相对路径交给 http.request。
4. 宣告基础层完成或改写 onCreate 前，grep 各 init 的调用点，确认命中入口 onCreate；只命中业务服务（如环境切换）时按未接线处理。
