# 订阅蓝牙 access.on('stateChange') 驱动开关时以 getState 终态回读为准，过渡态与迟到回调不写成关闭

ID：`lesson-29922f57cc365ff3d638` · 版本：3

[本主题](index.md)

## 何时使用

系统能力接入与状态接线阶段，决定蓝牙开关/可用状态以回调参数还是系统回读为真值时；重写已有蓝牙状态处理时

## 适用情境

源端只在 ACTION_STATE_CHANGED 的 STATE_ON/STATE_OFF 终态刷新 UI，或在变化时回读 BluetoothAdapter.isEnabled()；目标用 access.on('stateChange') 与 access.getState()，准备把回调参数直接写成开关值。

## 例外与边界

- 源端本身按 EXTRA_STATE 的全部取值（含 TURNING_*）驱动界面时，按源端分支逐一映射

## 原因

stateChange 会带出 TURNING_ON/OFF、BLE 等过渡态（@ohos.bluetooth.access 的 BluetoothState），回调还可能迟到；把“回调参数 === STATE_ON”直接写成开关值，过渡态与迟到回调会把已开启的蓝牙显示为关闭并清空设备。access.getState 自 API 13 的声明不再标 @permission（API 11 版标 ohos.permission.ACCESS_BLUETOOTH）；未授权时它的实际返回未经设备核实，因此不把权限申请顺序当作这一偏差的原因，compatibleSdkVersion 低于 13 的工程先完成权限申请再回读。

## 做法

1. 收到 stateChange 即以 access.getState() 回读：STATE_ON（业务需要时含 STATE_BLE_ON）为开；只有回读与回调都为 STATE_OFF 才报关闭；TURNING_* 与迟到回调不直接写成 false。
2. 重写已有状态处理前，对照被替换的旧逻辑与源端广播分支；旧实现已是“变化时回读”、源端只处理终态时，保留回读，不改成信任回调参数。
