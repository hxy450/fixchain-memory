# 沿用脚手架 bundleName/vendor 前核对所引部署期决策与签名配置；vendor 是描述字段，不随签名延后，按源端组织或作者落地

ID：`lesson-fb996956b33a1ba65861` · 版本：2

[本主题](index.md)

## 何时使用

资源前置阶段落地应用身份字段、决定 bundleName 与 vendor 是否替换脚手架值时；以及维护流水线里身份规则与验证门的口径时

## 适用情境

AppScope/app.json5 仍是 com.example.* 包名与 example 厂商，源 build.gradle 给出真实 applicationId；执行规则或身份技能的受限范围（如只写显示名与版本的开发期身份）要求这一阶段把包名、厂商一并留到部署期决策，而验证门对 com.example.* 包名或 vendor=example 判失败。

## 例外与边界

- 工程已有签名配置，或决策台账里确有已批准的部署期身份决策；这只影响 bundleName，vendor 不参与签名，仍按源端落地

## 原因

规则以“部署期决策、签名一致性”为由保留脚手架值，但工程台账里没有该决策、签名配置为空、流水线也没有后续落地步骤，而验证门对模板值直接判失败。vendor 只描述厂商，不参与签名与 profile 校验，与 bundleName 并列延后没有依据。来源中资源阶段 worker 读到了 applicationId，仍按规则保留脚手架值；另一应用的身份技能以开发期范围跳过 vendor，执行者照做，验证门判 FAIL，修复只改 vendor 后签名包仍能正常安装。

## 做法

1. 保留前在决策台账查规则所引的决策，并看 build-profile.json5 的 signingConfigs；二者都不成立时，按源端 applicationId 映射 bundleName 与 vendor，或在迁移报告登记“包名/厂商待定、验证门会判失败”的决策缺口，不静默沿用脚手架值。
2. 区分签名绑定字段与描述字段：bundleName 随签名 profile 绑定，可按决策延后；vendor 在开发期就从源端取值（applicationId/namespace 的组织段，或源工程 README、仓库所属的作者或组织），不因 bundleName 延后而一并保留 example。
3. 维护流水线时，让“部署期再落地”的跳过规则与验证门一致：身份规则跳过某字段前逐项比对验证门的模板默认值规则（如 vendor=example、bundleName 匹配 com.example.* 判失败），冲突时在输出中指出；进入验证前安排落地步骤，或让验证门对已登记延后的字段给出 DEFERRED。
