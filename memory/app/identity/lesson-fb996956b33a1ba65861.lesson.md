# 沿用脚手架 bundleName/vendor 前核对所引部署期决策与签名配置；vendor 是描述字段，不随签名延后，按源端组织或作者落地

ID：`lesson-fb996956b33a1ba65861` · 版本：3

[本主题](index.md)

## 何时使用

资源前置阶段落地应用身份字段、决定 bundleName 与 vendor 是否替换脚手架值时；规格/决策阶段登记模板身份技术项时；以及维护流水线里身份规则与验证门的口径时

## 适用情境

AppScope/app.json5 仍是 com.example.* 包名与 example 厂商，源 build.gradle 给出真实 applicationId；执行规则或身份技能的受限范围（如只写显示名与版本的开发期身份）要求这一阶段把包名、厂商一并留到部署期决策，而验证门对 com.example.* 包名或 vendor=example 判失败。源 applicationId 本身也可能位于 com.example.* 下（教学或示例工程）。

## 例外与边界

- 工程已有签名配置，或决策台账里确有已批准的部署期身份决策；这只影响 bundleName，vendor 不参与签名，仍按源端落地

## 原因

规则以“部署期决策、签名一致性”为由保留脚手架值，但工程台账里没有该决策、签名配置为空、流水线也没有后续落地步骤，而验证门对模板值直接判失败。vendor 只描述厂商，不参与签名与 profile 校验，与 bundleName 并列延后没有依据。来源中资源阶段 worker 读到了 applicationId，仍按规则保留脚手架值；另一应用的身份技能以开发期范围跳过 vendor，执行者照做，验证门判 FAIL，修复只改 vendor 后签名包仍能正常安装。源 applicationId 本身在 com.example.* 下时，忠实映射出的包名和 example 组织段同样会被字面规则判失败；例外不提前登记，就只能在验证期临时裁决。

## 做法

1. 保留前在决策台账查规则所引的决策编号（台账里查不到就不是已批准决策），同时看台账是否已有“迁移真实身份”的技术项、build-profile.json5 的 signingConfigs 是否为空；决策不存在、签名为空时，按源端 applicationId 映射 bundleName 与 vendor，或在迁移报告登记“包名/厂商待定、验证门会判失败”的决策缺口并把相关技术项标为未完成，不静默沿用脚手架值。
2. 区分签名绑定字段与描述字段：bundleName 随签名 profile 绑定，可按决策延后；vendor 在开发期就从源端取值（applicationId/namespace 的组织段，或源工程 README、仓库所属的作者或组织），不因 bundleName 延后而一并保留 example。
3. 维护流水线时，让“部署期再落地”的跳过规则与验证门一致：身份规则跳过某字段前逐项比对验证门的模板默认值规则（如 vendor=example、bundleName 匹配 com.example.* 判失败），冲突时在输出中指出；进入验证前安排落地步骤，或让验证门对已登记延后的字段给出 DEFERRED。
4. 源 applicationId 本身位于 com.example.*、组织段为 example 时，仍按源值映射（这是源端真实身份，不是脚手架残留）；在规格/决策阶段登记模板身份技术项时写明由哪个阶段以何种范围写 bundleName/vendor，并同时登记验证门的 com.example.* 例外，不留到验证期才发现规则字面必然判失败。
