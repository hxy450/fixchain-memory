# 源端拉起系统能力前的可用性预检、权限申请与无接收方回退逐段落成目标显式步骤，不用 pick/startAbility 的 catch 代替

ID：`lesson-4b5903a870344121e97e` · 版本：1

[本主题](index.md)

## 何时使用

规格提取与服务层实现阶段，把源端拉起相机、外部应用或隐式 Intent 前的能力检查、权限申请与失败回退翻译为目标契约和代码时

## 适用情境

源方法在 startActivity 或拍照前先用 IntentChecker.isAvailable、PackageManager.hasSystemFeature、resolveActivity 判可用，经权限工具申请运行时权限，无接收方时走回退（如 geo: 打不开改走网页地图）或提示；目标用 cameraPicker、startAbility/openLink 的隐式 Want 等实现，参考样例只给“调用 + catch”。

## 原因

catch 只覆盖调用失败，替代不了源端拉起前的分支：能力缺失提示、权限拒绝时不创建文件、无接收方时换路径都会丢失。隐式 Want 不预检时，系统可能弹出选择框，不含 // 的 URI（mailto:、geo:）还可能按推断的类型匹配到意外接收方（含本应用），失败不一定以异常返回。规格只留一个分类函数、不给探测与动作的目标符号时，实现者会把探测推给通用 openLink。

## 做法

1. 对照源方法逐段列出“预检 → 权限 → 拉起 → 结果/回退”，每段写出目标符号：能力预检用 canIUse 或对应能力查询；权限在 module.json5 声明并以 abilityAccessCtrl 的 requestPermissionsFromUser 申请，保留拒绝分支；拉起与结果按源分支实现。缺任一段即为未完成。
2. 隐式 Want 拉起外部应用（geo:、mailto:、tel: 等）前用 bundleManager.canOpenLink 探测，并在 module.json5 的 querySchemes 登记所查 scheme；无接收方时走源端的回退或提示分支，不依赖 startAbility 抛错。
3. 规格把源 helper 翻成服务契约时，为源方法里的每个动作（如 ACTION_SENDTO、ACTION_DIAL）与可用性探测各给一个目标符号，不只留 scheme 分类函数。
4. 目标 API 在 d.ts 中不标 @permission、源端却有权限申请与拒绝分支时，在规格写明是否保留申请流程及其对拒绝分支的影响，不静默删除这段可观察流程。
