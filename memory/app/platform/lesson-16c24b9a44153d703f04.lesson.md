# Android 前台服务改用扩展能力承载时，先在项目 SDK 确认基类导出；module.json5 extensionAbilities 的 type 与基类成对，backgroundModes 只写在 UIAbility

ID：`lesson-16c24b9a44153d703f04` · 版本：1

[本主题](index.md)

## 何时使用

后台服务迁移的规格、实现与编译/安装修复阶段，为源端 Foreground Service 选择承载类并在 module.json5 登记扩展能力时；因编译错误更换扩展基类时

## 适用情境

源端以 Service/LifecycleService 加 startForeground 承载长任务；目标准备用扩展能力类承载并在 module.json5 extensionAbilities 注册；规格、决策或文件头注释凭经验写了 ServiceExtensionAbility、type=service 或 backgroundModes，生成批次可能不能编译。

## 原因

扩展基类的可用性和 type 取值随 SDK 版本与导出范围变化，凭记忆写的类在当前 SDK 可能不存在；构建 schema 只校验字段是否合法，不校验类与 type 是否对应，错配要到真机安装才报 not allow use privilege extension。来源中规格把前台服务自答映射为 ServiceExtensionAbility，而项目 SDK（API 22）的 @kit.AbilityKit 只导出 AppServiceExtensionAbility；实现者在不能编译时把 type=service 与 backgroundModes 写进注册指引，收尾者因编译错误改了基类却没改 type 和注释，修复轮照旧注释重写注册，先被 schema 拒绝 backgroundModes，再被设备拒装，最后改为 type=appService 才安装成功。

## 做法

1. 选定承载类前，在项目 SDK 的 kit 导出（如 @kit.AbilityKit.d.ts）与 ets/api 目录确认该类存在及其 @since；规格与决策把类名和 module.json5 的 type 成对写出。
2. 注册时按基类取 type（来源 SDK 中 AppServiceExtensionAbility 对应 appService，WorkSchedulerExtensionAbility 对应 workScheduler）；长时任务的 backgroundModes 写在 abilities[] 的 UIAbility 上，extensionAbilities 条目不加该字段。
3. 编译修复中更换扩展基类后，同步修改 module.json5 的 type、源文件头注释与交接里的注册说明；构建通过不代表类与 type 匹配，有设备时以安装结果为准，不能编译时把未核实的注册字段标为待核而不是写成确定指令。
