# 用 relationalStore 重写 SQLiteOpenHelper 子类时补齐基类打开契约：按版本号分派建表、升级与降级报错，打开失败后下次取库重试

ID：`lesson-65358a02b1bf9ef652d3` · 版本：1

[本主题](index.md)

## 何时使用

数据层实现阶段，用 relationalStore 重写 SQLiteOpenHelper 子类的打开、建表与版本处理时；规格写“升级路径不迁移”“onCreate 即唯一入口”一类决策时

## 适用情境

源 helper 以 super(context, name, factory, VERSION) 构造并覆写 onCreate/onUpgrade，DAO 每次经 getWritableDatabase/getReadableDatabase 取库；目标用 getRdbStore 单例、store.version 与缓存的初始化 Promise 实现。

## 原因

这些行为写在基类里（AOSP SQLiteOpenHelper.getDatabaseLocked）：取库时比较库内版本与构造的 VERSION，为 0 调 onCreate、较低调 onUpgrade、较高调 onDowngrade（基类默认抛 SQLiteException），成功后写入新版本；打开失败只抛给本次调用方，下一次取库重新尝试。子类源码和规格文本都看不到这些分支：只写“版本不足就建表”会丢掉分派骨架，把初始化 Promise 永久缓存又会让一次失败后的所有访问都拿到同一个被拒绝的结果。

## 做法

1. 打开 RdbStore 后按源构造的 VERSION 分派：store.version 为 0 走建表（含源端在 onCreate 里的播种），低于 VERSION 走升级分支，高于 VERSION 按源端 onDowngrade（未覆写即抛错），全部成功后写 store.version = VERSION；规格只免去升级脚本内容时，仍保留分派骨架与版本写入。
2. 用缓存的 Promise 合并并发初始化时，在失败分支清掉缓存再抛出，让下一次取库重新打开；不让一次失败把单例永久钉在被拒绝的 Promise 上。
