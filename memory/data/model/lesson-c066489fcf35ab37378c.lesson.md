# 服务器下发的大整数 id 在 JSON.parse 前保真：源端 Long 用 bigint，String 承接的数值 id 保真为字符串

ID：`lesson-c066489fcf35ab37378c` · 版本：4

[本主题](index.md)

## 何时使用

数据模型与网络层实现阶段，映射 Kotlin Long 字段或以 String 承接的数值标识、编写全局响应解析入口与序列化时；规格提取阶段写服务层签名与接口字段类型时

## 适用情境

服务器生成的 id、hash、userId 以 JSON 数字下发，取值可达 19 位；源端用 Kotlin Long（Flutter 侧 Dart int）承载，或用 String 字段承接（Gson 把数值 token 直接读成字符串）；目标端 ArkTS 的 number 是双精度，JSON.parse 遇到超过 2^53 的整数直接舍入。

## 例外与边界

- Java long 常量（Long.MAX_VALUE 等哨兵）拼进 SQL 或字符串时，见 arkts/numeric 的 long 常量安全整数经验

## 原因

number 只能精确表示到 2^53，裸 JSON.parse 在解析那一刻就已舍入，之后字段改成什么类型都救不回来；舍入后的 number 再 stringify 不会再变，但值已经错了。源端声明为 String 时最容易误以为“字符串字段是安全的”，但下发的仍是数值 token，Gson 读原始 token 的行为不会被复现，parse 之后再 String(value) 已是舍入值，按该 id 回查的接口会被服务端拒绝。bigint 不能直接交给 JSON.stringify（按 ECMAScript 语义抛 TypeError），持久化与请求序列化都要成对的 replacer/reviver，并按服务端要求输出数字或字符串 token。

## 做法

1. 逐个列出源端 bean 与接口里的 id 类字段，并对照线上 token 类型：源端 Long 的服务器 id 用 bigint（默认值 0n），源端 String 承接数值 token 的保持 string；只有确认取值不超过 2^53（如 13 位毫秒时间戳、时长）才用 number，并在注释写明理由。
2. 解析响应用 @kit.ArkTS 的 JSON.parse(text, reviver, { bigIntMode: JSON.BigIntMode.PARSE_AS_BIGINT })（@ohos.util.json.d.ts，API 12 起，按工程 compatibleSdkVersion 核对）：该模式只把超出 ±(2^53−1) 的整数解析为 bigint，小值仍是 number，映射时 Long 字段统一 BigInt(v)、String 字段统一 String(v)。低于 API 12 时在解析前给相应数字加引号再按字段转换。最小检查：解析 {"id":6970321983963689496} 后 id.toString() 原样返回 19 位。
3. 模型有 bigint 字段时，每条 JSON.stringify/JSON.parse 往返（用户信息持久化、DAO、偏好里存的 JSON）都用成对的 replacer/reviver，存完读回比较 id；请求体按服务端要求输出数字或字符串 token。
4. 用“正则预处理 + reviver”这类全局方案前，把转换范围限定到已知字段名或值位置，并确认后端接受字符串形式的数字；确认不了就按字段处理，避免误伤 16 位以上的字符串或其他整数字段。
5. 规格写服务层目标签名和接口字段表时，记下线上 token 类型与量级：源端 Long 参数写 bigint 或注明“64 位，禁用 number”；雪花类 id 在响应契约中写明“超过 2^53 按字符串保真”。

## 可选检查

- 取一个真实列表响应，逐位比较解析后的 id 与报文字面量，再用该 id 调用按 id 回查的端点确认能查到。
