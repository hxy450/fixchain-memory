# 同步进度与失败事件按整批发布：补跑多轮时终态只在最后一轮后发一次，开始进度保留源端首次同步门控

ID：`lesson-34f35851208470602570` · 版本：1

[本主题](index.md)

## 何时使用

同步调度修改与同步迁移阶段，决定同步协调器在何处发布开始进度、结束/失败终态，以及首页据此显示进度或错误提示时

## 适用情境

目标由统一同步服务向首页发布 progress/失败事件，同一批同步可能合并请求或补跑多轮；首页收到结束事件就查询待同步/错误队列并显示错误提示；源端开始进度事件有前置条件（如已登录且空间 cursor 为 0 才算首次同步）。

## 原因

把终态事件留在单轮函数里再循环补跑，每轮都会发 100/失败，订阅方把中间轮次当成最终结果，错误提示在尾随轮执行前短暂出现。开始事件去掉源端门控后，每次同步都会显示“首次同步”进度提示。来源中修复者为补跑尾随请求新增循环调用单轮函数，没有把终态移出单轮；开始进度的无条件发布则来自一次按源端重核同步通知的审计遗漏了 cursor 门控，实现者照旧保留。

## 做法

1. 修改同步调度（合并、补跑、重试）前列出单轮函数里已发布的事件，把批次终态移到整批最后一轮结束处只发一次，并确认订阅方收到终态后会做什么。
2. 审计与实现开始进度时，把源端每个界面通知事件的发布位置与前置条件逐条带上（如仅在已登录且 cursor 为 0 时发布首次同步开始），订阅方不再用通用的“同步中”快照补显示。
