# 同步调度保留源端每次触发都会执行的语义：合并在途任务要补跑尾随请求，失败队列按源端选取条件重推

[本主题](index.md)

## 何时使用

数据同步迁移的规格提取、调度实现与复核阶段，确定多次同步触发的并发语义与失败项重试范围时

## 适用情境

源端每次同步触发都启动新任务并在互斥锁后排队执行（如协程 launch + Mutex.withLock，锁内先推送队列再拉取），待推送队列按资源类型而非同步状态选取；目标端用单一同步服务和 Promise 串行队列统一调度全量同步、定向拉取与状态推送；已有规格可能写着“并发触发复用当前任务”。

## 例外与边界

- 源端本身在同步进行中直接丢弃新触发，且没有依赖其推送结果的后续读取

## 原因

目标把运行中到达的全量同步请求直接返回在途 Promise 时，在该轮越过推送阶段后才入队的本地变更不会被推送，随后的拉取还会把云端旧状态写回本地，界面表现为“1项未同步”、状态回跳和误报失败。源端按资源类型选取队列，失败置 fail 的项下一轮会被重推；目标只取 pending 时 fail 项永不恢复。来源中同步规格写着“并发触发复用当前任务”，与编排者已读到的源端逐次加锁排队冲突；实现者修了定向拉取的“等待后 return”，却给全量同步写了返回在途 Promise 的捷径并保留只取 pending 的查询，复核者读回两处也未纠正。

## 做法

1. 规格提取时逐项写出源端每次触发如何执行（新建任务、锁后排队、合并或丢弃）以及推送队列的选取条件；已有规格与源码不一致时以源码为准并回改规格。
2. 实现时若采用单飞合并，用请求版本号记录运行中到达的请求，本轮结束时比较并补跑，直到没有新请求；失败只在最后一轮仍失败时发布。修一个入口的“等待后 return”时同步排查其他入口的同类写法。
3. 推送阶段的队列选取照源端条件：源端不按同步状态过滤时，同时取 pending 与 fail，使失败项在下一次触发时自动重推。

## 可选检查

- 不确定时补一条回归：同步越过推送阶段、尚未结束时入队并再次触发，断言推送次数增加且 pending 为 0；fail 项在下一次触发时被重推。
