# 新增或改写请求通道时按源端重载决定是否内置取 key 门；确需门时按请求实际基址握手，不用可被切服改写的默认基址

ID：`lesson-62499aa25e87fa6ab5e1` · 版本：1

[本主题](index.md)

## 何时使用

网络通道实现或修复阶段，为新增或改写的请求通道决定是否内置会话密钥前置门（ensureKey 一类）及其握手基址时

## 适用情境

源端某请求重载只带公共头直接发送（如 OkGo 无 body 的 post 重载），由调用方先按特定基址握手取 key；目标端会话 key 是全局单槽缓存，按基址比对决定命中或重新握手，默认基址取运行期可被选省、切服改写的地址，调用方则按另一基址握手。

## 原因

通道内再以默认基址取 key，在默认基址被切换后会与调用方的握手冲突：二次握手覆写会话 key，响应解密失败后静默返回空数据。只在清数据后的初始态验证时缓存恰好命中，问题被掩盖。来源中写者已读到源重载无门、key 缓存按基址比对、选省会改写默认基址，只核了基址常量的静态初值就判定“基址同值、加门安全”，照搬既有通道加了门；选省后再进页面，列表只剩标题。

## 做法

1. 按源端重载实际做的事实现通道（请求头、body 形态、是否取 key）；源端无前置门、由调用方先握手时，目标通道不为“与其他通道一致”自行加门。
2. 确需在通道内保证 key 时，门的基址与请求 URL 或调用方的握手基址一致（显式传入或由 URL 推导）；判断两个基址是否恒等时查遍所有赋值点（选省切服、登录后覆盖等），不只看静态初值。

## 可选检查

- 验证涉及会话 key 或服务基址的修复时，至少覆盖一次已切服的持久化状态（选择地区返回后再次进入页面），不只在清数据后的初始态验证。
