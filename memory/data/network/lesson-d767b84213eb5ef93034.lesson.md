# 把 Retrofit 接口迁成手工拼 URL 时，按相对 URL 解析语义把 endpoint 解析到 baseUrl 上，不统一增删斜杠

ID：`lesson-d767b84213eb5ef93034` · 版本：4

[本主题](index.md)

## 何时使用

网络层实现阶段，把 Retrofit 接口迁成自写 HttpClient，确定 baseUrl 常量与各 Service 的 path 如何连成完整 URL 时

## 适用情境

源端用 Retrofit 的 baseUrl 加 @GET/@POST 路径（多数不带前导 /，少数带；baseUrl 可能只到 host，也可能带上下文路径如 /app/），目标改用 @kit.NetworkKit http 手工拼 URL；参考模板示范 `${baseUrl}${path}` 直接拼接；baseUrl 常量与各 Service 的 path 分散在不同文件里。

## 例外与边界

- 源端所有 endpoint 都只有一种写法、baseUrl 没有路径段，且没有完整 URL、//authority 或 ../ 形式时，可以用受限拼接（去掉重复斜杠后用一个 / 连接），并在拼接函数旁写明这个前提

## 原因

Retrofit 按相对 URL 解析把 endpoint 解析到 baseUrl 上（Retrofit 2.11.0 Retrofit.Builder.baseUrl 的 Javadoc，github.com/square/retrofit tag 2.11.0，2026-10-15 访问）：baseUrl 必须以 / 结尾，否则抛 "baseUrl must end in /"；不带前导 / 的 endpoint 接在 baseUrl 路径后；以 / 开头的从 host 根起算，丢掉 baseUrl 的路径段；完整 URL 直接替换；以 // 开头的替换 host、沿用 baseUrl 的 scheme；../ 等点段按路径解析。手工直接拼接时分隔符只能由一侧提供，两侧都不带就把 host 与路径粘在一起，请求报无法解析主机；统一去斜杠再拼，又会在 baseUrl 带上下文路径时把源端以 / 开头的 endpoint 错接到上下文路径下，也处理不了 // 与 ../。

## 做法

1. 在公共 HTTP 层用带基准地址的 URL 解析得到完整地址，不手写按前缀分支的字符串拼接。目标侧可用 @ohos.url 的 url.URL.parseURL(endpoint, baseUrl)（本机 @ohos.url.d.ts：API 9 起，注释里 API 10、11 两段分别是跨平台与原子化服务支持；相对地址按 base 解析，绝对地址忽略 base），取结果的 toString()；它按 URL 标准解析，与 OkHttp 在反斜杠、非法字符编码等边角输入上可能不同，源端 endpoint 含这类写法时单独核对。
2. baseUrl 常量保留源端的尾 /（Retrofit 要求以 / 结尾）；各 Service 的 endpoint 保留源注解原样，前导 /、相对路径、完整 URL 都不增删改。
3. 沿用参考模板的 `${baseUrl}${path}` 写法前，先确认它约定的 baseUrl 与 path 形式；与源注解冲突时，拼接一律走第 1 步的解析函数。

## 可选检查

- 有疑问时用当前 baseUrl 与三种 endpoint 各解析一次，与 Retrofit 文档示例对照：base http://example.com/api/ 加 foo/bar/ 得 http://example.com/api/foo/bar/，加 /foo/bar/ 得 http://example.com/foo/bar/；base http://example.com 加 //github.com/square/retrofit/ 得 http://github.com/square/retrofit/。
