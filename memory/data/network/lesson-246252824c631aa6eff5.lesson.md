# 服务地址与环境沿地址键名追到源端常量与取址逻辑：分清各接口族的 host，环境枚举与默认环境按源端规则映射

ID：`lesson-246252824c631aa6eff5` · 版本：2

[本主题](index.md)

## 何时使用

规格提取与网络基础设施实现阶段，确定服务地址、环境枚举与默认环境时

## 适用情境

API 清单或规格只给出地址键名（如 SpKey.BASE_URL），没有实际 host；源端按接口族分设多套后端地址（如 Java 旧接口与 Go 新接口），由 DI 模块或环境工具类按构建类型选择环境。 也包括流程要求的 API 清单没有产出、计划只写“网络层（HTTP 请求封装）”，实现者按应用名拼出基址；源端 BuildConfig.BASE_URL 带上下文路径（如 /app/）。

## 原因

地址与环境的真值在键名指向的常量类、DI 模块取址函数和环境工具里；不沿着读，就只能照脚手架注释或常见命名填一组 dev/staging/prod 和 api.<域名> 形式的地址。两套接口若在不同 host 上，共用一个 baseUrl 会让其中一族全部发错地址。来源中规格作者只看到键名，就写下源端不存在的 dev/staging/prod（取自脚手架 TODO 注释）；实现者据此自拟三个域名，只留一个 baseUrl。同一时期参考文档里已有正式服的两个 host，没有交接到规格和派工。 另一应用的生成者跳过 API 清单步骤，从未读源端网络模块，写出源码中不存在的 api.<应用名>.com 基址与猜测的登录路径，响应也没有按统一响应壳解包。

## 做法

1. 沿地址键名打开常量定义与取址逻辑（地址键常量 → 地址常量类 → DI 模块的取址函数 → 环境工具），把每套接口在各环境的 host、环境枚举值和默认环境规则写进规格；查不到时写“未解析，待核”并注明源文件，不填自拟的环境名或域名。
2. 规格提到新旧接口并存时，先确认两套是否不同 host；不同就让客户端持有对应数量的 baseUrl，并写明选择规则（例如按 path 前缀）。
3. 环境默认值按源端规则映射到目标构建模式（源端按 debug/beta/release 取默认时照此映射），网络配置、桥接接口和偏好封装里的同一默认值统一引用一处，不各写一份。
4. 写 HTTP 封装前读源端网络装配（BuildConfig/NetworkModule 中的 BASE_URL 及其上下文路径、鉴权拦截器、Service 注解、响应包装类），基址与路径逐字取自源码，不用应用名拼占位域名。

## 可选检查

- 网络层写完有疑问时对账：目标 BASE_URL 与源 BASE_URL、页面调用路径与源 Service 的 @GET/@POST 注解、响应解包成功码与源包装类的判定逐项一致。
