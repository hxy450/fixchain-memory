# 服务地址与环境沿地址键名追到源端常量与取址逻辑：分清各接口族的 host，环境枚举与默认环境按源端规则映射

ID：`lesson-246252824c631aa6eff5` · 版本：4

[本主题](index.md)

## 何时使用

规格提取与网络基础设施实现阶段，确定服务地址、环境枚举与默认环境时

## 适用情境

API 清单或规格只给出地址键名（如 SpKey.BASE_URL），或没有产出 API 清单，没有实际 host；源端按接口族分设多套后端地址（如旧接口与新接口），由 DI 模块或环境工具类按构建类型选择环境；BuildConfig.BASE_URL 可能带上下文路径（如 /app/）。

## 例外与边界

- 地址与环境已经确定，要决定如何把构建期材料（地址、签名、密钥）注入目标并装配客户端时，见同主题构建期配置注入的经验

## 原因

地址与环境的真值在键名指向的常量类、DI 模块取址函数、BuildConfig 与构建脚本里；不沿着读，就只能照脚手架注释或常见命名填一组 dev/staging/prod 和按应用名拼出的地址。两套接口若在不同 host 上，共用一个 baseUrl 会让其中一族全部发错地址。BASE_URL 带上下文路径时，path 有无前导 / 还决定请求落在上下文路径下还是 host 根下。

## 做法

1. 沿地址键名打开常量定义与取址逻辑（地址键常量 → 地址常量类 → DI 模块的取址函数 → 环境工具），BuildConfig 字段再追到 gradle 里的 buildConfigField 定义，把每套接口在各环境的 host、环境枚举值和默认环境规则写进规格。沿链仍查不到时登记缺口：写明键名与已读到的源文件，并在回报中列出，不填自拟的环境名或域名。
2. 规格提到新旧接口并存时，先确认两套是否不同 host；不同就让客户端持有对应数量的 baseUrl，并写明选择规则（例如按 path 前缀）。
3. 环境默认值按源端规则映射到目标构建模式（源端按 debug/beta/release 取默认时照此映射），网络配置、桥接接口和偏好封装里的同一默认值统一引用一处，不各写一份。
4. 写 HTTP 封装前读源端网络装配（BuildConfig/NetworkModule 中的 BASE_URL 及其上下文路径、Service 注解、响应包装类），基址与路径逐字取自源码，不用应用名拼占位域名；基址与 path 的拼接按同主题 URL 拼接经验保留 Retrofit 的解析语义。

## 可选检查

- 网络层写完有疑问时对账：目标 BASE_URL 与源 BASE_URL、页面调用路径与源 Service 的 @GET/@POST 注解、响应解包成功码与源包装类的判定逐项一致。
