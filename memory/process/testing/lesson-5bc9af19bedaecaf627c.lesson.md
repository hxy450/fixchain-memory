# 为迁移代码定预期值或写验收样例时按源端实现逐步手算（源式含 float 时每步按 float32 舍入再按 Java (int) 截断），不编造比源端更严的区分性或过滤期望

ID：`lesson-5bc9af19bedaecaf627c` · 版本：2

[本主题](index.md)

## 何时使用

验证阶段设计与编写单元测试，为迁移的算法、集合过滤与初始化分支选择输入夹具和预期值时；规格提取阶段为数值公式写验收样例、或召回提醒给出具体样例值时

## 适用情境

迁移代码按源端逐函数对齐；测试设计模板要求每个验收项覆盖正常、边界、异常输入，设计者只拿到抽象期望（如“某模式只预选收藏”“不同图片哈希不同”），需要自己选输入、构造夹具；验收条目的文字可能超出源端范围。 也包括源式含 (float) 强转、f 后缀字面量或 float 返回类型，结果随后 (int) 截断或比较，而规格或经验提醒里的样例是按实数或 JS double 心算的。

## 例外与边界

- 当前规格或已批准决策明确要求目标行为不同于源端

## 原因

预期值若不从源端实现推出，测试会把源端本来的行为判成缺陷：只比较相邻像素梯度的感知哈希对纯色图本就输出相同结果；源端先合并再与当前列表求交时，列表外的成员不会被选中。来源中一个设计者为纯黑与纯白图写“哈希必不同”并预判为已通过；另一个编写者复制相邻用例的列表夹具，把要预选的收藏放在列表之外；第三处设计者按字面要求会话设置方法写入另一页的收藏组，虽怀疑归属其他功能也未核实。三处都导致修复者改动了产品代码。float32 逐步舍入后再截断，与 double 结果在少数输入上差 1；按实数心算的样例会把 double 实现判为正确，照样例实现的代码也随之偏离源端。另一应用中召回提醒给出“x=1375 对应 85”，规格作者照实数复算后写进样例，Java float 实际为 84。

## 做法

1. 对每个用例用源端实现（或已确认复刻源端数值类型的目标实现）逐步手算预期：源式含 (float)、x.0f 或 float 返回值时，每个操作数和每步 + − × ÷ 用 Math.fround（或 numpy.float32）舍入，再按 Java (int) 截断，并至少给一个 float 与 double 截断结果不同的样例。选区分性样本时避开源算法的退化输入（如梯度哈希不用纯色或常量图），或把预期写成源端的实际输出。
2. 复制相邻用例的夹具时，确认预期中的成员满足被测函数的过滤条件（如确实在 mock 的可用列表中）；只有改变产品过滤语义才能变绿的用例，先判为夹具错误。
3. 条目文字与实现冲突、又怀疑归属其他功能时，先查源端写入点与其他功能规格；无法确认就记为规格待确认，不直接写成要求当前方法实现的失败用例。
