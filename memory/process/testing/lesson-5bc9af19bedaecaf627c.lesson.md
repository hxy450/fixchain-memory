# 单元测试的预期与分诊以源端实现为准：设计时按源逐步手算并避开退化输入，失败时用同一输入核源端，不改产品迁就测试

ID：`lesson-5bc9af19bedaecaf627c` · 版本：5

[本主题](index.md)

## 何时使用

验证阶段设计与编写单元测试，为迁移的算法、集合过滤与初始化分支选择输入夹具和预期值时；对单测失败做分诊、写问题文件，以及修复代理处理失败用例时；规格提取阶段为公式写验收样例时

## 适用情境

迁移代码按源端逐函数对齐；设计者只拿到抽象期望（如“某模式只预选收藏”“相同输入签名一致”），需要自己选输入、构造夹具，可能加入比源端更严的契约（如“不同图片哈希必然不同”）；验收条目文字可能超出源端范围。修复代理被要求以测试为契约、通常不能改测试，但可用 BLOCKED、manual_review 或处置提示上报。

## 例外与边界

- 任务已有用户明确批准的行为变更（规格或台账写明且经用户授权，不是模型或流水线自记的 approved）时，该范围内的预期按批准后的契约写，不用旧源码否决

## 原因

预期值若不从源端实现推出，测试会把源端本来的行为判成缺陷：只比较相邻像素梯度的感知哈希对纯色图本就输出相同结果；源端先合并再与当前列表求交时，列表外的成员不会被选中。把“测试即契约”用在这类期望上，修复会把产品从源端语义改开（改算法、放宽过滤、耦合两组数据）让测试转绿。规格条目本身可能就是误译来源，不能凭它覆盖源端行为。

## 做法

1. 对每个用例用源端实现（或已确认复刻源端数值类型的目标实现）逐步手算预期；源式含 float 时按 float32 运算规则计算，并至少给一个与 double 结果不同的样例。选区分性样本时避开源算法的退化输入（如梯度哈希不用纯色或常量图），或把预期写成源端的实际输出。
2. 复制相邻用例的夹具时，确认预期中的成员满足被测函数的过滤条件（如确实在 mock 的可用列表中）；只有改变产品过滤语义才能变绿的用例，先判为夹具错误。
3. 条目文字与实现冲突、又怀疑归属其他功能时，先查源端写入点与其他功能规格；无法确认就记为规格待确认，不直接写成要求当前方法实现的失败用例。
4. 分诊时先用同一输入核对源端实现；源端得出同样结果时，按测试契约问题记录（manual_review 或退回设计），不标为源码缺陷，也不建议改算法。
5. 修复时失败期望与已核的源端语义矛盾，就在 BLOCKED 或处置提示中写明源端行为和需要修正的用例或规格条目，保持产品与源端一致；不按其他用例反推编码方向凑出通过。
