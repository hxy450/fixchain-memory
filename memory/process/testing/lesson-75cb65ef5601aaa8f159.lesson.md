# 单测失败分诊与修复时先用同一输入核对源端：源端同样如此就按测试契约问题上报，不改产品语义迁就测试

ID：`lesson-75cb65ef5601aaa8f159` · 版本：1

[本主题](index.md)

## 何时使用

验证阶段对单元测试失败做分诊、写问题文件，以及修复代理处理失败用例时

## 适用情境

修复代理被要求以测试为契约、通常不能改测试，但可用 BLOCKED、manual_review 或处置提示上报；失败用例的期望可能来自比源端更严或与源端相反的测试设计或规格条目。

## 例外与边界

- 当前规格或已批准决策明确要求目标偏离源端行为，此时按规格修复并记录差异

## 原因

把“测试即契约”用在与源端矛盾的期望上，会让修复把产品从源端语义改开：修复者自己已看出源端同样不满足、或源端两组数据互不同步，仍改算法或耦合数据来让测试转绿。来源中分诊者写明了失败机制，却没核对源端对同一输入也会“失败”，就把它记成源码缺陷并建议改算法；三次修复分别给哈希加了亮度位、放宽了收藏的求交过滤、让设置页收藏同时写入另一页的收藏组，测试通过，但行为与源端不再一致。

## 做法

1. 分诊时先用同一输入核对源端实现；源端得出同样结果时，按测试契约问题记录（manual_review 或退回设计），不标为源码缺陷，也不建议改算法。
2. 修复时失败期望与已核的源端语义矛盾，就在 BLOCKED 或处置提示中写明源端行为和需要修正的用例或规格条目，保持产品与源端一致；不按其他用例反推编码方向凑出通过。
