# 交互修复未经设备点击验证、验证被环境阻断或功能点不可观察时，交付结论标为未验证并回流为待补项；修复前就存在的字符串不作 RED/GREEN 依据

[本主题](index.md)

## 何时使用

缺陷修复与验证阶段，修复“点击没有反应”一类交互问题并选择回归验证方式时；验证阶段功能点因宿主不可达或数据未加载而无法观察时

## 适用情境

页面菜单项、按钮已绑定 onClick 却点击无效；设备可连接，但 UI 测试在启动 Ability 阶段超时，修复者考虑用 grep 结构契约代替设备断言。或验证阶段某些功能点因宿主不可达被 BLOCKED、页面因数据未加载看不到内容。

## 原因

没有复现就按猜测改容器，再用修复前已存在的字符串做契约，改前改后都会通过，“已修复”的结论没有依据；BLOCKED 与看不到的页面在汇总中消失，缺陷留到用户手里。来源中修复者未复现就把菜单改成锚点菜单，测试超时后改用 grep 契约，编译又被阻断，仍在交付中写“点击后切换模式”，用户随后报告仍不能切换；另两处验证把受阻功能点和因加载问题看不到的列表当作通过或静默放过，相关缺陷一直保留到修复期。

## 做法

1. 修复“点击没有反应”前先在设备复现并分层定位：用 uitest 点击（如 hdc shell uitest uiInput click）后 dumpLayout，确认是菜单未弹出、点击未命中还是回调未改状态，再决定改哪一层。
2. UI 测试被环境问题阻断时，改用 uitest 点击 + dumpLayout 做设备断言（点击后标题、日期等可见状态的变化）；修复前已存在的源码字符串在修复前后都会通过，不作为 RED/GREEN 依据。
3. 编译被阻断、没有完成设备验证、功能点因宿主不可达被 BLOCKED 或页面因数据未加载不可见时，在交付说明中标为未验证，并回流为待补项或用静态检查覆盖，不写成已修复或通过。
