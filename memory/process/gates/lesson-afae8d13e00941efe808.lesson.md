# 交互问题先复现并分层定位、确认触摸可达再改约束；未经设备验证、被阻断、不可观察或被点名为风险的结论标为未验证并回流，修复前已存在的字符串不作 RED/GREEN 依据

[本主题](index.md)

## 何时使用

缺陷修复与验证阶段，修复“点击没有反应”“滑不动”一类交互问题并选择回归验证方式时；验证阶段功能点因宿主不可达或数据未加载而无法观察时；收尾或收敛时，准备把被点名为风险、只能界面判定的验收项写进已实现清单时

## 适用情境

页面菜单项、按钮已绑定 onClick 却点击无效；设备可连接，但 UI 测试在启动 Ability 阶段超时，修复者考虑用 grep 结构契约代替设备断言。或验证阶段某些功能点因宿主不可达被 BLOCKED、页面因数据未加载看不到内容。也包括弹层、卡片内一片控件全部不响应点击或滑动，候选原因同时有祖先节点的命中测试设置与滚动容器的尺寸约束；或执行者已把只能靠界面判定的验收项点名为风险，生成期不能编译运行、没有真机。

## 原因

没有复现就按猜测改容器，再用修复前已存在的字符串做契约，改前改后都会通过，“已修复”的结论没有依据；BLOCKED 与看不到的页面在汇总中消失，缺陷留到用户手里。来源中修复者未复现就把菜单改成锚点菜单，测试超时后改用 grep 契约，编译又被阻断，仍在交付中写“点击后切换模式”，用户随后报告仍不能切换；另两处验证把受阻功能点和因加载问题看不到的列表当作通过或静默放过，相关缺陷一直保留到修复期。命中测试会让整棵子树失去响应，表现与尺寸约束错误相同；同时改几处时，修好后会把效果记到错误的改动上，形成错误经验。收尾者凭结构派生宣称风险已处置而没有往返验证时，这些项随后都在验证期成了工单。

## 做法

1. 修复“点击没有反应”前先在设备复现并分层定位：用 uitest 点击（如 hdc shell uitest uiInput click）后 dumpLayout，确认是菜单未弹出、点击未命中还是回调未改状态，再决定改哪一层。
2. UI 测试被环境问题阻断时，改用 uitest 点击 + dumpLayout 做设备断言（点击后标题、日期等可见状态的变化）；修复前已存在的源码字符串在修复前后都会通过，不作为 RED/GREEN 依据。
3. 编译被阻断、没有完成设备验证、功能点因宿主不可达被 BLOCKED 或页面因数据未加载不可见时，在交付说明中标为未验证，并回流为待补项或用静态检查覆盖，不写成已修复或通过。
4. 一片区域内控件全部不响应时，先点一下其中可点的控件确认触摸能否到达，并检查祖先节点的 hitTestBehavior；确认可达后再调整尺寸约束。每次只改一处并复测，记录是哪一处改动让行为恢复。
5. 被点名为风险且只能界面判定的验收项，不凭结构派生写进已实现清单；列入验证阶段必测项，或在收尾前做一次真机或模拟器往返核对。
