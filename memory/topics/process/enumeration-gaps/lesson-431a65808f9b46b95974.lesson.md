# 按 feature 切分规格归属时，源 ViewModel 的每一步都要有 feature 以数据流和验收认领；委托出去的步骤写成跨 feature 契约

ID：`lesson-431a65808f9b46b95974` · 版本：4 · 阶段：spec · 主题：[process/enumeration-gaps](index.md)

概要：ViewModel 每步须有 feature 认领或跨契约

信号：`initData`, `getPlaceById`, `queryPlaceById`, `homeV2`, `DAO`, `ViewModel`, `Fragment`, `Activity`

## 何时使用

规格提取阶段，按目录或 feature 划分源码归属、把源端 ViewModel 的数据准备与列表组装写进各 feature 的数据流和对接点时

## 适用情境

源端 ViewModel 在请求前或列表组装时有中间步骤（按 areaId 查本地库补齐经纬度、把定位城市插入列表首位并去重、恢复与回写选中项）；目标规格把 DAO 划给城市 feature、天气 feature 只写“消费当前城市选择”，或双方都声明不认领某个容器 ViewModel；规格作者对部分类只读了函数签名。也包括源 Fragment 的设置项动作（清缓存、检查更新）或回前台刷新链被委托给其他 feature，而接收方规格没有对应验收项；以及 API 表列出的端点被注成“归某 feature 消费”，各方都不在服务接口中生产它。也包括源 Activity、控制器或接口实现类里的回调链与跨方法会话（启动、逐帧累积、完成、取消，或完成回调里的状态复位、续拍、错误恢复，键盘/遥控导航状态机），一方规格写“归另一 feature”，对方规格只覆盖触发侧或只把这些方法当作已有动作调用。

## 原因

按所有权拆分后，被委托出去的步骤两边都不写：消费方只写“使用当前选择对象”，提供方只发布对象，不认领“先查库补齐”“定位项置顶”这类组装逻辑，实现者照规格接线后行为缺失。来源为同一应用：天气规格作者读到请求前按 areaId 查库补齐经纬度的完整链，却把城市解析划给城市 feature，两个规格都没有写这一步，默认城市不带经纬度，请求发出空坐标；多城市容器 ViewModel 只读了签名，定位城市插入首位的逻辑无人认领。

## 做法

1. 规格提取时逐步列出源端请求前与展示前的准备链（例如 initData → getPlaceById → queryPlaceById → homeV2），每一步写进某个 feature 的数据流与 AC，并写明首页与各详情入口都使用补齐后的对象。
2. 委托给其他 feature 的步骤写成跨 feature 契约：提供方接口、调用时机、“输入可能只有 ID”的情形；对接点写“← 另一 feature 的列表”时，核对对方确实认领了该源码，未认领就在一方补上契约或登记缺口。
3. 对只看过签名的容器 ViewModel，展开 init、loadXxx 的函数体，确认列表组装顺序、插入位置与去重规则。
4. 委托设置项动作或刷新链前，打开接收方 feature 的规格与切片账本，确认已有对应验收项与工件；API 表中源端在用的端点要落到某个服务接口的唯一生产方，不以“归某 feature 消费”结束。覆盖审计判定某个活 ViewModel 已被承接时，逐个调用面找到对应验收项。
5. 源端回调链、跨方法会话或导航状态机被写成“归另一 feature”时，打开对方规格确认它认领的是执行侧（复位、续拍、多帧采集、行导航）而不只是触发侧；没有就在一方补 AC（进入条件、各步骤、取消与退出）并在对接点写明状态机归属。
