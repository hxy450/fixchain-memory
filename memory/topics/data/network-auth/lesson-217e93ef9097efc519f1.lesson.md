# 源端拦截器统一注入的请求头逐条迁到 HttpClient 默认头，头名与格式以源码为准，不照模板写 Bearer 前缀

ID：`lesson-217e93ef9097efc519f1` · 版本：2 · 阶段：execute · 主题：[data/network-auth](index.md)

概要：拦截器注入的请求头逐条迁到默认头，格式以源码为准

信号：`addHeader`, `TokenInterceptor`, `Authorization`, `Bearer`, `OkHttp`, `Interceptor`, `@ohos.net.http`

## 何时使用

网络基础层实现阶段，写 HttpClient 默认请求头与 Authorization 取值格式时

## 适用情境

源端用 OkHttp 拦截器（如 TokenInterceptor）给每个请求加鉴权、语言、平台、地区等头，接口声明上看不到这些头；目标端用 @ohos.net.http 自建 HttpClient，skill 参考模板示范 `Authorization: Bearer ${token}`；API 清单可能只给出拦截器路径和 header_write 一类标签。

## 原因

拦截器注入的头不出现在任何接口声明里，只看接口清单或规格就会漏；服务端可能把缺失的头当空串解析后报错（来源中缺 Platform-Type 时报 strconv.Atoi: parsing ""）。模板里的 Bearer 前缀是通用示例，源端可能直接放 token。来源中实现者手里只有清单里指向拦截器的 header_write 标签和模板，没打开拦截器源码，写出只含 Content-Type、X-Platform 的默认头，Authorization 还加了 Bearer 前缀。

## 做法

1. 写默认头之前打开清单里标为 header_write/token_injection 的拦截器源码，逐条对照 addHeader：头名、取值来源（token、系统语言、地区、平台常量）和格式。
2. 取源拦截器 addHeader 的键集合与目标默认 headers 的键集合做差集，差集非空就补齐，或在规格里写明不迁的原因。
3. 模板里的 `Bearer ${token}` 只当结构参考，Authorization 等头的格式以源码为准。
