# 拉起外部应用或系统能力前的可用性与权限门控逐段落实：隐式 Want 先 canOpenLink，不靠 startAbility 抛错

ID：`lesson-948d876672049969b865` · 版本：3 · 阶段：spec/execute · 主题：[app/capability/launch](index.md)

概要：隐式 Want 先 canOpenLink 预检，不靠抛错

信号：`bundleManager.canOpenLink`, `querySchemes`, `17700056`, `startAbility`, `resolveActivity`, `hasSystemFeature`, `IntentChecker.isAvailable`, `ACTION_SENDTO`, `FEATURE_CAMERA`, `mailto:`, `geo:`

## 何时使用

实现阶段把 IntentChecker.isAvailable、resolveActivity、hasSystemFeature 或运行时权限请求之后再 startActivity 的源方法迁为 startAbility、picker 调用时；规格阶段为这类 helper 写目标服务契约时

## 适用情境

源方法按“可用性探测 → 权限 → 拉起 → 结果或回退”组织，例如 geo: 无接收者时转地图网页、mailto 走 ACTION_SENDTO、FEATURE_CAMERA 不可用时提示且不建附件；目标准备直接 startAbility 或调用 picker，用 catch 代替预检，或把探测推给通用的打开链接函数。

## 原因

隐式 Want 没有合适接收者时不一定抛错：系统可能弹出选择框，或按隐式 Want 匹配规则（action、uri 前两条匹配失败且 uri 为文件路径时，按文件后缀取 MIME 类型再与 skills 的 type 匹配；HarmonyOS 文档 explicit-implicit-want-mappings，访问于 2026-10-17）命中意外的应用乃至本应用，catch 里的回退不会执行；把探测折叠进 catch 或只留分类函数，源端的提示与回退分支就丢失。

## 做法

1. 对照源方法逐段列出“预检 → 权限 → 拉起 → 结果或回退”，每段写出目标步骤；规格的服务契约为动作（ACTION_SENDTO、ACTION_DIAL 等）与可用性探测都给出目标符号，不只留 scheme 分类函数。
2. 隐式 Want 拉起外部应用前用 bundleManager.canOpenLink(link) 预检，并在 module.json5 的 querySchemes 登记该 scheme（未登记时报 17700056，见 SDK @ohos.bundle.bundleManager.d.ts，API 12 起）；mailto:、geo: 这类不带“//”的链接按 scheme:// 形式探测；无接收者时走源端的回退或提示分支。
3. 源端的设备能力与权限门控（能力不可用时提示、权限被拒时不建文件不拉起）落成目标侧的能力判断与相同的用户可见结果；目标 API 在 d.ts 声明 @permission 时先申请权限再调用。
