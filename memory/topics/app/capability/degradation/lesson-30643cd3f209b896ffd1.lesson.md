# 后台 Worker 计时与带动作的进度通知迁到 HarmonyOS 时，降级只覆盖做不到的执行载体：保活窗口内保留逐拍刷新与静默按钮，挂起后交代理提醒，回前台按步骤表补算并持久化会话

ID：`lesson-30643cd3f209b896ffd1` · 版本：2 · 阶段：spec/plan/execute · 主题：[app/capability/degradation](index.md)

概要：后台计时降级只砍执行载体，保留逐拍刷新与回前台补算

信号：`WorkManager`, `elapsedRealtime`, `PendingIntent.getBroadcast`, `backgroundTaskManager.requestSuspendDelay`, `SEND_COMMON_EVENT`, `commonEventManager`, `reminderAgentManager`, `NotificationRequest`, `AppStorageV2`, `systemDateTime.getUptime`, `TimeType.STARTUP`, `START_ABILITY`

## 何时使用

规格提取与决策阶段，为源端后台计时任务（WorkManager Worker、前台服务）及其进度通知、通知按钮制定替代路径、差异验收与平台差异决策时；实现阶段按这类决策写计时会话与通知时

## 适用情境

源端 Worker 逐拍刷新进度通知，在后台跨步推进：计时步结束续下一步，需输入步停住，末步发完成通知。偏移以 elapsedRealtime 计，任务经 WorkManager 持久化，回前台读取进度。通知按钮经 PendingIntent.getBroadcast 交给后台处理，不拉起应用。目标为第三方应用，退后台后会被挂起；规格准备写成“退后台停摆 + 单条静态常驻通知 + 按钮拉起应用 + 回前台从剩余时长续跑”，会话只放进程内状态。

## 原因

平台限制排除的只是“后台长驻执行”这个载体。进程存活期间的逐拍刷新、步骤切换和不拉起应用的按钮动作仍然做得到；回前台的跨步推进、需输入步停顿与完成判定，也能由锚点加步骤表纯计算复现。把“没有长驻 Worker”扩大成整体降级，这些可观察语义就被删掉。会话只放在进程内存、锚点用墙钟时，进程被回收或系统校时后也无法正确恢复。

## 做法

1. 先把源后台任务拆成执行载体（长驻 Worker、广播接收器）和可观察语义（逐拍进度、步骤切换、按钮动作、完成通知、回前台状态），逐项写明目标通道；只给确实不可用的载体登记差异。
2. 进程存活期间，或短时任务（backgroundTaskManager.requestSuspendDelay；项目可申请对应后台模式时用长时任务）的保活窗口内，保留进程内逐拍刷新与步骤切换。通知按钮在进程存活时用 wantAgent.OperationType.SEND_COMMON_EVENT，由 commonEventManager 订阅后静默处理，挂起态才用 START_ABILITY。挂起后的步骤到期与完成交 reminderAgentManager 代理提醒（按 d.ts 的 @permission 声明权限）。进度条先核对 NotificationRequest 的模板进度能力，不预设第三方通知没有进度字段。
3. 回前台由锚点与步骤表纯计算：后台时长越过当前步时逐步扣减、跨步，遇需输入步停住，越过末步进入完成态，与持久化恢复共用同一函数。差异验收覆盖后台时长超过当前步剩余、跨多步、停在需输入步与已完成这几种场景，不只测单步内恢复。
4. 会话记录（步骤、锚点、剩余量）落盘（如 preferences），并在进程重建后恢复；AppStorageV2 只在进程内存活，不能作唯一载体。锚点用不受校时影响、计入深睡眠的单调时钟（elapsedRealtime 对应 systemDateTime.getUptime(TimeType.STARTUP)），并以项目 d.ts 的 @since 对照 compatibleSdkVersion。
