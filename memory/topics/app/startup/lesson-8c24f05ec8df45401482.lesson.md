# 迁移启动链路时打开闪屏各去向页的初始化入口，列出冷启动请求与登录态组合的处理位置；源端推迟到主页处理的也要迁到位

ID：`lesson-8c24f05ec8df45401482` · 版本：2 · 阶段：spec/execute · 主题：[app/startup](index.md)

概要：迁启动链路时列出各去向页初始化请求与登录态组合

信号：`initRequestData`, `SplashActivity`, `MainActivity`, `refreshToken`, `Interceptor`, `onCreate`, `StartupViewModel`

## 何时使用

启动链路迁移与功能切片划分阶段，确定已登录、未登录冷启动要执行哪些请求，以及各登录态组合去向哪里时

## 适用情境

源端闪屏只做路由（如已登录 → 主页、未引导 → 引导页、无 token → 静默游客登录），刷新 token、拉配置等请求写在主页 Activity 的初始化方法里；token 失效等状态靠进入主页后的刷新与拦截器踢登处理；目标端用启动 ViewModel 承载闪屏路由。

## 原因

只迁闪屏的分支，会漏掉路由目标页进入时发出的请求；这些请求常不属于任何功能域，划分切片时也容易没人认领。来源中启动链路迁移者被要求读透启动顺序，计划读主页 Activity 却没读，已登录分支直接进主页，漏掉了启动刷新 token；功能索引也没把主页 Activity 的初始化请求归到任何功能。之后目标端出现“有用户信息但 token 为空”的状态，源端这时靠进入主页后的刷新与失效码踢登处理，目标端这两段都没迁，用户只好要求在启动时加兜底。

## 做法

1. 打开闪屏每个去向页的初始化入口（如主页 Activity 的 initRequestData），列出冷启动请求清单（刷新 token、拉配置、版本检查、权益等），逐项落到对应 ViewModel 或标为未迁。
2. 按启动判定用到的持久化状态列出组合（用户信息有/无 × token 有/无 × 是否完成引导），写明源端各组合的去向；源端交给后续流程处理的组合，确认目标端的后续流程已经接通，不只照搬闪屏的分支。
3. 划分功能与切片时用端点调用方反查（如清单里刷新接口的 callers 指向主页 Activity），确认宿主 Activity 的初始化请求有功能认领。
