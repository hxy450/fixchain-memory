# 源端应用内分享面板（自定义渠道列表）按交互形态复用目标的应用内分享弹层并逐渠道映射，不以系统分享面板整体替代

ID：`lesson-b366cf7ae68525577f57` · 版本：3

[本主题](index.md)

## 何时使用

规格提取、能力核对与功能实现阶段，为源端分享入口选定目标工程已有的分享能力，并把面板的各渠道接到目标入口时；按用户要求更换分享面板时

## 适用情境

Android 源端用应用内分享面板（如 ShareUtil.shareImage 加 ShareItem 渠道列表，按渠道分发到各社交平台、动态、蓝牙等），其中可能有把截图带进 App 内发布页的渠道；目标工程同时有 systemShare 封装和应用内分享弹层组件及各渠道发送工具；需求要求复用现有能力，规格的依赖接缝可能已写明各渠道与承接页参数，验收条目却只写“分享截图”。

## 例外与边界

- 源端本身调用系统分享（Intent.ACTION_SEND、createChooser），或用户已确认改用系统面板并登记了这项 UX 差异

## 原因

系统分享面板与应用内渠道面板交互形态不同，App 内渠道（发动态等）也无法经系统面板到达。只在工具目录里按 share 关键词检索既有能力，会找到系统分享封装、漏掉组件目录下的应用内弹层；分享整体改成一次系统面板调用后，验收只核截图内容，漏掉的渠道能通过自检。

## 做法

1. 核对既有能力时，检索范围覆盖组件目录与已有页面中承载渠道列表的弹层组件及各渠道发送工具（例：ShareTo*、Share*Sheet、Share*Dialog、bindSheet 渠道项、各平台图片发送工具）；核对表写出源端交互形态（应用内面板或系统面板、渠道列表、分享图片还是链接）与目标候选，形态一致才算复用既有能力。
2. 从源码渠道列表与分发分支逐项列出全部渠道，每个渠道映射到目标既有入口（App 内渠道按承接页参数接入，如把截图路径作为发布页入参，并保留登录检查）或明确的缺目标提示；交付报告逐渠道写明接入状态。
3. 只能用系统分享替代时，作为“系统组件 vs 应用内”的 UX 差异写入台账请用户确认，不在“复用现有能力”的笼统批准下默认替换；更换分享面板时重新对照源端渠道清单补齐。
4. 规格把渠道清单写成可验收条目（每个渠道一条或组合断言），不只写在依赖接缝说明里。

来源支持：2 张卡 · 1 次迁移 · 1 个应用
