# 单行省略先查完整 SDK 能力：无现成映射时 middle 测量保头尾、start 测量保尾部，不统一降级为尾部省略

ID：`lesson-a184209501ba02cb62e7` · 版本：3

[本主题](index.md)

## 何时使用

界面实现阶段，转换单行文本的省略位置（ellipsize），而目标 TextOverflow 枚举没有对应成员时

## 适用情境

源 TextView 用 android:ellipsize="middle"（或 start）配合 lines=1/maxLines=1 显示文件名等尾部有意义的文本，可能还有关键字 Span 高亮；ArkUI Text 的 TextOverflow 只有尾部 Ellipsis 等模式，映射参考只给 end → Ellipsis 示例。

## 例外与边界

- 项目已批准以尾部省略作为平台差异

## 原因

尾部省略会截掉文件名最有区分度的扩展名，用户可见差异真实存在；只凭一个枚举的部分检索结果就判定无能力，再以 TODO 推给后续阶段，降级往往保留到交付。来源未核实 ellipsisMode 等属性在当时 SDK 及 Span 高亮组合下是否可用。

## 做法

1. 先在 SDK 声明中全文检索 Text 与省略位置相关的属性；没有现成能力时在本阶段实现测量截断：onAreaChange 取可用宽度并换成 px，getUIContext().getMeasureUtils().measureText 以相同字号测量，按源省略位置二分求可放下的文本：middle 用“头 + … + 尾”（多余字符可优先留尾），start 用“… + 尾”而不保头；切点避开代理对，按宽度、文本及实际字体、字号、字重、间距、缩放等排版输入缓存，相关样式变化时使旧结果失效，不在 build() 里测量。
2. 有关键字高亮时，先保留源文本上的匹配区间和样式，再将区间投影到截断后仍可见的头尾片段并构建 Span；不要仅对新字符串重跑完整关键词匹配而丢掉被切断词的原样式。按当前文本核对与源端先 span 后省略的可见结果，不把截断顺序本身当等价证明。
