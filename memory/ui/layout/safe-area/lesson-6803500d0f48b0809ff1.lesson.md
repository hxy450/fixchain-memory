# Scaffold 无 topBar 时 innerPadding.top 就是状态栏 inset：子页无 statusBarsPadding 不能推出「不做顶部避让」

ID：`lesson-6803500d0f48b0809ff1` · 版本：1

[本主题](index.md)

## 何时使用

规格提取阶段，为壳页（Scaffold / Tab 宿主）及其子页、页内浮层写「谁避让状态栏」的沉浸式与安全区契约时

## 适用情境

Android 子页自身没有 statusBarsPadding，但作为 Material3 Scaffold 的 content 经 modifier.padding(innerPadding).consumeWindowInsets(innerPadding) 嵌入（无 topBar、contentWindowInsets 默认 systemBars）；目标端父容器不为 Tab 内容区加顶部避让，而是把状态栏高度以 @Param statusBarHeight 下发。

## 例外与边界

- Scaffold 有 topBar 或覆写了 contentWindowInsets，此时 innerPadding.top 不再等于状态栏高

## 原因

spec 作者读到了 `padding(padding).consumeWindowInsets(padding)`，却写成「只消费底栏高度，顶部状态栏由各 Tab 页自行处理」，随后 Profile 页被指示「不做顶部占位」、FilterScreen 浮层「跳过安全区契约」，同一误读经 F001-AC44 固化；F003 worker 纠正后只回改了 page_0003，同区域其他 spec 与裁决未回改。

## 做法

1. 按 modifier 传递链（Scaffold content(padding) → addHomeGraph(modifier.padding(padding)) → Page(modifier)）逐边写出 innerPadding 的实际来源：无 topBar 时 top = 状态栏 inset，有 bottomBar 时 bottom = 底栏高；再判定目标端该页顶部由谁避让。
2. 同一内容区内的所有层（列表、顶栏、浮层/对话框）共用一个避让口径；收到某页的 inset 纠正时 grep 引用同一区域的其它 page/feature spec 一并改，并把「宿主 padding 还是子页自理」落成一条可引用的决策。
3. 为每个子页写明应消费 statusBarHeight 的数值来源（innerPadding top）或为 0 的依据（父级已加避让）。

## 检查

- Android 内容块在 [状态栏底, 底栏顶] 内居中/对齐，目标端也必须在同一区间内；浮层遮罩起点 y 等于状态栏高，不压灰状态栏。
