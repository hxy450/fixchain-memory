# 视觉修复以源布局与源码分支为准：截图尺寸差先折算成 vp 对照，容器尺寸与自绘组件的绘制尺寸同源修改，截图里缺少的入口先查渠道与开关分支，文档截图与 @Preview 示例不当应用真值

ID：`lesson-8119d8bf0b58e4daac24` · 版本：4

[本主题](index.md)

## 何时使用

视觉校验与修复阶段，根据截图差异撰写工单，决定修改固定尺寸、列数、背景，删减截图中没有出现的入口与区块，或按基线截图选定空态等文案与图标时；按差异单调整包裹自绘组件（Canvas 日历等）的容器高度与折叠范围时

## 适用情境

源端基线截图与目标截图来自不同设备或屏幕密度，并排对比显示目标主内容“偏小”或“偏上”；目标页的主要区块已按源布局 dp 字面值写入固定高度与 marginTop，并与底部 Tab 共享有限的纵向空间。截图也可能只来自某个渠道、会员或开关变体，或只反映某一时刻的天气与昼夜状态；源 Fragment 中有按 getChannel()、开关对入口 setVisibility 的分支。也包括把源仓库 docs/assets 下的截图或 @Preview 预览当作基线，而其中的示例文案、图标与应用实际调用链不同的情形。也包括外层容器按“行数 × 行高”计算高度并 clip、同一行高还决定手势折叠范围，而行高实际由内部 Canvas 的常量绘制；差异单只有“行高更大”一类文字结论。

## 原因

跨设备截图的像素比例差包含密度与逻辑宽度差，不等于 dp 值写错；只凭观感把已等于源值的固定尺寸放大，累计高度会超出可用空间，底部内容被 Tab 遮挡。来源中视觉协调者没有把差异折算成 dp，也没有与源布局值对照，就按“整体缩小 10%–15%”把地图区、主按钮、统计卡放大并继续加大间距；之前的巡检报告已写明这些尺寸与源端一致。另一应用中两次：黄历页修复者按单张截图删掉了两个 tab、灵签、查看黄历、宜忌与解梦区，而截图来自在代码里隐藏这些入口的渠道变体，另一渠道的截图全部可见，几天后又整体补回；它读取 Fragment 时输出被截断，没看到渠道分支。天气首页返修以单张截图为真值，把只绑定两天的概览写成三列、首卡与头图取截图估值，并把按状态切换的背景改成固定夜景图。第三个应用的修复者已读到空态实际引用的字符串 key 与取值，仍按 docs 截图写成只在 @Preview 中出现的“No devices found”纯文本空态，后一轮才按调用链改回图标加标题加提示。另一应用的视觉修复者没看并排截图、没读源布局行高，就把容器行高和折叠范围从 53 压到 45，Canvas 仍按 53 画行，最后一行被裁掉、下方面板像盖住日历，且随月份行数变化；源端与目标行高本来一致。

## 做法

1. 写尺寸工单前，按两端设备各自的密度/逻辑宽度把截图差异折算成 vp，与源布局 dp 值、目标代码当前值三方对照；目标值已等于源值时，改查视口、安全区或容器层级，不写“对齐固定高度”，源码定位不能留空。
2. 拟改值偏离源布局值时，要有源码或资源固有尺寸依据，不用放大常量补偿截图比例。
3. 放大元素前累计所有固定高度与 margin，确认底部内容仍位于 Tab 之上。
4. 截图中缺少而源码布局存在、且有点击逻辑的 tab、入口或区块，先在 Fragment/Activity 中搜索其 setVisibility、getChannel、会员或开关分支，确认是运行变体还是已下线；属于变体时按忠实复刻保留完整入口或实现同等条件开关，并请用户确认截图所属渠道，不按单张截图删减。
5. 截图只代表某一时刻与状态：列数与区块数以 Adapter 实际绑定的数据项为准，背景以源码的状态选择逻辑为准，尺寸以源布局为准；读取出现截断就按单个文件重读后再下删改结论。
6. docs/assets 截图与 @Preview 中的示例文案、图标不是应用真值：选定字符串 key 或图标前，搜索它在应用代码中的真实引用；与页面实际调用链读到的不一致时以调用链为准。
7. 差异涉及自绘组件时，先定位实际绘制尺寸的来源（如 Canvas 的行高常量）；外层容器高度、clip 范围与折叠距离引用同一常量同步修改，不单独压缩外层容器。源端与目标值已一致时，回头复核差异单的成因。

## 可选检查

- 改动带 clip 的自绘容器后，用行数不同的数据（如 5 行、6 行月份）及折叠中间态截图，核对末行完整、相邻面板不遮挡。
