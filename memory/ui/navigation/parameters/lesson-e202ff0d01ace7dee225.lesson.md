# 同一路由参数被调用方与接收页当作不同语义（完整 JSON、实体 ID、预览地址）时，按源端契约拆成字段或在入口解析，不用格式判断把冲突屏蔽成占位

ID：`lesson-e202ff0d01ace7dee225` · 版本：1

[本主题](index.md)

## 何时使用

组件详情、编辑页等页面的实现或按截图补齐阶段，确定页面启动参数与编辑会话模型的契约时；构建修复为悬空引用补建该页依赖的模型与 ViewModel 时

## 适用情境

目标页只有一个字符串入参（如 resource），各调用方实际写入完整业务 JSON，页面内部却把它当实体 ID 请求详情、又当图片地址显示；源端页面按已安装实例、用户数据、缓存的完整 JSON 等顺序恢复会话。

## 原因

一个参数同时承担几种语义时，每种用法都会让另外几种调用出错：整段 JSON 被当作 ID 拼进 /xxx/{id}，预览拿到 JSON 不显示。用 startsWith('{') 一类格式判断把 JSON 排除出预览只是掩盖冲突，详情请求仍然错误；补建模型时只按一个调用方用到的字段建模，又把缓存 JSON、预览地址等上游已有字段丢掉，冲突被固化进会话模型。

## 做法

1. 接入或改写页面前，检索全部 push 或构造该页的调用方，列出它们实际写入参数的值，再对照接收页内部对该参数的每种用法；不一致时按源端契约拆成实体 id、业务 JSON 与预览地址等独立字段，或在页面入口解析 JSON 取出 id 与预览字段后再分发。
2. 无权修改契约时把冲突登记为结构化缺口并报告，不用格式判断把一种语义排除出某个用法，让页面看起来不报错。
3. 为悬空引用补建会话模型或 ViewModel 时，以规格数据流与上游 DTO（如列表项的预览地址、原始 JSON）建模并保留缓存 JSON 入口，不只按单个调用方当前用到的字段补最少集合。

## 可选检查

- 收口前取一条真实入口数据走查：从列表或合集进入，确认详情请求路径只含实体 id、预览取自 JSON 的预览字段。
