# pushPathByName 传参用目标页 instanceof 的类：ArkTS 名义匹配，同形局部类与 JSON 对象不命中

ID：`lesson-b714378f18d168bce81c` · 版本：2

[本主题](index.md)

## 何时使用

页面转换与功能切片接线阶段，为 pushPathByName 选择参数类型、在 NavDestination onReady 解析路由参数时；计划阶段为分批或并行生成的页面确定路由参数契约时

## 适用情境

目标页在 onReady 用 instanceof 收窄 pathInfo.param；源端路由是 profile/{id} 一类字符串模板；多个页面由不同写者分批或并行生成，canonical 参数类可能在路由宿主或独立路由模块里，也可能尚未建立；部分参数来自 API 响应 DTO（JSON.parse 得到的普通对象）。

## 原因

ArkTS 类按名义匹配：字段完全相同的另一个类的实例、或 JSON.parse 得到的普通对象，instanceof 都为假，目标页走进兜底分支后打开空白页或以 id=0 提交，编译与结构检查都不报错。契约未定、怕循环导入或照抄兄弟页时，各写者自建同形类，偏差随页面复制。

## 做法

1. 写 pushPathByName 前打开目标页的 onReady（或路由参数模块），确认它 instanceof 的类与字段，直接 import 该类构造实例（如 new ProfileParam(id)）；不自建同形类，也不依赖目标页的形态兜底。
2. 担心 import 页面成环时，把参数类移到不 import 页面的独立路由模块再引用，不在生产页复制一份。
3. 消费端参数可能来自多个生产页或是 API DTO 时，不以 instanceof DTO 类判定：导出本页专属参数类，或对非实例按 id、name 等字段收窄。
4. 计划阶段在分批或并行派发页面前固定 canonical 参数类所在文件与字段，并在每份转换或接线派工里写明导航参数一律 import 该模块。
5. 收尾时发现某处 instanceof 不命中，就用 pushPathByName 与 class *Param 检索全部生产端，逐一对照目标页接受的类型；确认的断裂同轮修完，不只记为待验证。
