# Activity 级按键映射到页面根 onKeyEvent：核实际焦点链与消费结果，保留源按钮的获焦能力，不以 consumed:0 判链未经过页面

ID：`lesson-80e1d2c095a3698a7156` · 版本：3

[本主题](index.md)

## 何时使用

页面实现与输入接线阶段，为源端 Activity 级硬件按键回调（onKeyDown、dispatchKeyEvent）选择 ArkUI onKeyEvent 的挂载节点时；接收“焦点获取归本任务”一类移交时

## 适用情境

安卓源在 Activity 上覆写 onKeyDown 或 dispatchKeyEvent 处理方向键、MENU、Ctrl+Z 等，不依赖某个 View 持有焦点；目标页面是 Navigation 下的 NavDestination 或 @Entry 页，交互由内部 Canvas、自绘子组件或 Image + onClick 承载。也包括页内没有 Button/TextInput 或 focusable(true) 组件，源端按键控件是缺省可获焦的 ImageButton/Button。

## 原因

ArkUI 按键沿焦点链派发：应核对当前实际焦点与根节点回调；consumed: 0 只说明未消费，不证明事件未经过本页，根容器也可能持焦。子组件的 onKeyEvent 也只有在焦点链上才会收到。来源中转换者误以为 NavDestination 不支持 onKeyEvent 而挂到 Canvas，返修中用 defaultFocus、onReady 时 requestFocus 给该子组件抢焦点都没生效，移到 NavDestination 后按键正常，获焦子节点的事件也会冒泡到这里。另一来源的页面把源端 ImageButton 都转成 Image + onClick，根节点上的 onKeyEvent 从未触发，给这些按钮设 focusable(true) 后方向键与 Ctrl+Z 才可用。“只写 focusable(true) 不会让它获焦”只针对把处理挂在子组件上靠抢焦点的做法，在来源第二种结构中，让对应控件可获焦是有效修复，不能据此证明所有页面根处理按键都必须额外有可获焦叶子。

## 做法

1. 源端是 Activity 级按键回调时，把 .onKeyEvent 挂在页面根节点（NavDestination 或 @Entry 根组件）上；按源端只在按下时触发的语义加 KeyType.Down 过滤，源端吞掉的键（如 MENU）同样返回 true。同时核实际焦点链并保留源控件的获焦能力：源端 ImageButton/Button 缺省可获焦，目标对应的 Image/按钮设 focusable(true)（源端焦点态不可见时把焦点框设为透明样式），焦点进入本页后事件冒泡到根节点。
2. 确需挂在子组件上时同时写出获焦机制，并确认页面显示后的实际焦点节点就是该组件；“某容器不支持 onKeyEvent”一类判断先查 SDK 声明。收到“焦点获取归本任务”的移交时，核实根回调、实际焦点与源要求的获焦能力均已接通，不以补一个可获焦组件的代码代替事件验证。

## 可选检查

- 对挂载点有疑问时，在设备上注入方向键查看 hilog 中的当前焦点节点与 consumed 结果；consumed: 0 只表示未消费；结合根回调日志、返回值、当前焦点及输入法分发判断链路。
