# Compose Scaffold 无 topBar 时 innerPadding 顶部就是状态栏 inset：目标端只在一处落实，同一内容区各层用同一基准

ID：`lesson-f64afc22d41b130f1628` · 版本：1

[本主题](index.md)

## 何时使用

规格提取与界面实现阶段，把 Compose Scaffold 的 content padding 与 consumeWindowInsets 拆成宿主壳与各子页（含页内浮层）的顶部避让分工时

## 适用情境

源端 Scaffold 不传 topBar、未覆写 contentWindowInsets（默认含状态栏），把 Modifier.padding(innerPadding).consumeWindowInsets(innerPadding) 交给嵌套内容；子页自身可能没有 statusBarsPadding，也可能另写 statusBarsPadding 或 windowInsetsTopHeight(statusBars + N)；目标端全屏窗口，由宿主 padding 或向子页下发状态栏高度来避让。

## 例外与边界

- Scaffold 传了 topBar 或覆写了 contentWindowInsets 时，innerPadding 顶部不再等于状态栏高，按实际来源推导

## 原因

无 topBar 时 innerPadding 的顶部分量就是状态栏 inset，padding(innerPadding) 已把整块内容放到状态栏之下；consumeWindowInsets 再让后代经 statusBarsPadding、windowInsetsPadding、windowInsetsTopHeight 这类按已消费量计算的修饰符取到 0（后代直接读取的原始 inset 不因此清零）。只看子页源码会两头出错：子页没写 statusBarsPadding 就推出“不做顶部避让”，或把子页里的 statusBars 项照译、再叠一次状态栏；宿主只让出底栏时，悬浮顶栏和页内浮层又会压到状态栏下。宿主统一避让与子页自理两种分工都出过错，出错点相同：同一条边没有恰好落实一次。

## 做法

1. 规格里按 modifier 传递链逐边写出 innerPadding 的来源（无 topBar 时顶部 = 状态栏 inset，有 bottomBar 时底部 = 底栏高），再把“宿主统一 padding”或“子页按下发的状态栏高度自理”定为一条可引用的决策；子页自身没有 statusBarsPadding 不能推出不避让。
2. 选宿主统一避让时：宿主内容区显式写顶部 padding（只靠 layoutWeight 让出底栏不算消费），子页把已被消费的 statusBars 项按 0 处理、只保留源码另加的固定值，不再订阅窗口避让值；报告写“宿主统一避让”前逐边核对代码里确有对应 padding。
3. 选子页自理时：同一内容区的每一层（列表首项、悬浮顶栏、浮层或对话框）都消费同一个状态栏高度，每个子页规格写明数值来源或为 0 的依据。
4. 收到某页的 inset 纠正时，检索引用同一内容区的其他页面与功能规格一并改，不只改被指出的那一页。

## 可选检查

- 有设备时用 dumpLayout 看子页第一个前景元素和浮层遮罩的顶边：应等于状态栏高；为 0 说明漏了避让，约两倍说明重复叠加。
