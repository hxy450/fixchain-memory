# 常驻 NavBar 或保活页会被子页覆盖再返回时，TextInput 获焦回调先判别是否由用户触摸引起，再写业务状态

ID：`lesson-4c476a62732697c56c22` · 版本：3

[本主题](index.md)

## 何时使用

规格提取阶段，把源端 remember（非 rememberSaveable）随组合销毁的状态翻译成目标复位方案时；界面实现阶段，把 TextInput 的焦点回调接到页面业务状态，且页面常驻 NavBar 或保活容器、会被 pushPath 覆盖时

## 适用情境

源页面离开组合时丢弃全部状态，其中 focused 等由框架焦点事件驱动的业务字段决定显示分支（如建议列表与分类）；目标页面常驻 Navigation 的 NavBar（或 Stack、Tabs 保活），经 pushPath 进入子页后再系统返回，框架可能把焦点交还该 TextInput。

## 例外与边界

- 源端用 rememberSaveable 等方式让焦点与输入在返回后保留：返回时恢复焦点本就符合源端行为，不做判别

## 原因

子页返回后，ArkUI 可能把焦点交还保活页上次获焦的输入框；onFocus 无条件上抛时，框架恢复的焦点会被当作用户聚焦写进刚复位的状态，返回后显示错误分支并拉起键盘。只把数据字段重置成新对象挡不住这次恢复，在 push 前 clearFocus 也不一定能阻止返回时的焦点恢复。

## 做法

1. 规格提取时，除数据字段外逐项列出目标框架会替用户恢复的界面状态及复位手段：焦点按下一步判别并 clearFocus，输入法用 TextInputController.stopEditing，滚动位置用 Scroller.scrollTo/scrollToIndex，选区用 TextInputController.setTextSelection；由框架事件驱动的业务字段，把“返回后为初始值”写成验收步骤：一次 push → 系统返回后 dump 对应组件状态。
2. 实现时 TextInput 加 onTouch 在 TouchType.Down 置标记，并设 enableKeyboardOnFocus(false)（非点击方式获焦时不拉起输入法，text_input.d.ts，API 11）；没有 touch-down 先行的 onFocus 视为框架恢复，执行 stopEditing 与 getUIContext().getFocusController().clearFocus()、不写业务 focused；有 touch-down 的照常处理，复位状态时一并清标记。
3. 上一步的判别只认触摸：页面需要支持外接键盘 Tab 导航或无障碍获焦时，这些获焦也会被当成框架恢复而清焦，判别条件需另行设计并实测（来源未覆盖这类获焦）。

## 可选检查

- 有设备时做一次 push → 返回往返：返回后显示初始分支、未聚焦、没有键盘；用户点击输入框仍进入聚焦分支并拉起键盘。
