# 提炼任务书：把一张卡写成候选规矩

## 这是什么

这是安卓转鸿蒙（ArkTS）迁移的经验库。一张「卡」是对一次迁移里某个错的调查记录：哪个阶段的子代理、在什么情境下、出了什么偏差，后来怎么修好的。卡里的做法是修好并验证过的。

规矩是这样用的：迁移里写规格、派工、写代码、迁资源的子代理刚做完一个任务，另一个 agent 来审。它看得到这个子代理读过的东西（安卓源文件、规格、派工说明、映射参考等）和交回的产物（规格文档、派工、鸿蒙代码、资源文件），拿着规矩一条一条判断：这个情景在不在，写得对不对，不对就改。所有规矩都按「任务刚做完、在审」来写，不分动笔前和动笔后。

你的工作是把每张卡写成若干条候选规矩，后面的步骤会把不同卡里相同的规矩合并、归族。

## 三条原则

1. **窄。** 一条规矩只讲一件事：一个触发对一个做法。审的人看一处就能判断适不适用；照做之后这条里没有剩下的事。
2. **带知识。** 能查清的直接写查清的结果和出处；因为随应用而变查不清的，写怎么查。不把「去查」「以 API 为准」留给用的人。
3. **按触发情景写。** 触发写的是那个子代理的视野：它读过的东西里看得到什么，它交回的产物里写错成什么样。审的人顺着自己手里的东西能对上规矩。

## 你要做的

给你的清单文件里每行是一张卡的文件（`work\cards\<卡号>.md`）。对每张卡写一个输出文件。卡与卡之间互不相干，一张一张做，写完一张、自检过了再做下一张。

卡文件里有：

- **情境**：卡的 title、when、description，以及卡里记的环境版本（鸿蒙 SDK、安卓 compileSdk、依赖库）。
- **诊断**（`diagnosis`）：调查的全过程，修好并上机验证过的做法和观察到的行为多写在这里。
- **建议**（`recommendation:1`、`recommendation:2`…）：每条建议的原文。
- **没核到的点**（有的卡有）：调查时没能确认的事。
- **调查图里的节点**：每个出了问题的产物涉及哪些文件和子代理、各自读到了什么、在哪里写错。只供理解情境，不能作 `support`。

结论前方括号里的内容（例如 `[case-…#recommendation:2]`）就是它在 `support` 里的写法。

## 一条规矩要满足的

格式和每一栏的写法见 `references\format.md`（同目录），那里有一条代码类、一条规格类的完整例子（`references\examples\`）。下面是必须做到的。

1. **一个触发对一个做法。** 卡里讲了几件不同的事就写几条，一张卡通常 1–4 条，最多 8 条。同一张卡里几条建议讲的是同一个触发、同一个做法，并成一条。
2. **标明审的是哪种产物。** `product` 是「规格」「计划与派工」「代码」「资源」之一。同一件事在几个产物上都有该做的，各写一条：规格里该写明什么是一条，代码该怎么写是另一条。文档类的产物这样归：规格页、源码理解笔记、决策台账、验收条目归「规格」；任务拆分、派工说明、移交项和占位的登记、覆盖清单和跳过清单归「计划与派工」。
3. **触发写审的人看得到的东西。** 每个触发有两栏，至少写一栏：
   - `read`：这个子代理读过的东西里看得到的写法（安卓源文件里的 XML 标签和属性、类名、方法名、资源类型、取值词；规格或派工里的说法）。
   - `wrong`：它交回的产物里写错的样子：出现了什么，或者少了什么。
   - 代码和资源类的规矩，写了的那一栏里至少要有一个代码标识符。规格和派工类的规矩，`wrong` 一定要写，写文档里看得到的说法或缺的那一项。
   - 流水线里固定出现的记号也算看得到的写法：规格、派工、代码注释和报告里固定的大写记号和编号（比如占位登记、移交项用的那些），可以写进触发和 `keys`，写成反引号括起来的原样也行。不许为了过检查编造占位标识符（`<Class>.<method>`、`stopXxx` 这类）：卡里没有确切写法的，就用文字写清楚看得到什么。
   - 同一件事在不同的写法下（View 的 XML、Java 代码、Compose）触发不同，各写一个触发，放在同一条规矩的 `triggers` 里。只写卡里出现过的写法，不要自己推想别的。
   - 只写平台和公共库的词。不写出事应用自己的类名、资源名、控件 id、文件名。
4. **默认行为成立的条件要写明。** 卡里的情形带着条件（比如背景不透明、主题是某一族、某个属性没写）时，把条件写进触发或 `scope`，不要写成无条件的默认。
5. **做法是能直接照着写的写法。** 写出目标的确切写法（接口调用、规格里该有的那一句或那一项），以及源端的每个值对应到哪个参数。1–3 步，每步标 `support`：出自这张卡的哪条结论。
6. **没有触发的不写成规矩。** 下面四种记进 `left_out` 并写明原因，不写成规矩：
   - 没有任何产物里看得到的触发的内容，即纯流程上的提醒（比如「动笔前回源码核对」「冲突时以 API 为准」「把错误记下来」）；
   - 要上机或截图才能做的；
   - 只对出事应用成立的；
   - 针对经验库本身的建议（比如「修订某条经验」「召回漏了某条」）。
7. **跟具体应用无关。** 不出现出事应用的名字、它的文件名和资源名、转录文件名和行号、「本例」「本应用」「该应用」，也不写哪个子代理当时做了什么。出事那个应用自己的取值（它的颜色、尺寸、文案）不带。
8. **限定和例外必须出自卡。** 卡里没说的例外不要自己加，尤其不要写「规格、计划或台账另有选择时可以不照做」这一类：上游文档本身可能就是出错的地方。卡里确实写了不适用的情形，写进 `exceptions` 并标 `support`。声明里写明的版本要求（`@since`）可以写进 `scope`，注明出自声明，这不算自己加的例外。
9. **给召回用的词。** `keys` 分 `read` 和 `product` 两栏，各 3–12 个：前者是读过的东西里会出现的词，后者是产物里会出现的词。代码和资源类只用平台和公共库的词；规格和派工类可以用文档里固定出现的说法（中文或记号），不限于代码词。
10. **能搜就写 `probe`。** 写错的样子如果能表达成在产物文件里搜一个正则，就写成 `{"pattern": "…", "note": "搜到说明什么"}`；表达不了的写 `null`。

卡里的某条建议本身就是一种查法时（看到哪一类写法 → 去哪查、怎么读出值 → 写成目标端的显式写法），照样写成一条规矩：触发可以是一类写法（「源控件没有显式写某个外观属性」「源端引用了平台或库提供的值，如 `@android:…`、`?attr/…`」），做法写查法，随应用而变的部分写进 `lookups`，固定的部分（解析的先后顺序、默认值定义在哪个文件的哪个符号）查实写进 `values`。不列各种情况的取值表。

## 带上知识库的事实

知识库指下面三类来源，怎么找、出处怎么写见 `references\knowledge-sources.md`：

1. **本机的鸿蒙 SDK**：`.d.ts` 声明文件，含注释。常见在 DevEco Studio 安装目录的 `sdk\default\openharmony\ets\` 下；HarmonyOS 专有的能力在 `sdk\default\hms\ets\` 下。
2. **本机的安卓 SDK 和依赖库**：`%LOCALAPPDATA%\Android\Sdk\` 下的 `platforms\android-*\data\res\`（平台资源）和 `sources\android-*\`（框架源码）；Gradle 缓存 `%USERPROFILE%\.gradle\caches\` 里依赖库的资源文件。
3. **OpenHarmony 官方文档的本地副本**：分支根目录下的 `work\ohdocs\zh-cn\application-dev\`（只有 .md 文件），总目录页是其中的 `Readme-CN.md`，从目录页顺着链接（相对路径）找确切的文件，不用猜。不联网取文档。文档和本机声明文件不一致时以声明为准。

对每条规矩，去知识库查和它的做法有关的事实：

- **能查清的，直接写查清的结果。** 接口的签名、参数、默认值、单位、枚举值，答案对所有应用都一样，查实了就写进 `how` 或 `values`，在 `refs` 里给出处。不要留一句「去查」「以 API 为准」。
- **查不清是因为随应用而变的，写怎么查。** 取决于应用的主题、编译版本、依赖库版本、资源的东西，写进 `lookups`：要查的是什么、去哪类来源的哪个文件里按什么找、找到之后怎么读出值。`where` 可以是源工程或目标工程里的某一类文件（写文件类型和找法，例如「源工程的布局 XML 里这个控件的 style 属性」），不写某个应用的文件名。可以附一个带条件的例子（「例：某主题下是某值」），不要写成让人照抄的答案。
- **每条出处必须带来源里的逐字原文。** 凭记忆知道、但在来源里找不到原文的，不写进规矩，记到 `gaps`。
- **源端不是安卓时**（比如 Web 框架、Flutter），三类来源里查不到的，写进 `lookups` 或 `gaps`，不硬凑出处。
- **依赖库代码里的事实**（不是资源文件）本机多半只有编译产物、没有源码。查不到原文的，按卡写，并记进 `gaps`。
- **卡里记的 SDK 版本和本机的不同时**，照本机的声明核实，在 `refs` 的 `version` 里写明核实用的版本；卡里观察到的行为出自别的版本的，在 `unverified` 里注明。
- **同族接口一并查。** 做法落在某个接口的参数、属性或枚举上时，用这个参数类型或枚举名在本机声明文件里搜一遍，把同样带它的其他接口也写进 `values`，各写各的完整签名并写明是哪个类的，`meaning` 里注明「同族接口」，在 `refs` 里各带原文。搜的词和搜到几个写进 `siblings_checked`；做法不落在具体接口上的，或者落在事件名、通用方法这类没有专门参数类型可搜的接口上的，写「无：」加原因。
- **上机验证过的结论不动。** 卡里修好并验证过的做法优先。知识库里查到、但卡没有验证过的替代写法，不写进 `how` 和 `values`，记到 `alternatives_unverified`。知识库的说法和卡里上机看到的行为冲突时，不改做法，把冲突记到 `conflicts`。
- **明显写错的可以改。** 只限声明里写死的东西：签名、参数个数、默认值、单位、枚举值。卡里写的和声明不一样，以声明为准写，并在 `corrections` 里记一笔。拿不准算不算这一类的，不改，记到 `conflicts`。
- **冲突和缺口分开记。** `conflicts` 记知识库和卡里做法的冲突、卡内自相矛盾的地方；`gaps` 只记想查而没查实的。

## 出处和路径怎么写

- `refs` 只给检查脚本核对原文用，不会给审的人看。`where` 写来源里的相对路径加符号名，不写任何本机路径（各来源从哪一级算起、依赖库怎么写坐标，见 `knowledge-sources.md`；本机的根目录用 `check_rules.py --roots` 看）；`quote` 是逐字原文，不超过 200 字，检查脚本照本机文件核对。
- `values` 里每一项的 `source` 会原样给审的人看，是它唯一看得到的出处。写到「哪类来源的哪个文件，加符号名或资源名」：
  - 鸿蒙 SDK：「鸿蒙 SDK 的 ets/component/text.d.ts，TextAttribute.textShadow」；HarmonyOS 专有能力：「鸿蒙 SDK 的 hms/ets/…，符号名」。
  - Android 平台资源：「Android SDK 平台资源 data/res/values/attrs.xml，资源名（按应用的 compileSdk 取对应平台）」。
  - 安卓框架源码：写类和方法，如「android.widget.TextView#setShadowLayer」。
  - 依赖库：坐标加包内路径加资源名，如「androidx.appcompat:appcompat 包内 res/values/values.xml，资源名（按应用依赖的版本）」。
  - 官方文档：文件名加小节名。
  - 出自卡的：「卡里修好并验证过」，`support` 标卡的结论。
- 除了 `refs`，其他各栏都会给审的人看或用于召回，里面不能出现本机的路径、盘符、用户目录和行号；`refs` 里也不能有本机路径。

## 输出

每张卡写一个文件 `store\candidates\<卡号>.json`（分支根目录下；UTF-8，不带 BOM，用 Write 工具写）：

```json
{
  "case": "case-…",
  "rules": [
    {
      "title": "触发在前、做法在后的一句话，不超过 60 字",
      "product": "规格 | 计划与派工 | 代码 | 资源",
      "triggers": [
        {"read": "这个子代理读过的东西里看得到的写法；没有就写空字符串",
         "wrong": "它交回的产物里写错的样子：出现了什么，或者少了什么；没有就写空字符串"}
      ],
      "scope": "适用范围，一句话",
      "exceptions": [{"text": "卡里写明的不适用情形", "support": ["case-…#recommendation:2"]}],
      "how": [{"text": "一步做法，带确切写法", "support": ["case-…#recommendation:2"]}],
      "values": [{"value": "确切的值或写法", "meaning": "它是什么", "source": "出处，写到文件加符号名，不带本机路径", "support": []}],
      "lookups": [{"what": "要针对这个应用查的是什么", "where": "去哪类来源的哪个文件里、按什么找", "how": "找到之后怎么读出值"}],
      "why": "一句话：不这样做会出什么错",
      "keys": {"read": ["读过的东西里会出现的词"], "product": ["产物里会出现的词"]},
      "probe": null,
      "unverified": ["没能核实的点（简短）"],
      "alternatives_unverified": ["知识库里查到、但卡里没验证过的替代写法（简短）"],
      "siblings_checked": "搜了什么词、另有几个接口带它；或者「无：」加原因",
      "refs": [{"what": "这条出处说明的是什么", "kind": "harmony-dts | android-sdk | android-lib | oh-docs",
                "where": "来源里的相对路径（依赖库写 group:artifact:version 加包内路径），加符号名或小节名", "quote": "逐字原文，不超过 200 字",
                "version": "SDK 或库的版本；看不出来写「未标明」"}]
    }
  ],
  "left_out": [{"text": "卡里没写成规矩的内容（简短）", "reason": "没有产物里看得到的触发 | 要上机或截图才能做 | 只对出事应用成立 | 针对经验库本身的建议 | 其他：…"}],
  "corrections": [{"was": "卡里原来怎么写", "now": "按声明改成什么", "ref": "依据的出处（简短）"}],
  "gaps": ["想查而没查实的（简短）"],
  "conflicts": ["知识库和卡里做法的冲突、卡内自相矛盾的地方（简短）"]
}
```

- `support` 写成「卡号#结论」，结论是 `diagnosis` 或 `recommendation:N`，只能引这张卡自己的、没有撤回的结论。
- `values` 里来自卡的值，`support` 标卡的结论；来自知识库的值，`support` 写空列表，并在 `refs` 里有对应出处。
- 每条规矩的正文（title、triggers、scope、exceptions、why、how 合计，不含 values、lookups 和 refs）不超过 800 字。
- `values` 每条规矩不超过 8 项，只留照做时用得上的。同族接口最多写 3 个最常用的，其余只在 `siblings_checked` 里写数量。
- 不写 `id`、`general`、`status`、`sources` 这几栏，后面的脚本会补。
- 没有内容的列表写空列表。一张卡一条规矩都写不出来时，`rules` 写空列表，原因写进 `left_out`。

## 自检

每写完一张卡就在分支根目录下跑：

```
py -3 skills\memory-rules\scripts\check_rules.py <卡号里 case- 后面的前 8 位>
```

脚本查格式和必填栏、长度、`support` 是否存在、`refs` 的 `where` 是不是相对路径、按本机根目录找到的文件（含文档副本）里能不能逐字找到 `quote`、各栏里有没有本机路径和行号、触发是否合乎产物的要求、`keys` 的个数、`probe` 的正则能不能编译、有没有出事应用的名字。改到没有硬规则违反为止。提示（不算硬规则）也看一眼：取值的出处写得不够具体、找不到对应的引文、取值超过 8 项、触发里有占位写法。

## 不许做的

- 只读这些：`skills\memory-rules\references\` 下的本任务书、`format.md`、`knowledge-sources.md` 和 `examples\`；检查脚本 `skills\memory-rules\scripts\check_rules.py`；给你的清单文件和清单里列的卡文件；上面三类知识库来源，其中文档只读 `work\ohdocs\zh-cn\application-dev\` 这份本地副本。其他文件和目录一律不打开，包括本仓库 `store\` 下的卡原件和快照、`memory\` 下已有的经验、`store\candidates\` 里别的卡的输出、`work\` 下清单、卡文件和文档副本以外的东西，以及任何具体应用的源码和迁移工程。
- 只往 `store\candidates\` 里写，一张卡一个文件。临时脚本放在本会话的临时目录。
- 不打开凭据文件（文件名或路径带 key、token、credential 的）。
- 不调用任何模型 API，不起子代理。不联网。
- 不改 SDK、Gradle 缓存、文档副本或任何已有文件；Python 脚本设 `sys.dont_write_bytecode = True`。

## 交回

不超过 20 行，不贴规矩正文：用的鸿蒙 SDK 版本、安卓平台版本、依赖库和版本、查了哪些文档；每张卡一行（写成几条规矩、各是哪种产物、没写成规矩的有几项、改正了几处、`conflicts` 几处）；`check_rules.py` 对你这批输出（带上这批卡号的前 8 位）的最后一行。
