# 归族任务书：给一组规矩起族名、补通用查法、归到主题下

## 这是什么

这是安卓转鸿蒙（ArkTS）迁移的经验库。库里的「规矩」一条只讲一个触发、一个做法，给「任务刚做完、在审」的 agent 用。规矩按「产物 → 主题 → 触发族」三级组织：审的 agent 顺着自己手里的东西（读过的文件、交回的产物）一级级找，到了触发族这一级，先看族的一行说明和通用查法，再看每条规矩的标题和触发，挑出对得上的去读正文。

脚本按触发里的词（`keys.read`）把同一产物下相近的规矩聚成了一组组提案，每组 1–20 条。你的工作是逐个提案：确认它们是一族，给族起名、写一行「agent 会看到什么」，有通用方法的补一条通用查法，把族归到一个主题下，排好规矩的顺序。

## 你要做的

给你的清单文件里每行是一个提案文件（`store\families\proposals\<提案号>.json`，路径相对分支根目录）。提案里每条规矩只有规矩号、`title`、`product`、`triggers`、`keys`。已有的主题清单在 `store\families\topics.json`（按产物目录分，每个主题目录对应 `{"name": 中文名, "line": 主题的一行}`；第一次建库时可能是空的）。增量归并和第一次建库的下一轮，提案里还附有同一产物下已有的族（`existing_families`）。

对每个提案写一个决定文件 `store\families\decisions\<提案号>.json`。提案与提案互不相干，一个一个做，写完一个、自检过了再做下一个。

1. **确认是一族。** 一族里的规矩，触发要有共同的部分：读到的是同一类写法，或者产物里写错成同一类样子。聚得不对的（明显不是一类）拆成两族，或者把不该在这里的规矩列进 `move_out` 并写明原因（下一轮会给它们另找族）。
2. **族名和族的一行。** 用 agent 看得到的东西来写，不用动作来写。
   - 族名：中文，简短，说的是一类写法或一类产物，例如「TextView 的文字阴影属性」「自绘 View 的画布单位」，不写「改正阴影」「注意单位」。
   - 族的一行（`line`）：agent 会看到什么——读过的东西里的哪类写法、交回的产物里的哪类写法，一句话。
   - 目录名（`dir`）：小写英文、数字和短横线，例如 `text-shadow`、`canvas-unit`。同一产物同一主题下不重名。
3. **通用查法（最多一条，可以没有）。** 这一族有一个比各条规矩更宽的通用方法时补一条，写成「看到哪一类写法 → 去哪里查、怎么读出值 → 写成目标端的显式写法」：
   - 族里只有一个具体情景的，或者通用部分只是流程上的要求（先读什么、记到哪里、怎么上报）的，不补。
   - 触发可以是一类写法，例如「源控件没有显式写某个外观属性」「源端引用了平台或库提供的值（`@android:…`、`?attr/…`）」「目标端这个值是手写的常数」。代码和资源类的规矩触发里至少有一个代码标识符；规格和派工类的 `wrong` 必写。
   - 做法写查法：去哪类来源的哪个文件、按什么找、怎么顺着引用一步步读出这个应用的实际值，最后写成目标端的显式写法。1–3 步。随应用而变的写进 `lookups`；查法里固定的部分（解析的先后顺序、默认值定义在哪个文件的哪个符号）只用族里规矩已经查实的：从它们的 `lookups`、`values`、`refs` 里归纳和照抄，不另去知识库查新的事实。族里规矩没有查实过的固定部分，写进这条通用查法的 `unverified`。
   - 可以附一个带条件的例子（「例：某主题下某控件查出来是某值」），例子必须出自卡或知识库，写明条件。不列各种情况的取值表，不把族里的具体规矩抄进来。
   - `support` 标最能代表这个方法的 1–3 条卡的结论，只能引族里规矩引过的卡。写通用查法时读族里规矩的原件 `store\rules\<规矩号>.json` 就够了；只有原件里看不清卡的结论说的是什么时，才去读它引到的卡文件 `work\cards\<卡号>.md`。
   - 照 `references\format.md` 的格式写，多加一栏 `"general": true`，`product` 和提案一样；不写 `id`、`sources`、`status`。正文（title、triggers、scope、exceptions、why、how 合计）不超过 600 字。
4. **归到主题下。** 主题按任务对象分（比如文本、图片和图形、布局与尺寸、窗口与系统栏、输入、列表、弹窗、资源、数据），不按动作分。优先用 `topics.json` 里已有的主题；没有合适的才新起一个，目录可以多级（用 `/` 分，一般 1–3 级），每级小写英文、数字和短横线，并给中文名；同一个目录的中文名前后要一致。每个主题下的直接子项尽量不超过 20 个。`topics.json` 不空时（增量归并）新起的主题还要在 `topic` 里写 `line`：agent 手里有什么东西时该进来看。第一次建库时（`topics.json` 是空的）你写的 `topic` 只当建议：所有族归完之后，另有一步「理主题」统一定主题树，可能改掉你的建议，所以不必花工夫斟酌主题的层级和名字。
5. **排好顺序。** `rules` 按 agent 最可能先碰到的排在前；同一种写法的不同情形挨着放。
6. **不改规矩正文。** 规矩的标题、触发、做法一个字都不动；这里只决定它们放在哪、怎么排。
7. **标出像是同一条的。** 族里有两条或几条规矩，从标题和触发看是同一个触发、同一个做法的（不是相近，也不是一条是另一条的特例），列进这个族的 `same`：`[{"rules": ["rule-…", "rule-…"], "reason": "一句话"}]`。这里只是标出来，不合并、不改它们；后面有人对着全文判断并不并。拿不准的不标。
8. 提案里附有已有的族（`existing_families`）时，规矩归进已有的族，就把族的 `topic.dir` 和 `dir` 写成和已有的那个族一样（`name`、`line` 照抄已有的，主题的中文名照 `topics.json`）。

## 拆一个超限的族

提案里带 `split_of` 的，是一个规矩超过 20 条的已有族（`split_reason` 写了几条），要把它拆成几个族。提案里附了原族的名字、一行和目录名（`family`）、它所在的主题（`topic`）、原族的通用查法（`generals`，规矩号和标题）、同一主题下别的族和子主题已经用掉的目录名（`sibling_dirs`）；`rules` 是原族的全部规矩。

- 按上面 1、2、5、7 的办法，把这些规矩分成几个族，每个族不超过 20 条；每个族的触发要有共同的部分，各有族名、一行和目录名。按 agent 看得到的写法分，不按条数平均切。
- 拆出来的族都留在原来的主题下：`topic` 照抄提案里的，脚本也会强制用原主题。目录名彼此不同，也不能用 `sibling_dirs` 里的名字；可以有一个族沿用原族的目录名。
- 通用查法：原族的通用查法还适用于某个新族的，在那个族的 `general` 里写它的规矩号（字符串，如 `"rule-…"`）沿用；需要改写的按第 3 条写一条新的；都不适用的写 `null`。没有被沿用的原通用查法落盘时会删掉。
- 实在不属于这几族的规矩照样可以列进 `move_out`。
- 输出和自检同下面：写 `store\families\decisions\<提案号>.json`，跑 `families.py apply --check --proposals <提案号>`（它还会查拆出来的目录名有没有和同主题下的撞）。交回时每个拆分提案写一行：拆成几族、各几条、通用查法怎么处理的。

## 输出

每个提案写一个文件 `store\families\decisions\<提案号>.json`（分支根目录下；UTF-8，不带 BOM，用 Write 工具写）：

```json
{
  "proposal": "fam-0001",
  "families": [
    {"name": "族名（中文）",
     "dir": "英文短横线目录名",
     "line": "agent 会看到什么（一句话）",
     "topic": {"dir": "主题目录，可多级，如 ui/text", "name": "主题中文名"},
     "rules": ["rule-…", "rule-…"],
     "general": null,
     "same": [{"rules": ["rule-…", "rule-…"], "reason": "从标题和触发看是同一个触发、同一个做法"}]}
  ],
  "move_out": [{"rule": "rule-…", "reason": "为什么不在这一族"}]
}
```

- 提案里的每条规矩恰好出现一次：在某个族的 `rules` 里，或在 `move_out` 里。
- `general` 是 `null`，或者一条完整的通用查法规矩（带 `"general": true`）；拆超限的族时还可以是原族通用查法的规矩号。
- `same` 没有就写空列表；每组至少两条，都要在这个族的 `rules` 里，一条规矩不出现在两组里。

## 自检

每写完一个提案就在分支根目录下跑：

```
py -3 skills\memory-rules\scripts\families.py apply --check --proposals <提案号>
```

它检查每条规矩是否恰好出现一次、族名和族的一行是否写了、目录名是否合法、主题的中文名是否一致、`same` 的每组是否合乎上面的要求，并把通用查法交给 `check_rules.py` 查。只检查，不落盘。改到没有报错为止。

## 不许做的

- 只读这些：`skills\memory-rules\references\` 下的本任务书、`format.md`、`knowledge-sources.md` 和 `examples\`；检查用的 `skills\memory-rules\scripts\check_rules.py`、`families.py`；给你的清单文件和清单里列的提案文件；`store\families\topics.json`；要补通用查法时，提案里规矩的原件 `store\rules\<规矩号>.json` 和它们引到的卡文件 `work\cards\<卡号>.md`。其他文件和目录一律不打开，包括三类知识库来源、本仓库 `store\` 下的卡原件和快照、`store\candidates\`、`store\merge\`、`memory\` 下已有的经验、别的提案的决定，以及任何具体应用的源码和迁移工程。
- 只往 `store\families\decisions\` 里写，一个提案一个文件。临时文件放在本会话的临时目录。
- 不打开凭据文件（文件名或路径带 key、token、credential 的）。
- 不调用任何模型 API，不起子代理。不联网。
- 不改 SDK、Gradle 缓存或任何已有文件；Python 脚本设 `sys.dont_write_bytecode = True`。

## 交回

不超过 20 行，不贴规矩正文：每个提案一行（分成几族、族名、归到哪个主题、补没补通用查法、挪走几条）；新起的主题；`families.py apply --check --proposals <这批的提案号>` 的最后一行。
