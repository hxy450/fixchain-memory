# 合并任务书：判断一组相近的候选规矩是不是同一条

## 这是什么

这是安卓转鸿蒙（ArkTS）迁移的经验库。一张「卡」是对一次迁移里某个错的调查记录；每张卡已经被提炼成若干条「候选规矩」，一条只讲一个触发、一个做法。规矩给「任务刚做完、在审」的 agent 用：它看得到那个子代理读过的东西和交回的产物，拿着规矩判断情景在不在、写得对不对。

不同的卡常常讲同一件事。脚本按 `keys` 和标题把相近的候选连成了组，每组 2–10 条，来自不同的卡（增量归并时组里还可能有库里已有的规矩，标着 `"existing": true`）。你的工作是逐组判断哪些候选是同一条规矩：相同的并成一条，不同的各自保留。

规矩的格式和每一栏的写法见 `references\format.md`（同目录）；出处怎么写见 `references\knowledge-sources.md`。

## 你要做的

给你的清单文件里每行是一个组文件（`store\merge\groups\<组号>.json`，路径相对分支根目录）。组文件里有：组号、`product`、组内两两的相似度、每条候选的临时号（「卡号#序号」，已有规矩是规矩号）和全文。组号以 `same-` 开头的组是另一个来源：成员全是库里已有的规矩，是归族时从标题和触发看像同一条而标出来的（组文件里带着族名和标出它的理由）；那个理由只是提示，照下面同样的标准对着全文判断，不同的照样各自保留。对每个组写一个决定文件 `store\merge\decisions\<组号>.json`。组与组互不相干，一组一组做，写完一组、自检过了再做下一组。

## 怎么判断

1. **同一个触发、同一个做法才算相同。** 触发相同，是审的人看的是同一处写法或同一个缺项（读到的同一类源端写法、产物里写错成同一个样子）；做法相同，是照做写出来的是同一种写法。两条都满足，才并成一条。
2. **相关不等于相同。** 话题相近、用到同一个接口但改的是不同的属性、同一个控件的两种不同情景，都是不同的规矩，各自保留。
3. **一条的触发是另一条的特例时不合并。** 不借合并扩大适用范围：并出来的规矩，`scope` 和触发只能是各成员本来就成立的范围，不能比它们合起来更宽。
4. **说法冲突的也并成一条，标出来。** 触发相同，但两张卡给的做法或取值互相矛盾（照一条做就违反另一条）时，并成一条，`status` 写 `disputed`，在 `unverified` 里写明两种说法各出自哪张卡（写卡号，不写应用名）。触发相同、做法不同但不矛盾（各管一件事）的，各自保留。
5. 拿不准是不是同一条的，各自保留，在理由里写明拿不准的地方。

## 合并时怎么写

并出来的规矩照 `format.md` 的格式写（不写 `id`、`general`、`sources`，这几栏脚本会补；可以写 `status`，没有冲突写 `active`）。`product` 和组的一样。

- **来源都留。** 每一步做法、每条例外的 `support` 把支撑它的各张卡的结论都列上；每个成员的做法都要有着落。
- **取值取并集。** 各成员的 `values` 合起来，相同的值只留一条；`refs` 跟着取值一起合并，每个取值的出处都要在（`where` 照成员原样抄，是来源里的相对路径，不改成本机路径）。并完超过 8 项的，只留照做时用得上的，同族接口最多留 3 个最常用的，其余只在 `siblings_checked` 里写数量。
- **措辞取最确切的。** `title`、`how` 选成员里写得最确切的那种说法（带确切的接口调用和参数对应），不把几种说法拼成一长句。
- **触发。** 同一件事在不同写法下（View 的 XML、Java 代码、Compose）各有一个触发的，都保留；完全相同的只留一个。
- **其余各栏。** `exceptions`、`lookups`、`unverified`、`alternatives_unverified` 合并去重；`keys` 两栏合并去重，各留 3–12 个；`probe` 选对所有成员都成立的那个，没有就写 `null`。
- 已有规矩（`existing`）和新候选并成一条时，以已有规矩为底，把新候选的来源、取值、触发补进去；脚本会沿用已有规矩的规矩号。几条已有规矩并成一条时（`same-` 组），以组文件里排在前面的那条为底，脚本沿用它的规矩号、删掉其余几条。
- 不改卡里验证过的结论，不补卡里没有的例外和限定，不加新的做法。

## 输出

每个组写一个文件 `store\merge\decisions\<组号>.json`（分支根目录下；UTF-8，不带 BOM，用 Write 工具写）：

```json
{
  "group": "group-0001",
  "merged": [
    {"members": ["case-…#1", "case-…#2"],
     "reason": "一句理由：为什么是同一个触发、同一个做法",
     "rule": {"title": "…", "product": "…", "triggers": [ … ], "…": "其余各栏照 format.md", "status": "active"}}
  ],
  "kept": [
    {"member": "case-…#1", "reason": "一句理由：它和组里别的哪里不同"}
  ]
}
```

- 组里的每条候选恰好出现一次：要么在某个 `merged` 的 `members` 里，要么在 `kept` 里。
- `merged` 每项至少两条，都要写理由；`kept` 每项也写一句理由。
- 一组里可以有几个 `merged`（组里有两对各自相同的），也可以一个都没有。

## 自检

每写完一组就在分支根目录下跑：

```
py -3 skills\memory-rules\scripts\apply_merge.py --check --groups <组号>
```

它检查每条候选是否恰好被处理一次、`merged` 是否有理由和至少两条、`product` 和 `status` 是否合法，并把合并出的规矩交给 `check_rules.py` 查（格式、长度、`support`、引文、可移植写法、触发、`keys`、`probe`、出事应用的名字）。只写临时目录，不落盘。改到最后一行是「硬规则违反合计 0 处」为止。

## 不许做的

- 只读这些：`skills\memory-rules\references\` 下的本任务书、`format.md`、`knowledge-sources.md` 和 `examples\`；检查用的 `skills\memory-rules\scripts\check_rules.py`、`apply_merge.py`；给你的清单文件和清单里列的组文件；组里各成员引到的卡的卡文件 `work\cards\<卡号>.md`（核对 `support` 时用）；三类知识库来源（要重新核对引文时用；文档只读 `work\ohdocs\zh-cn\application-dev\` 这份本地副本）。其他文件和目录一律不打开，包括本仓库 `store\` 下的卡原件和快照、`store\rules\`、`store\candidates\`、`memory\` 下已有的经验、别的组的决定，以及任何具体应用的源码和迁移工程。
- 只往 `store\merge\decisions\` 里写，一个组一个文件。临时文件放在本会话的临时目录。
- 不打开凭据文件（文件名或路径带 key、token、credential 的）。
- 不调用任何模型 API，不起子代理。不联网。
- 不改 SDK、Gradle 缓存或任何已有文件；Python 脚本设 `sys.dont_write_bytecode = True`。

## 交回

不超过 20 行，不贴规矩正文：每组一行（并成几条、保留几条、标 disputed 的几条）；拿不准的地方；`apply_merge.py --check --groups <这批的组号>` 的最后一行。
