# 复核任务书：对着卡把候选规矩再核一遍

## 这是什么

这是安卓转鸿蒙（ArkTS）迁移的经验库。一张「卡」是对一次迁移里某个错的调查记录；每张卡已经由别的子代理提炼成若干条「候选规矩」（`store\candidates\<卡号>.json`），一条只讲一个触发、一个做法，带查好的知识。规矩给「任务刚做完、在审」的 agent 用，它会照着规矩去改别的应用的产物，所以规矩里多出一句卡里没有的话、适用范围写宽一点，都会让它在不该改的地方改错。

抽查过的情况：查好的知识（签名、取值、引文）是准的，不用你重查。毛病都出在规矩比卡多说了：一条里捆了两件事，范围写宽了，添了卡里没有的写法，出处标高了。你的工作是逐张卡对着卡文件把候选规矩核一遍：有下面这几类毛病的改掉，没有的不动。你不是来重写的。

规矩的格式和每一栏的写法见 `format.md`（同目录）。先把它和本任务书读完再开始。

## 你要做的

给你的清单文件里每行是一张卡的卡文件（`work\cards\<卡号>.md`）。对每张卡：读卡文件，读它的候选文件 `store\candidates\<卡号>.json`，逐条规矩核对下面六件事，该改的直接改候选文件，然后写一份复核记录。卡与卡互不相干，一张一张做；改完一张、自检过了、记录写好，再做下一张。

## 逐条核对的六件事

1. **做法和例外都出自卡的结论。** `how` 的每一步、`exceptions` 的每一条，看它标的 `support` 指到的那条结论（诊断或建议）说的是不是这件事。
   - 卡的结论里没有的另一个动作、另一个接口或方法、另一组取值、另一条例外，删掉——哪怕它是对的、是常识。卡没有点名的方法，即使和卡点了名的方法在同一个类里，也算另一个接口。知识库里查到的替代写法挪到 `alternatives_unverified`。
   - 不算添加的：卡点了名的那个接口（方法、属性），规矩写出它的确切调用、参数名、单位，以及源端各值对应哪个参数（在 `values` 和 `refs` 里有出处）。这是提炼该做的，不要删。
   - 调查过程里的中间记录、猜测、被撤回的说法不能当 `support`。
   - 卡里验证过的写法和名字不许换成别的（比如把卡里的回调名换成另一个接口的回调名）。只有声明里写死的事实（签名、参数个数、默认值、单位、枚举值）和卡不一致时才许改，改了必须记进 `corrections`；别的不一致恢复卡里的原话，记进 `conflicts`。

2. **一条规矩一个做法——该拆的要拆。** 用两问来判断：
   - 把其中一件事整个拿掉，剩下那件事的触发和做法还完整吗？
   - 别的应用里会不会只碰到其中一件？

   两问都是「是」，就是捆了，拆成两条，即使它们出自卡里的同一条建议。拆出来的每一条各带各的 `title`、`triggers`、`how`、`support`，以及和它相关的 `values`、`refs`、`lookups`、`keys`、`probe`。
   - 不拆的：同一处改动的先后步骤；一个做法连带必须做的配套修改（少了它做法就不成立）；同一件事在不同写法下的几个触发。
   - 这一件不适用「拿不准就不动」：你自己已经看出是两处独立的改动、触发也不同的，就拆。
   - 拆了之后这张卡超过 8 条的，留更要紧的那件，另一件记进 `left_out` 并写明原因。

3. **范围不超出卡里出错并修好的情形。** `title`、`scope`、触发、`lookups` 说的适用范围，以卡里实际出错、修好的那种情形为准：出错的是哪种控件、哪个属性、哪种写法，规矩就只说这一种。卡在描述背景时顺带提到的别的控件、别的属性不算验证过，要从标题、触发和 `keys` 里拿掉。卡的建议原话说得更宽的，也以出错并修好的情形为准。卡里的情形带条件（背景不透明、某一族主题、某个属性没写），条件要在触发或 `scope` 里。

4. **触发是当时字面上看得见的。**
   - `read` 只写子代理做这个任务时会读到的文件里字面上有的东西（源码、资源、规格文字里的写法）。写成概念的（「源端依赖平台行为」这类）、写的是事后调查才知道的东西的，改成字面的写法；改不出来就把这个触发删掉。一条规矩至少留一个触发；一个都留不下的，整条挪进 `left_out`，写明原因。
   - `wrong` 只写产物里字面上看得到的写法或缺项。后面带着的运行时现象、设备上的症状，挪到 `why` 里。挪走之后剩下的要仍是一句完整的话；代码和资源类的规矩还要带着代码标识符。剩下的不成句时，照卡里出事的产物当时是怎么写的，把它写成看得见的写法；写不出来就保留原样，记进 `unsure`。

5. **「卡里修好并验证过」只标在卡里有的东西上。** `values` 里 `source` 写「卡里修好并验证过」的，可以是两种：卡里的修法本身（建议或诊断里写的、修复时落到产物里的写法和取值），和卡里写明在设备上观察到的行为。卡里的做法默认就是修好并验证过的，不要求卡里另有「已验证」的字样。
   - 不算的：卡里没有写的结果描述（提炼时添的「与源端一致」「不再遮挡」这类话）、期望的验收路径、猜测、没有落地的设想、提炼时自己的推断或换算。这些从 `values` 里拿掉；确实有用的，写进 `why` 或 `unverified`。
   - 出处是鸿蒙 SDK、安卓 SDK、依赖库、文档的取值不用重查，也不要为了补引文去翻知识库。只在一种情况下动：`meaning` 里有半句话明显不是引文说的、也不是卡的结论，把那半句删掉，或挪进 `unverified`。
   - 自己算出来的值、自己推断的行为不算已核实，不放在 `values` 里。

6. **不带出事应用自己的东西。** `how`、`values`、触发、`keys` 里出事应用自己起的名字（变量、函数、类、资源名、控件 id、界面文案）和它那个界面特有的取值，换成一般的说法（「按源端的取值」「源端对应的那个颜色」）；随应用而变的值写进 `lookups`，可以附「例：某条件下是某值」。
   - `left_out` 里记成「只对出事应用成立」的内容，如果又出现在某条规矩的做法里：先判断它到底是不是只对出事应用成立。是，就从做法里拿掉；不是，就改 `left_out` 那一项。

## 改完之后顺手做的

- **`keys` 跟着改。** 规矩里删掉的词（控件名、接口名）从 `keys` 两栏里一并删掉；出事应用自己的词删掉。每栏仍要 3–12 个。
- **记录放对地方。** 想查没查到的记在 `gaps`；和知识库说法不一致、没有改的记在 `conflicts`；规矩里没能核实的点记在该条的 `unverified`。放错了的挪过去。

## 改的分寸

- 除了第 2 件事，拿不准算不算毛病的不动，写进复核记录的 `unsure`。
- 不为了改而改：措辞、顺序、风格不动；没有毛病的规矩一个字都不动。
- 不新增规矩（拆分除外），不补新的做法，不查新的知识。
- 改过的规矩仍要守 `format.md` 的各项要求（长度、`support`、可移植的出处、触发里的标识符、`keys`）。

## 输出

1. 直接改 `store\candidates\<卡号>.json`（只改清单里的卡；UTF-8，不带 BOM，用 Edit 或 Write 工具）。
2. 每张卡写一份复核记录 `store\reviews\<卡号>.json`（没有改动也要写）：

```json
{
  "case": "case-…",
  "rules_before": 4,
  "rules_after": 5,
  "changes": [
    {"rule": 2, "check": 1, "what": "一句话：改了什么（删了哪一步里的哪句、把什么挪到了哪里）"}
  ],
  "splits": [{"from": 3, "into": [3, 5], "why": "一句话：哪两件事"}],
  "moved_to_left_out": [{"rule": 4, "why": "一句话"}],
  "unsure": ["拿不准、没有动的地方，一项一句"]
}
```

`rule` 是改之前这条规矩在文件里的序号（从 1 起），卡一级的改动（`left_out`、`gaps`、`conflicts`）写 0；`check` 是上面六件事的编号（顺手做的两项记 0）。拆出来的新规矩接在文件末尾，`into` 写原来的序号和新规矩的序号。没有的栏写空列表。

## 自检

每改完一张卡，在分支根目录下跑：

```
py -3 skills\memory-rules\scripts\check_rules.py <卡号前 8 位>
```

改到最后一行是「硬规则违反合计 0 处」为止，再做下一张。

## 不许做的

- 只读这些：`skills\memory-rules\references\` 下的本任务书、`format.md` 和 `examples\`；检查用的 `skills\memory-rules\scripts\check_rules.py`；给你的清单文件；清单里的卡文件和这些卡的候选文件。其他文件和目录一律不打开，包括三类知识库来源、本仓库 `store\` 下的卡原件和快照、别的卡的候选和复核记录、`memory\` 下已有的经验，以及任何具体应用的源码和迁移工程。
- 只改清单里的卡的候选文件，只往 `store\reviews\` 里写这些卡的复核记录。临时文件放在本会话的临时目录。
- 不打开凭据文件（文件名或路径带 key、token、credential 的）。
- 不调用任何模型 API，不起子代理。不联网。不做 git 提交。
- 不改任何别的已有文件；Python 脚本设 `sys.dont_write_bytecode = True`。

## 交回

不超过 20 行，不贴规矩正文：每张卡一行（规矩从几条到几条；六件事各改了几处，没改的写 0；拆了几条）；`unsure` 里的事合起来几项、主要是哪几类；整批跑 `check_rules.py <这批的卡号前 8 位…>` 的最后一行。
