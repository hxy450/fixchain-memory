# 蓝牙开关以终态回读为准：状态回调后读 getState，过渡态与迟到回调不写成关闭；门控放在决策点实时读取

ID：`lesson-29922f57cc365ff3d638` · 版本：1

[本主题](index.md)

## 何时使用

系统能力接入与状态接线阶段，决定蓝牙开关/可用状态以什么为真值、在何处门控、初始加载按什么顺序赋值时

## 适用情境

源端在点击与广播处理时实时读 BluetoothAdapter，只在 ACTION_STATE_CHANGED 的 STATE_ON/STATE_OFF 终态刷新 UI；目标用 access.on('stateChange') 与 access.getState()，经 ViewModel 与页面 @Local 副本驱动开关、设备入口和二级连接页。

## 原因

stateChange 会带出 TURNING_ON/OFF、BLE 等过渡态，回调到达顺序也不保证；把“回调参数 === STATE_ON”直接写成开关值，过渡态与迟到回调会把已开启的蓝牙显示为关闭并清空设备。页面 @Local 快照做入口门控、初始加载把系统状态放在多个无关 await 之后，也会误拦入口、首帧显示错误。来源中修复波把原本“变化时回读 isEnabled()”的实现改成信任回调参数，后续重写又原样保留，并在新增的连接页加了源端没有的开关拦截；真机上系统蓝牙已开，应用仍显示关闭、设备页进不去。未核实未授权时 getState 的表现，权限顺序本身未作为独立原因。

## 做法

1. 收到 stateChange 即以 access.getState() 回读；STATE_ON（业务需要时含 STATE_BLE_ON）为开，只有回读与回调都为 STATE_OFF 才报关闭，TURNING_* 与迟到回调不直接写成 false。
2. 重写已有状态处理前，对照被替换的旧逻辑与源端广播分支；旧实现已是“变化时回读”、源端只处理终态时，不改成信任回调参数。
3. 源端在点击瞬间实时读取的门控，放到 ViewModel/Service 的决策点：先完成权限申请，再实时回读；不用页面快照拦截导航，也不在目标页新增源端没有的开关拦截。
4. 初始水合时先同步读取可立即获得的系统状态并通知 UI，再等待偏好、通知授权等异步读取。
