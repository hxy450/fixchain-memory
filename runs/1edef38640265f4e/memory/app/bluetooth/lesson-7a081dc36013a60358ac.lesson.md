# 源端在应用内直接开关蓝牙时，先查 @ohos.bluetooth.access 的开关接口与权限再定方案，不把现有的设置跳转当作平台限制

ID：`lesson-7a081dc36013a60358ac` · 版本：1

[本主题](index.md)

## 何时使用

规格提取、增量规格与服务实现阶段，为源端在应用内直接开关的蓝牙确定目标实现与验收项时；以及真机安装因权限被拒而调整权限清单时

## 适用情境

源端点击开关后在应用内调用 BluetoothAdapter.enable()/disable()；决策只允许“平台不允许应用直接完成的开关”改走系统授权弹窗或设置跳转；现有目标代码已把 enable/disable 写成打开系统蓝牙设置，或权限清单里有从第三方文档抄来的系统级权限。

## 例外与边界

- 目标最低 API 与设备上确无可用的应用内开关接口，且决策已批准设置跳转

## 原因

“走系统设置”只在平台确实不允许时成立；把现有实现当作平台限制的证据，会让规格和重写都沿用降级。来源中生成期按第三方 SDK 文档加入系统级 MANAGE_BLUETOOTH，真机安装被拒后删权限并把开关改成固定跳转设置；而同一 SDK 的 access 声明早已返回给另一个 worker：enableBluetooth/disableBluetooth 与 API 20 的 enableBluetoothAsync/disableBluetoothAsync 都只需 ACCESS_BLUETOOTH。增量规格作者读到源端直接开关、“以源端为真值”和“平台不允许时才跳设置”两条决策，仍把现状写进规格与验收项，实现者据此重写服务；用户问有没有别的方式后，才改为 API 20+ 应用内系统确认、低版本设置页兜底。

## 做法

1. 定方案前查 @ohos.bluetooth.access 声明中 enableBluetooth/enableBluetoothAsync/disableBluetoothAsync 的 @permission 与 @since，确认不可行才写“走系统设置”。
2. 契约写明版本分支：API 20+ 用 enableBluetoothAsync/disableBluetoothAsync（ACCESS_BLUETOOTH，系统确认框，处理用户拒绝或未响应的错误码），低版本用同步接口或设置页兜底；操作后以 stateChange/getState 回读真实状态。
3. 权限清单按实际调用 API 的 @permission 声明；真机安装因系统级权限被拒时，只移除未被调用 API 需要的权限，不借此把应用内能力降级为跳转设置。
4. 实现时规格写的是跳转设置而源码是应用内直接开关，重写服务前核对 SDK 是否有可用接口；有可行路径就回报规格疑点，不照旧保留跳转。
