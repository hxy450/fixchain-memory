# 源端 Long 承载的服务器 id 在 ArkTS 里用 bigint，响应解析、请求序列化与持久化往返都保住 64 位精度

ID：`lesson-c066489fcf35ab37378c` · 版本：1

[本主题](index.md)

## 何时使用

数据模型与网络层实现阶段，把 Kotlin Long 字段和接口参数映射成 ArkTS 类型、决定 JSON 解析与序列化方式时；规格提取阶段写服务层 ArkTS 目标签名时

## 适用情境

源端 bean 或接口用 Kotlin Long（Flutter 侧 Dart int）承载服务器生成的用户 id、hash、userId，后端按 JSON 数字返回，取值可达 19 位；目标端 ArkTS 的 number 是双精度，JSON.parse 遇到超过 2^53 的整数直接舍入。

## 原因

Long 与 Dart int 都是 64 位，number 只能精确表示到 2^53。映射成 number 后，裸 JSON.parse 在解析那一刻就已舍入，之后字段改成什么类型都救不回来；持久化时 JSON.stringify 还会再丢一次。改成 string 又会与后端和 Flutter 侧的整数语义不一致，来源中用户否决了 string 方案。来源中实现者读到了源端 Long 声明，派工也要求按源码确认类型，仍一律写成 number，并对所有响应裸 JSON.parse；规格作者读到 userId: Long，在服务层签名里写成 number，规格模板的示例签名也用 number 表示 id。

## 做法

1. 逐个列出源端 bean 和接口里的 Long 字段：服务器生成的 id、hash、userId 用 bigint（默认值 0n）；只有确认取值不超过 2^53（如 13 位毫秒时间戳、时长）时才用 number，并在注释写明理由。
2. 响应里有 64 位整数字段时不用裸 JSON.parse：解析前给这些数字加引号再用 reviver 转 BigInt，或换支持 bigint 的解析器；请求序列化配 bigint 转字符串的 replacer。最小检查：解析 {"id":6970321983963689496} 后 id.toString() 原样返回 19 位。
3. 模型有 bigint 字段时，每条 JSON.stringify/JSON.parse 往返（用户信息持久化、DAO、偏好里存的 JSON）都用成对的 replacer/reviver，存完读回比较 id。
4. 用“正则预处理 + reviver”这类全局方案前，把转换范围限定到已知的 64 位字段名，并确认后端接受字符串形式的数字；确认不了就按字段处理，避免误伤 16 位以上的字符串或其他整数字段。
5. 规格写服务层目标签名时，源端 Long 参数写 bigint 或注明“64 位，禁用 number”，不照模板示例写 number。
