# 用应用内计时加长时任务替代后台 Worker 时，恢复入口共用逐步扣减函数，前台专属状态在每个退出点复位，通知正文按源端逐字段核对

ID：`lesson-35a684862ee500f08912` · 版本：1

[本主题](index.md)

## 何时使用

实现或重写后台计时交接、持久化恢复、紧凑模式与进度通知时

## 适用情境

源端由后台 Worker 跨步骤推进计时并发进度通知（正文含重量与步骤时长，具名高重要度渠道），回到前台取 Worker 已推进到的步骤；目标端改为应用内计时加长时任务，用应用内紧凑模式代替系统画中画、窗口常亮代替 WakeLock，恢复与退出清理都要自己写。

## 原因

Worker 天然跨步骤推进；应用内实现若为持久化恢复另写一个只把停机时长加到当前步的分支，跨步时间就丢了。常亮、紧凑模式是前台专属状态，漏掉任一退出点就会残留。来源中修复轮 worker 写前读到了源端“回前台按 Worker 步骤恢复”和规格“停止即清常亮”，仍写出三处偏差：恢复只前进一步、回前台不退出紧凑模式、后台交接与通知停止不清常亮；另一个 worker 的通知正文漏了步骤时长，自己定义的时长字段没有消费。

## 做法

1. 所有恢复入口（后台 tick、持久化恢复）共用一个按有序步骤扣减经过时间的函数：遇到需要手动确认的步骤停下，越过末步进入完成态。
2. 列出前台专属状态（keep-screen-on、紧凑模式）的进入点和全部退出点：回前台、后台交接、后台完成、通知停止、页面销毁，逐个显式复位；grep 每处置为 true 的位置，核对对应的 false。
3. 通知按源端 createContentText/createChannel 逐字段核对；快照里自定义的字段要在渲染处消费，不带着未用字段交付。

## 可选检查

- 对恢复算法有疑问时，用跨两个步骤的停机时长手算一次恢复结果，与实现对照。
