# process/build

编译修复循环与构建结果判定：只改报错定位处、不以删功能换取通过、整文件重写时保留未报错写法，读全错误输出，失败构建不以警告或部分通过放行，最终结论只引用晚于最后改动的构建

## 本级经验

- [编译修复只改报错定位的行与符号，不以删掉功能换取通过；必须整文件重写时逐段对照上一版，未报错的写法原样保留](lesson-29744eb694376e8acaca.lesson.md)
  - 时机：编译修复阶段，为修某条编译错误决定局部修改还是整文件重写时
  - 情境：修复循环用 here-string 或 Write 整文件重写页面来处理导入导出、@Entry 等报错，文件里还有未被报错的组件用法（页签 builder、状态绑定、导入等）。或报错只涉及某个导入或符号，修复者考虑把相关功能块（如自绘趋势图）整体换成占位以通过编译。也包括报错来自调用了 SDK 不存在的参数字段（如在 AlertDialog 参数里写自定义内容 builder），修复者准备删掉该字段连同其中承载的控件。
- [编译检查按完整构建结果判定：读全 ERROR 列表与 COMPILE RESULT，构建失败只记 FAIL，不以“仅警告”“部分通过”放行](lesson-7426a20525e52e34c2e7.lesson.md)
  - 时机：验证阶段执行编译检查并决定是否标记阶段完成时；编译修复循环查看构建输出时；构建通过后又改动了源码、准备宣称“最终构建通过”时
  - 情境：hvigor 构建输出重定向到文件，WARN 常排在 ERROR 之前；修复循环只截取错误文件前若干行；验收规范规定编译通过才 PASS、否则 FAIL 并继续修复循环。或编排者在构建报成功后又追加源码改动，派出的复核构建尚未返回结果。
