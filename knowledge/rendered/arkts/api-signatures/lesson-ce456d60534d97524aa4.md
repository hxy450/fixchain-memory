# 源端单调计时（System.nanoTime、SystemClock.elapsedRealtime）映射到 systemDateTime.getUptime，并按是否计入深睡眠选 TimeType：不写未经 SDK 核实的 performance.now，也不退回会随校时跳变的 Date.now

## 何时使用

规格提取阶段为 System.nanoTime、SystemClock.elapsedRealtime 等源端系统计时 API 选目标 API 或写平台差异时；实现或编译修复阶段，时钟映射在当前 SDK 中不存在、需要换时钟源时

## 适用情境

源端帧动画或计时用 System.nanoTime（CLOCK_MONOTONIC）求帧间隔与进度；目标 ArkTS 把时钟封装在单点函数里，规格映射写了 Web API（performance.now），构建报找不到符号或 Kit 无导出。也包括后台计时用 elapsedRealtime（计入深睡眠）记录起点与偏移，规格准备映射为墙钟，并写“平台未开放跨休眠单调时钟”。

## 例外与边界

- 只管源端取单调时钟的调用；源端用 System.currentTimeMillis 取墙钟时间（显示日期时间、存盘时间戳、跨重启比较）的地方，目标端继续用 Date.now 或 systemDateTime.getTime，不改成 getUptime——开机时长重启后从零算起，不能当日期用。
- 帧间隔已经取自 displaySync 帧回调 IntervalInfo 的 timestamp/targetTimestamp 时，它本身是系统启动以来单调递增的纳秒时间，不需要再换成 getUptime。

## 原因

来源工程的 SDK 中没有可导入的 performance，按记忆写的 Web API 把时钟选择推到了编译门；编译门凭印象把 systemDateTime 判为墙钟，换成 Date.now 后单调语义丢失，系统校时会让帧间隔回拨或跳变。systemDateTime.getUptime 自 API 10 提供不受校时影响的开机时长，并以 TimeType 区分是否计入深睡眠。

## 做法

1. 规格映射计时 API 时写清所需语义（单调、是否计入深睡眠、精度），并以项目 SDK 的 d.ts 作为目标 API 存在的依据，记下 @since 并对照 compatibleSdkVersion。System.nanoTime 对应 systemDateTime.getUptime(systemDateTime.TimeType.ACTIVE, true)（@kit.BasicServicesKit，纳秒），再换算毫秒；计入深睡眠的 SystemClock.elapsedRealtime 对应 getUptime(systemDateTime.TimeType.STARTUP)。
2. 编译门遇到时钟 API 不存在时，按原调用注释与规格写明的语义，在本地 ets/api 与 kits 的 d.ts 中检索候选（getUptime、TimeType、monotonic），读完声明再排除；只剩语义不同的替代时不在门内落地，作为决策缺口回报。

- 〔原因 / 做法第 1 步〕systemDateTime.getUptime 自 API 10 起提供；isNanoseconds 为 true 时返回纳秒，为 false 或不传时返回毫秒（默认 false）
- 〔原因 / 做法第 1 步〕systemDateTime.TimeType.STARTUP 是系统启动以来的时长、包括深度睡眠时间；TimeType.ACTIVE 不包括深度睡眠时间
- 〔适用情境 / 做法第 1 步〕安卓 System.nanoTime 只用于量经过的时间、与墙钟无关，它和 uptimeMillis 同属深度睡眠时停走的单调时钟
- 〔适用情境 / 做法第 1 步〕安卓 SystemClock.elapsedRealtime 返回开机以来的毫秒数，包括睡眠时间，是单调时钟
- 〔原因〕systemDateTime.getTime 返回自 Unix 纪元起的时间戳（isNanoseconds 为 true 时为纳秒，否则毫秒），属于系统时间，不是开机时长
