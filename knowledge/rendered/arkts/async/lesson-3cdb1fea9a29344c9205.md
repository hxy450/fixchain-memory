# 源端后台线程或回调里写的字段，调用方发起后又同步写同一字段时，按实际生效顺序推导结果；改成同步调用要把调用方的写挪到调用之前

## 何时使用

规格提取阶段把源端 Thread、Handler.post、异步回调里写入的状态翻译成目标契约与验收时；实现阶段把源端后台加载改成同步调用，或把源端发起函数内同步执行的回调改成异步完成后才执行（如启动改为 Promise 链）时

## 适用情境

源端方法启动后台线程（new Thread、Handler.post、AsyncTask、异步回调），成功后在线程里写某个字段；调用方在发起它之后紧接着在主线程同步写同一字段（如先发起加载、再把该字段清零）。目标把这段后台工作改成事件循环内的同步执行，或规格按代码书写顺序推导可观察结果。也包括反方向：源端发起函数内同步执行的回调先写字段（如启动时“计数为 0 才按偏好初始化”），调用方在发起返回后再写同一字段（如递减剩余次数）；目标把发起改成 Promise 链，回调要等异步完成才执行。 也包括 JS/TS 源端未 await 的 async 赋值与随后同步执行的初始化并存：如 i18n 初始化时设备语言的异步分支尚未返回，init 读到空值、由检测插件（navigator.language）裁决；规格可能把这条落败分支当作“文档化意图”写进契约。

## 原因

后台线程里的写入落在调用方后续同步语句之后，源端最终值来自后台写；按书写顺序推导会得到相反的最终值。目标把后台工作改成同步调用后，调用方的后写反而覆盖了加载结果；以“单线程天然消除竞争”为由照书写顺序实现，返回、重试、撤销这类可重复操作的连续结果就和源端不同。反方向同理：源端同步回调先写、调用方后写，目标回调延后到异步完成，回调里的写会覆盖调用方已做的修改（如把已递减的有限次数补满）。 未 await 的 async 赋值同样落在后续同步语句之后：初始化当下读到的是赋值前的值，真正生效的是同步路径，按书写顺序取异步分支的结果就选错了分支。

## 做法

1. 规格提取时，凡源端在 Thread、Handler.post 或异步回调里写的字段，查调用方发起后是否还同步写同一字段；按运行时生效顺序（后台写落在调用方后续语句之后）推导可观察结果，并在契约里列出这些字段与最终值。
2. 把后台工作映射为同步调用时，把调用方在发起之后对同一字段的写挪到同步调用之前，保持源端最终值；源端结果随线程调度而不确定时，在报告里写明并按实测的主要结果取一种。
3. 把源端同步执行的回调映射为异步完成后才执行时，把回调里依赖先后顺序的初始化挪到发起端同步执行，用显式参数区分首次发起与重复发起（如续录、重启段），不依赖回调晚于调用方写入的时序。
4. 返回、撤销、重试这类可重复操作的验收连续写第 1、2、3 次的结果，并覆盖不同起点；有后台写参与时以设备实测序列定条目。
5. 源端是未 await 的 async 赋值与同步初始化并存时，按执行时序写出初始化那一刻实际取到的值；与“文档化意图”或派工描述冲突时，把两种结果及其用户可见后果写成待决项交裁决，不在验收判据里写死有争议的分支；有源端实机基线时用它核对。
