# Kit API 的 catch 值按 BusinessError 取 message 与 code，code 先 Number() 归一再比较错误码

## 何时使用

规格提取与服务实现阶段，迁移源端按异常类型分类、以 getMessage() 记录详情的 catch 分支时；按 SDK @throws 错误码为 Kit 调用编写异常分支判别时

## 适用情境

目标 catch 到的是网络、文件、数据库、定位等 Kit API 抛出或拒绝的 BusinessError（运行时形态因接口而异：@ohos.net.http 拒绝的是带数值 code 与 message 的普通对象，不是 Error 实例；经 napi_throw_error 抛出的，如 geoLocationManager 的同步出错路径，是 Error 实例且 code 为字符串；经 napi_create_error 的是 Error 实例、code 为原生侧传入的字符串或数，经 napi_throw_business_error 的是 code 为数的 Error 实例）；源端按 IllegalArgumentException、SocketTimeoutException、UnknownHostException 等异常类型分支；@ohos.net.http 的失败码为 2300000 加 libcurl 码。也包括依据 d.ts @throws 列出的数值错误码（如定位开关关闭）决定等待、重试或失败，而 d.ts 把 BusinessError.code 声明为 number。

## 原因

按 instanceof Error 取消息会把以普通对象拒绝的 BusinessError（如 @ohos.net.http 的失败）记成“[object Object]”；按 Java 异常类名或英文消息关键词分类，会让所有失败落入通用 IO 错误。d.ts 的 code: number 只是声明，部分 Kit 抛出的 BusinessError.code 运行时是字符串（例：geoLocationManager 在定位开关关闭时同步抛出的 code 为 "3301100"），与数值常量严格相等永不成立，分支静默落空。

## 做法

1. 公共层建一个取消息函数（Error 取 message，否则读 BusinessError 的 message 与 code，都没有才字符串化），各 catch 统一调用，不在每处写 instanceof Error ? message : String()。
2. 错误分类优先比较 code：@ohos.net.http 为 2300000 加 libcurl 码（3 URL 格式错误、6 无法解析主机、28 超时、60/77 证书校验），消息匹配只作兜底并先用目标平台实际消息核对；规格的错误码表写出这一目标判据，依据取 SDK 声明的 @throws 或网络错误码表。
3. 比较错误码前先归一：Number((err as BusinessError).code) === 常量（或同时接受数值与字符串形式），各分支共用同一判别函数；沿用已有代码的错误码判别时同样改为归一比较。

## 可选检查

- 日志或提示出现 [object Object]、或失败分类全部相同时，用不可达地址、坏域名、非法 URL 各触发一次核对
- 错误码分支决定用户可见行为（如开关关闭时等待还是失败）时，在设备上触发该错误，用 hilog 打印 JSON.stringify(err) 核对 code 的实际类型与值，确认分支命中

- 〔适用情境 / 原因〕BusinessError 声明在 @ohos.base（可从 @kit.BasicServicesKit 导入）：export interface BusinessError<T = void> extends Error { code: number; data?: T }；code: number 只是声明类型，运行时 catch 到的值不一定是 Error 实例，code 也不一定是 number
- 〔适用情境〕Node-API 的 napi_throw_error(env, code, msg) 中 code 是 C 字符串，抛到 ArkTS 的是 Error 实例、code 属性为字符串（文档示例用 %{public}s 打印 error.code）；OpenHarmony 版允许 code 为空指针、允许 code 属性设置失败
- 〔适用情境〕Node-API 的 napi_create_error 在 OpenHarmony 中 code 参数支持 String 或 Number 类型（类型不匹配返回 napi_invalid_arg），创建的 Error 对象经 napi_throw 抛出后 code 的类型取决于原生侧传入的是哪一种
- 〔适用情境〕napi_throw_business_error(env, int32_t errorCode, const char* msg)（起始版本 API 23）抛出的是原生 Error 对象，code 属性为 number，不是 ArkTS SDK 中声明的 BusinessError 对象
- 〔适用情境 / 原因〕geoLocationManager.on(type: 'locationChange', request: LocationRequest | ContinuousLocationRequest, callback: Callback<Location>): void（从 @kit.LocationKit 导入；首段 @since 9）在声明里 @throws { BusinessError } 3301100 - The location switch is off.，即定位开关关闭时同步抛出
- 〔原因 / 做法第 3 步〕HarmonyOS 6.1.1(24) 设备上定位开关关闭时，geoLocationManager.on('locationChange') 同步抛出的错误经 JSON.stringify 打印为 {"code":"3301100"}：code 是字符串，与数值常量 3301100 严格相等（===）不成立；其他 Kit 的 code 运行时类型卡里没有实测
- 〔适用情境 / 原因 / 做法第 1 步〕设备上 @ohos.net.http 请求失败时 catch 到的值是带数值 code 和 message 的普通对象：instanceof Error 为 false，String(值) 得到 '[object Object]'；超时失败时 message 为 'Operation timeout'
- 〔做法第 2 步〕HttpRequest.request(url: string, options?: HttpRequestOptions): Promise<HttpResponse>（http 从 @kit.NetworkKit 导入；首段 @since 6）的 @throws 含 2300003 Invalid URL format or missing URL.、2300006 Failed to resolve the host name.、2300028 Operation timeout.、2300060 Invalid SSL peer certificate or SSH remote key.、2300077 The SSL CA certificate does not exist or is inaccessible.
- 〔做法第 2 步〕HTTP 错误码文档：2300003 URL 格式错误、2300006 域名解析失败、2300028 操作超时、2300060 远程服务器 SSL 证书或 SSH 密钥不正确、2300077 SSL CA 证书不存在或没有访问权限；各码给的定位日志关键词是「HttpClient CURLcode result N」，N 即错误码减去 2300000（如 2300028 对 result 28）
