# Kit API 的 catch 值按 BusinessError 取 message 与 code，code 先 Number() 归一再比较错误码

## 何时使用

规格提取与服务实现阶段，迁移源端按异常类型分类、以 getMessage() 记录详情的 catch 分支时；按 SDK @throws 错误码为 Kit 调用编写异常分支判别时

## 适用情境

目标 catch 到的是网络、文件、数据库、定位等 Kit API 抛出或拒绝的 BusinessError（运行时形态因接口而异：@ohos.net.http 拒绝的是带数值 code 与 message 的普通对象，不是 Error 实例；经 napi_throw_error 抛出的，如 geoLocationManager 的同步出错路径，是 Error 实例且 code 为字符串；经 napi_throw_business_error 的是 code 为数的 Error 实例；经 napi_create_error 的是 Error 实例，code 是数还是字符串取决于传入的值）；源端按 IllegalArgumentException、SocketTimeoutException、UnknownHostException 等异常类型分支；@ohos.net.http 的失败码为 2300000 加 libcurl 码。源端靠异常判出的 HTTP 状态失败（HttpURLConnection 读 4xx、5xx 响应时抛 FileNotFoundException 一类 IOException）在 @ohos.net.http 下不进 catch：请求照常完成，状态在响应的 responseCode 里，这类分支按 responseCode 判断，不在 catch 的错误码里找。也包括依据 d.ts @throws 列出的数值错误码（如定位开关关闭）决定等待、重试或失败，而 d.ts 把 BusinessError.code 声明为 number。

## 原因

按 instanceof Error 取消息会把以普通对象拒绝的 BusinessError（如 @ohos.net.http 的失败）记成“[object Object]”；按 Java 异常类名或英文消息关键词分类，会让所有失败落入通用 IO 错误。d.ts 的 code: number 只是声明，部分 Kit 抛出的 BusinessError.code 运行时是字符串（例：geoLocationManager 在定位开关关闭时同步抛出的 code 为 "3301100"），与数值常量严格相等永不成立，分支静默落空。

## 做法

1. 公共层建一个取消息函数（Error 取 message，否则读 BusinessError 的 message 与 code，都没有才字符串化），各 catch 统一调用，不在每处写 instanceof Error ? message : String()。
2. 错误分类优先比较 code：@ohos.net.http 为 2300000 加 libcurl 码（3 URL 格式错误、6 无法解析主机、7 无法连接服务器、28 超时、60/77 证书校验；映射表里没有的 libcurl 码统一为 2300999），消息匹配只作兜底并先用目标平台实际消息核对；规格的错误码表写出这一目标判据，依据取 SDK 声明的 @throws 或网络错误码表。
3. 比较错误码前先归一：Number((err as BusinessError).code) === 常量（或同时接受数值与字符串形式），各分支共用同一判别函数；沿用已有代码的错误码判别时同样改为归一比较。

## 可选检查

- 日志或提示出现 [object Object]、或失败分类全部相同时，用不可达地址、坏域名、非法 URL 各触发一次核对
- 错误码分支决定用户可见行为（如开关关闭时等待还是失败）时，在设备上触发该错误，用 hilog 打印 JSON.stringify(err) 核对 code 的实际类型与值，确认分支命中

- 〔适用情境〕Node-API 抛出的错误 code 类型随接口不同：napi_throw_error 的 code 传的是 C 字符串，抛到 ArkTS 的 Error.code 为字符串；napi_create_error 的 code 可以是 String 或 Number；napi_throw_business_error（API 23 起）抛出原生 Error、code 为 number，文档注明它不是 SDK 声明的 BusinessError 对象
- 〔何时使用 / 做法第 2 步〕定位开关未开启时，geoLocationManager 的 on('locationChange') 等定位接口以错误码 3301100 失败，错误信息为 The location switch is off.
- 〔做法第 2 步〕@ohos.net.http 的错误码按 2300000 + libcurl 错误码映射（libcurl 1 对应 2300001，28 对应 2300028）；libcurl 返回映射表里没有的码时统一返回 2300999
- 〔做法第 2 步〕@ohos.net.http 错误码含义：2300003 URL 格式错误或 URL 缺失；2300006 域名解析失败；2300007 无法连接到服务器（地址或端口不对、服务未启动、被防火墙拦截，文档也把连接超时列为可能原因）；2300028 操作超时（connectTimeout、readTimeout 不写时都是 60000ms）；2300060 远程服务器 SSL 证书或 SSH 密钥不正确；2300077 SSL CA 证书不存在或没有访问权限
- 〔做法第 2 步〕设备上 @ohos.net.http 请求超时时，catch 到的错误 message 是 'Operation timeout'（与 SDK 声明里 2300028 的说明文字一致），不是安卓 SocketTimeoutException 那类英文消息
