# Kit API 的 catch 值按 BusinessError 取 message 与 code，code 先 Number() 归一再比较错误码

## 何时使用

规格提取与服务实现阶段，迁移源端按异常类型分类、以 getMessage() 记录详情的 catch 分支时；按 SDK @throws 错误码为 Kit 调用编写异常分支判别时

## 适用情境

目标 catch 到的是网络、文件、数据库、定位等 Kit API 抛出或拒绝的 BusinessError（运行时形态因接口而异：@ohos.net.http 拒绝的是带数值 code 与 message 的普通对象，不是 Error 实例；经 napi_throw_error 抛出的，如 geoLocationManager 的同步出错路径，是 Error 实例且 code 为字符串；经 napi_create_error 或 napi_throw_business_error 的是 code 为数的 Error 实例）；源端按 IllegalArgumentException、SocketTimeoutException、UnknownHostException 等异常类型分支；@ohos.net.http 的失败码为 2300000 加 libcurl 码。也包括依据 d.ts @throws 列出的数值错误码（如定位开关关闭）决定等待、重试或失败，而 d.ts 把 BusinessError.code 声明为 number。

## 原因

按 instanceof Error 取消息会把以普通对象拒绝的 BusinessError（如 @ohos.net.http 的失败）记成“[object Object]”；按 Java 异常类名或英文消息关键词分类，会让所有失败落入通用 IO 错误。d.ts 的 code: number 只是声明，部分 Kit 抛出的 BusinessError.code 运行时是字符串（例：geoLocationManager 在定位开关关闭时同步抛出的 code 为 "3301100"），与数值常量严格相等永不成立，分支静默落空。

## 做法

1. 公共层建一个取消息函数（Error 取 message，否则读 BusinessError 的 message 与 code，都没有才字符串化），各 catch 统一调用，不在每处写 instanceof Error ? message : String()。
2. 错误分类优先比较 code：@ohos.net.http 为 2300000 加 libcurl 码（3 URL 格式错误、6 无法解析主机、28 超时、60/77 证书校验），消息匹配只作兜底并先用目标平台实际消息核对；规格的错误码表写出这一目标判据，依据取 SDK 声明的 @throws 或网络错误码表。
3. 比较错误码前先归一：Number((err as BusinessError).code) === 常量（或同时接受数值与字符串形式），各分支共用同一判别函数；沿用已有代码的错误码判别时同样改为归一比较。

## 可选检查

- 日志或提示出现 [object Object]、或失败分类全部相同时，用不可达地址、坏域名、非法 URL 各触发一次核对
- 错误码分支决定用户可见行为（如开关关闭时等待还是失败）时，在设备上触发该错误，用 hilog 打印 JSON.stringify(err) 核对 code 的实际类型与值，确认分支命中

已核实的平台事实（核实时用的是 HarmonyOS 6.1.0（API 23，SDK 6.1.0.105）；安卓 不涉及。和具体应用无关，直接用，不用再查；其中的默认值只在应用自己的主题、样式、清单和代码没有另设时成立，应用有没有另设要到应用里看）：
- 〔适用情境〕@ohos.net.http 的请求失败时，Promise 拒绝值（或回调的 err）是用 napi_create_object 建的普通对象，带数值 code 和字符串 message（开启 USE_ARES 的构建另带 extendInfo）：err instanceof Error 为 false，没有 stack，String(err) 得到“[object Object]”。〔成立范围：对象：@ohos.net.http 的 HttpRequest.request、requestInStream 的失败值。条件：依据是 OpenHarmony communication_netstack 仓 master 的实现（失败时 http_exec.cpp 用 NapiUtils::CreateErrorMessage 建对象后 napi_reject_deferred 或作回调首参），HarmonyOS 商用版本的实现未核。不成立：别的 Kit 不一定是这种形态，走 napi_throw_error / napi_create_error 的是 Error 实例，见条目 2。〕
- 〔原因〕经 napi_throw_error 抛出的错误是 Error 实例，code 属性是字符串（取自传入的 const char*）；geoLocationManager 的 isLocationEnabled、getLastLocation 等接口的同步出错路径经 HandleSyncErrCode 用 napi_throw_error(std::to_string(错误码)) 抛出，所以 err instanceof Error 为 true、err.code 是“3301100”这样的字符串；同一 Kit 里经 ThrowBusinessError → CreateError（napi_create_error 加数值 code）抛出的，则是 code 为数的 Error。〔成立范围：对象：@ohos.geoLocationManager 的同步抛错路径，以及任何经 napi_throw_error 抛错的 Kit 接口。条件：依据是 base_location 仓与 arkui_napi 仓 master 的实现。不成立：经 napi_create_error 传数值 code、或经 napi_throw_business_error 抛出的，code 是数。〕
- 〔做法第 2 步〕@ohos.net.http 的失败码多数是 2300000 加 curl 错误码：2300003 URL 格式错误、2300006 域名解析失败、2300007 无法连接到服务器、2300028 操作超时（TCP 连接超时或读写超时都是它）、2300060 远程服务器 SSL 证书或 SSH 密钥不正确、2300077 SSL CA 证书不存在或没有访问权限；另有 2300997 明文 HTTP 被拦截、2300998 不允许访问域名、2300999 内部错误，这三个不对应 curl 码。〔成立范围：对象：@ohos.net.http 的 request、requestInStream 等失败时的 code。条件：依据是文档（HTTP 错误码表和接口说明里的映射关系）。不成立：通用错误码（如 201 权限、401 参数）不在 2300000 区间。〕
- 〔适用情境〕@ohos.net.http 的 request 在参数、权限等调用前的检查通过以后，只在传输层失败（curl 结果不是 CURLE_OK，或取响应码、Cookie 等响应信息失败）时拒绝；服务器返回 4xx、5xx 时 Promise 照常兑现，状态码在 HttpResponse.responseCode 里，catch 分支收不到。〔成立范围：对象：@ohos.net.http 的 request。条件：依据是 OpenHarmony communication_netstack 仓 master 的 http_exec.cpp（GetCurlDataFromHandle 只在 curl 失败或取响应信息失败时 SetErrorCode，读到的响应码只存进 response；没有设 CURLOPT_FAILONERROR），HarmonyOS 商用版本的实现未核。不成立：参数错误（401）、缺权限（201）这类调用前的错误同样进 catch；超时、域名解析、证书校验这类 curl 层失败会拒绝、进 catch。〕
