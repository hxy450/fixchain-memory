# Java 文本读行、split/trim、BOM、String.format、SimpleDateFormat/Calendar 的时区与周规则不用同名 JS API 近似：按 Java 语义集中实现兼容函数，未 setTimeZone 的格式化按构造时默认时区取本地字段

## 何时使用

页面转换和服务/VM 抽取阶段，把 Java 标准库的读行、切分、去空白、解码、数值格式化与日历计算翻译成 ArkTS 时；把 SimpleDateFormat 格式化毫秒值（含语义像时长的值）或格式化固定 epoch 的偏移探测翻译成显式算术时

## 适用情境

源码用 BufferedReader.readLine、String.split/trim、FileReader/InputStreamReader、String.format("%.2f", float) 或 Calendar.getInstance() 的 WEEK_OF_YEAR 处理文件行、编辑框文本、百分比与日期；目标准备用 JS 的 split/trim/toFixed、TextDecoder 或手写 ISO 周换算；派工可能写“与 readFileLineByLine 等价”“数值域同 Android”。 也包括 new SimpleDateFormat(pattern, Locale) 或 Calendar 未调用 setTimeZone 就格式化一个毫秒值（变量语义像时长，如 gameTime + hourOffset×3600000），或格式化 1970-01-01T00:01Z 按本地小时位探测偏移；目标准备“不经 Date/Intl”按 UTC 手工拆 h/m/s。

## 原因

同名 API 语义不同：Java readLine 在最后一个终止符后不产生空行、split 丢弃末尾空串，JS split 保留；Java trim 只去 ≤U+0020，JS trim 还去 NBSP、U+FEFF；util.TextDecoder 默认（ignoreBOM 为 false）结果保留 BOM、设 ignoreBOM: true 才去掉，Java 读取器把它当普通字符；String.format 按 float、HALF_UP 与默认 Locale 输出小数点（fr、it 等为逗号），toFixed 不是；Calendar 的周首日与首周最少天数随区域变化，不等于 ISO。来源中这些近似分散在多个页面，又被服务抽取原样搬运：以换行结尾的文件多出空行、扇区文本被判为 5 行而报错、差异百分比丢了区域小数点、生产周的起止日偏移。未 setTimeZone 的 formatter 绑定构造时的默认时区，format 输出本地字段；按 UTC 拆 h/m/s 只在偏移为 0 的时区与源端一致，用当前 getRawOffset 代替对 1970 时刻的探测会丢掉历史偏移与夏令时。另一应用中召回摘要把本条压成“不用 Date/Intl 模板近似”，规格与实现都把对局时间写成了 UTC 纯时长。

## 做法

1. 在服务层集中实现一组 Java 兼容函数（readLines、split、trim、decode、formatFixed 等），所有服务、VM 与页面统一调用，不在各处各写近似实现。
2. readLine 按 \n、\r、\r\n 断行且最后一个终止符后不产生空行；split 丢弃末尾空串；trim 只去 ≤U+0020；解码保留 BOM 字符（输入以 EF BB BF 开头、解码结果首字符却不是 U+FEFF 时，在结果前补回 U+FEFF）。
3. String.format("%.Nf", float) 按 float 运算（每步运算结果用 Math.fround 舍入到单精度）、对这个 float 转成 double 后的十进制展开做 HALF_UP 舍入（不是对 Float.toString 的短串舍入，如 1.005f 用 %.2f 得 1.00），并按默认 Locale 输出小数点与数字；Calendar.getInstance() 或 SimpleDateFormat(..., Locale.getDefault()) 按区域的 firstDayOfWeek 与 minimalDaysInFirstWeek（如 i18n Calendar）计算。
4. SimpleDateFormat/DateFormat/Calendar 未调用 setTimeZone 时，把 format 的输入当作时刻：在源端构造时机取 i18n.getTimeZone()，local = instant + tz.getOffset(instant) 后再拆 HH/mm/ss，输入值语义像时长也一样；“格式化固定 epoch 的本地小时位”一类探测用 tz.getOffset(该时刻) 复刻，不用当前 getRawOffset；时间显示类验收至少给一个非零偏移时区的样例。

## 可选检查

- 最小样例：内容为 "a\nb\n" 的文件按行读取应得 ["a","b"]；以换行结尾的文本 split 后不多出末尾空串
- UTC+8 时区下 gameTime=0 的格式化结果为 08:00:00，不是 00:00:00。

已核实的平台事实（核实时用的是 HarmonyOS 6.1.0（API 23，SDK 6.1.0.105）；OpenHarmony 文档 master 2026-11-21（提交 e42bd18a）；安卓 源码 android-36.1；时区数据取 AOSP platform/system/timezone main 的 tzdata2025a。和具体应用无关，直接用，不用再查；其中的默认值只在应用自己的主题、样式、清单和代码没有另设时成立，应用有没有另设要到应用里看）：
- 〔原因 / 做法第 2 步〕Java BufferedReader.readLine() 以 '\n'、'\r'、紧跟 '\n' 的 '\r' 三者之一或文件尾结束一行，返回的行不含终止符；流已到尾且没读到任何字符时返回 null，所以最后一个终止符之后不再产生一行（"a\nb\n" 读出 "a"、"b" 两行），而相邻两个终止符之间会读出空串行（"a\n\nb" 读出 "a"、""、"b"）
- 〔原因 / 做法第 2 步〕Java String.split(regex) 等于 split(regex, 0)：末尾的空串全部丢弃（"a\nb\n".split("\n") 得 ["a","b"]，"\n\n".split("\n") 得空数组）；一处都没匹配时返回只含原串的数组；开头是正宽度匹配时保留开头的空串，开头的零宽匹配不产生开头空串；limit 为负时末尾空串保留
- 〔适用情境 / 做法第 2 步〕Android 上 System.getProperty("line.separator") 是 "\n"，源码 split(System.getProperty("line.separator")) 只按 LF 切，不认 '\r'
- 〔原因 / 做法第 2 步〕ArkTS 里字符串的 split('\n') 或 split(/\r\n|\r|\n/) 保留末尾空串：以换行结尾的文本切出的数组末尾多一个 ""，按行数判定的逻辑会多算一行
- 〔原因 / 做法第 2 步〕Java String.trim() 去掉首尾码点 ≤ U+0020 的字符（空格和 U+0000–U+001F 全部控制字符），不去 U+00A0（NBSP）、U+3000（全角空格）、U+FEFF 等 Unicode 空白
- 〔原因 / 做法第 2 步〕ArkTS 的 String.prototype.trim() 去掉首尾的 white space 和 line terminator 字符（声明注释原话），范围和 Java trim 不同：比 Java 多去 NBSP、U+FEFF 等 Unicode 空白
- 〔原因 / 做法第 2 步〕util.TextDecoder（import { util } from '@kit.ArkTS'）：static create(encoding?: string, options?: TextDecoderOptions): TextDecoder（自 API 9 起），encoding 默认 'utf-8'；TextDecoderOptions { fatal?: boolean; ignoreBOM?: boolean }（自 API 11 起），两项都默认 false；文档写 ignoreBOM 为 false 时对 BOM 解码、结果含 BOM，为 true 时忽略 BOM（文档示例 ignoreBOM: true 解 EF BB BF 61 62 63 得 "abc"）；解码用 decodeToString(input: Uint8Array, options?: DecodeToStringOptions): string（自 API 12 起）。卡里记录过 TextDecoder 解码后 BOM 丢失，没记用的构造和选项
- 〔做法第 3 步〕Java String.format(String, Object...) 用 new Formatter()，区域取 Locale.getDefault(Locale.Category.FORMAT)；%f 输出时小数点换成该区域 DecimalFormatSymbols 的 decimal separator（区域为 Locale.US 时才固定为 '.'），数字换成该区域的 zero digit 起算的字形，带 ',' 标志时才加分组分隔符
- 〔做法第 3 步〕Android 的 Formatter 对 float 参数先转成 double（print(float) 直接调 print((double) value)），%.Nf 再对这个 double 的十进制展开（FloatingDecimal 的结果）在第 N 位小数做 HALF_UP 舍入；类注释写的是按 Float.toString 的位数舍入，和实现不一致。例：1.005f 的 double 值展开是 1.0049999952316284，%.2f 得 "1.00"；33.335f 展开是 33.334999084472656，%.2f 得 "33.33"（Float.toString 是 "33.335"）
- 〔做法第 3 步〕Math.fround(x: number): number 返回最接近 x 的单精度浮点值；ArkTS 的 number 是双精度
- 〔做法第 3 步〕源端 (float) 除法再乘 100 后取整的百分比，用双精度算和每步按单精度舍入算，在卡里构造的输入上有 116 组相差 1
- 〔做法第 3 步〕intl.NumberFormat（import { intl } from '@kit.LocalizationKit'）：constructor()（自 API 8 起）用当前系统区域；constructor(locale: string | Array<string>, options?: NumberOptions)；NumberOptions 有 minimumFractionDigits、maximumFractionDigits、useGrouping、numberingSystem，roundingMode?: string（自 API 18 起，取值 ceil、floor、expand、trunc、halfCeil、halfFloor、halfExpand、halfTrunc、halfEven，不传时为 "halfExpand"）
- 〔做法第 3 步〕取区域：i18n.System.getSystemLocale(): string 自 API 9 起、API 20 起废弃，替代为 static getSystemLocaleInstance(): Intl.Locale（自 API 20 起，本机 SDK 有）；应用偏好语言用 static getAppPreferredLanguage(): string（自 API 9 起）；i18n 从 @kit.LocalizationKit 导入
- 〔原因 / 做法第 3 步〕Java Calendar 的第一周是从 getFirstDayOfWeek() 开始、含当年（当月）至少 getMinimalDaysInFirstWeek() 天的最早 7 天；Android 上 Calendar.getInstance() 总是建 GregorianCalendar，区域取 Locale.getDefault(Locale.Category.FORMAT)，这两个值按区域从 ICU 的周数据取（Android 14 起区域带 fw Unicode 扩展时周首日按扩展，android-13.0.0_r1 的 libcore 没有这一支），也可用 setFirstDayOfWeek、setMinimalDaysInFirstWeek 改；SUNDAY = 1 … SATURDAY = 7
- 〔做法第 3 步〕GregorianCalendar 只设了 YEAR 和 WEEK_OF_YEAR、没设 DAY_OF_WEEK 时，日期取那一周的周首日：先取 1 月 1 日起 7 天内落在 firstDayOfWeek 的那天，它离 1 月 1 日不少于 minimalDaysInFirstWeek 天时再往前退 7 天，得第 1 周起点，第 n 周起点再加 7×(n−1) 天
- 〔做法第 3 步〕i18n.getCalendar(locale: string, type?: string): Calendar（自 API 8 起），type 不传时取该区域的默认历法（可传 "gregory"）；Calendar.getFirstDayOfWeek(): number 返回 1 表示周日、7 表示周六（文档示例 en-US 为 1），getMinimalDaysInFirstWeek(): number 返回首周最少天数（文档示例 zh-Hans 为 1），另有 setFirstDayOfWeek、setMinimalDaysInFirstWeek；i18n.System.getFirstDayOfWeek(): WeekDay（自 API 18 起）取的是系统设置里的周起始日，不是按区域
- 〔原因 / 做法第 4 步〕Java SimpleDateFormat(pattern, locale) 构造时 initializeCalendar 调 Calendar.getInstance(loc)，用的是构造那一刻的默认时区（TimeZone.getDefault() 返回副本，构造以后改默认时区不影响已构造的 formatter；Android 14 起区域带 tz Unicode 扩展时取扩展指定的时区，android-13.0.0_r1 的 libcore 不看这个扩展）；SimpleDateFormat(pattern) 的区域取 Locale.getDefault(Locale.Category.FORMAT)；无参 GregorianCalendar() 也用默认时区。未调用 setTimeZone 时 format 输出的是这个时区下的本地字段
- 〔原因 / 做法第 4 步〕Java TimeZone.getOffset(long date) 返回该时刻相对 UTC 的偏移（毫秒，含夏令时），时区实现支持历史规则时按历史给值；Android 用的 IANA 时区数据里 Europe/London 在 1968-10-27 至 1971-10-31 全年为 UTC+1（BST），1970-01-01T00:01Z 的本地小时是 01，和现在的原始偏移 0 不同
- 〔原因 / 做法第 4 步〕i18n.getTimeZone(zoneID?: string): TimeZone（自 API 7 起），不传 zoneID 取系统时区；TimeZone.getOffset(date?: number): number（自 API 7 起）的 date 是毫秒时刻、不传取当前时间，返回该时刻的偏移（毫秒），处于夏令时时为原始偏移加夏令时偏移；getRawOffset(): number 返回原始偏移（毫秒），不随时刻变（文档示例 Asia/Shanghai 均为 28800000）
