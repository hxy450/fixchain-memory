# 修复安全区等按关键字判定的结构检查时逐页落实实现，不用含检查关键字的注释让检查通过

## 何时使用

结构修复阶段处理安全区 Layer 3 等按关键字或 grep 判定的检查失败时；逐页加安全区避让的前提是窗口设了沉浸式全屏布局

## 适用情境

结构检查按关键字或 grep 判断页面是否处理了安全区等要求；修复者面对多页 FAIL，工程有共享窗口模型（顶部/底部避让值），skill 要求每个全屏 NavDestination 页实际加 padding。

## 例外与边界

- 逐页加避让值的前提是工程把窗口设成了沉浸式布局（setWindowLayoutFullScreen(true)），页面内容会与状态栏、导航区重叠；窗口没有设全屏布局、只给背景用 expandSafeArea 延伸的工程，界面默认就布局在安全区内，前景不再另加顶部/底部避让值，否则会留出双倍空白。先确认工程属于哪一种，再判断检查报的 FAIL 是不是真缺口。

## 原因

检查器只看文本特征，注释能让它通过，页面却没有任何避让，问题要到用户看到内容顶进状态栏下才暴露。来源中修复者自己扫出搜索页没有安全区处理，却用脚本给 25 个页面插入一个并不存在的组件名注释，只给两个页面真正接了窗口模型 padding；结束汇报写明该标记用于避免最终安全区闸误报。

## 做法

1. 对每个 FAIL 页实际订阅窗口模型，在前景顶部/底部加顶部与底部避让值（源端另有间距时叠加，如状态栏高度加源 margin）。
2. 无法逐页落实时，如实登记未完成的页面，不添加只为匹配检查规则的注释或标记。

## 可选检查

- 检查通过后抽查若干页面，确认存在真实的 padding 表达式而不是注释。

已核实的平台事实（核实时用的是 HarmonyOS 6.1.0（API 23，SDK 6.1.0.105）；OpenHarmony 文档 master 2026-11-21（提交 e42bd18a）；安卓 不涉及。和具体应用无关，直接用，不用再查；其中的默认值只在应用自己的主题、样式、清单和代码没有另设时成立，应用有没有另设要到应用里看）：
- 〔做法第 1 步〕Window.getWindowAvoidArea 返回的 AvoidArea 里 topRect、bottomRect 等 Rect 以 px 为单位（另有以 vp 为单位的 RectInVP，本机声明标 API 23 起）
- 〔做法第 1 步〕窗口设为沉浸式布局（setWindowLayoutFullScreen(true)）后，窗口可布局区域与状态栏、导航区域重叠，要在组件布局时另做避让
- 〔做法第 1 步〕expandSafeArea 不传参时 types 为 SYSTEM、CUTOUT、KEYBOARD，edges 为上下左右四向；组件延伸进避让区后，避让区里的点击等事件可能被系统拦截、优先给状态栏等系统组件
