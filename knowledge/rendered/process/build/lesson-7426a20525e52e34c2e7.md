# 编译检查按完整构建结果判定：读全 ERROR 列表与 COMPILE RESULT，构建失败只记 FAIL，不以“仅警告”“部分通过”放行

## 何时使用

验证阶段执行编译检查并决定是否标记阶段完成时；编译修复循环查看构建输出时；构建通过后又改动了源码、准备宣称“最终构建通过”时

## 适用情境

hvigor 构建输出重定向到文件，WARN 常排在 ERROR 之前；修复循环只截取错误文件前若干行；验收规范规定编译通过才 PASS、否则 FAIL 并继续修复循环。或编排者在构建报成功后又追加源码改动，派出的复核构建尚未返回结果。

## 原因

只看前 N 行会只见警告、漏掉错误；把 BUILD FAILED 记成“部分通过/仅警告”并标记阶段完成，失败构建就进入交付，用户首次运行即遇编译错误。来源中验证阶段读到 FAILURE 与“编译失败”，仍把编译检查写成部分通过并进入下一阶段；页签重载错误和登记页缺 @Entry 两处错误都留到了用户侧。另一应用中编排者在构建报 BUILD SUCCESSFUL 后又往页面写入新代码，复核构建尚无结果就宣称“最终构建通过、0 errors”，新改动带来的编译错误由用户运行时报出。另一应用中，多轮构建都打印了“To use this API, you need to apply for the permissions: ohos.permission.APPROXIMATELY_LOCATION”，构建者只按错误数判 PASS，缺失的权限声明留到了真机。

## 做法

1. 按 ERROR 过滤，或读 COMPILE RESULT 汇总（如 ERROR:6 WARN:7）与 BUILD SUCCESSFUL/FAILED 结论，逐条列出剩余错误；剩余错误按编号的「<序号> ERROR:」行逐条数，不拿汇总行的 ERROR 数当错误条数：hvigor 6.23.6 的 CompileArkTS 失败时打的汇总，ERROR 数比编号的错误条数多 1（这一点只在这个版本、这条编译路径上读代码确认过，别的 hvigor 版本没确认；ets-loader 自带的 webpack 编译路径打的 ERROR 数就是错误条数）。
2. 构建失败时编译检查只记 FAIL 并列出剩余错误，继续修复循环；不以警告为由记为部分通过，也不标记阶段完成。
3. “最终构建通过”只引用开始时间晚于最后一次源码写入的构建结果；构建后又改源码就重新构建并等待该次结果。
4. 构建日志出现“To use this API, you need to apply for the permissions: X”一类警告时，与 module.json5 的 requestPermissions 逐项对照，缺项先补再判定通过。

来源支持：4 张卡 · 3 次迁移 · 3 个应用

已核实的平台事实（核实时用的是 HarmonyOS 6.1.0（API 23，SDK 6.1.0.105）；DevEco Studio 自带 hvigor 6.23.6；OpenHarmony 文档 master 2026-11-28（提交 4d3e2aa3）；安卓 不涉及。和具体应用无关，直接用，不用再查；其中的默认值只在应用自己的主题、样式、清单和代码没有另设时成立，应用有没有另设要到应用里看）：
- 〔做法第 1、2 步〕hvigor 的 CompileArkTS 任务（hvigor 6.23.6，经 hvigor-arkts-compose 打包）失败时，错误块最后一行是「COMPILE RESULT:FAIL {ERROR:<n>」，后接 WARN:<警告数>、INFO:<提示数>（各自只在不为 0 时出现）和「}」；n 的计数器从 1 起、每列出一条编号错误加 1，所以 n 比块里编号的错误条数多 1（块里没有编号错误时 n 为 1）。这条路径编译成功时不打 COMPILE RESULT 行。ets-loader 自己的 webpack 编译路径（compile_info.js 的 printLogCount，CompileArkTS 不走它）另有一种汇总：有错误时「COMPILE RESULT:FAIL {ERROR:<错误数>…}」，字节码编译没有成功时错误数为 0 也记 FAIL，没有错误且字节码编译成功时是「COMPILE RESULT:SUCCESS」，有警告或提示时花括号里带 WARN、NOTE。两条路径下警告数多少都不会让结果变成 FAIL。
- 〔做法第 1、2 步〕hvigor 构建结束时整体结论是「BUILD SUCCESSFUL」或「BUILD FAILED」；CompileArkTS 失败时，hvigor 的错误块里每条错误写成「<序号> ERROR: <信息>」（序号从 1 起），块末是上一条说的「COMPILE RESULT:FAIL {ERROR:… }」一行；同一次的警告另列成「<序号> WARN: <信息>」、提示另列成「<序号> INFO: <信息>」，不在错误块里。
- 〔做法第 4 步〕ArkTS 编译时，对代码里调用的每个 SDK 接口，取它声明注释里的 @permission 标签，和本模块 module.json5 的 requestPermissions 各项 name 对照；对不上时报一条警告（类别是警告，不是错误）「To use this API, you need to apply for the permissions: <@permission 标签原文>」。这条警告不影响 COMPILE RESULT 和 BUILD 的结论：缺了权限声明，构建仍可以是 SUCCESS。
- 〔做法第 4 步〕权限声明在 module.json5 的 requestPermissions 里，每项 name 必填；申请 user_grant 或 manual_settings 类权限时 reason 必填（写成 $string: 引用，要多语种适配），usedScene 也必填（abilities 为使用权限的 UIAbility 或 ExtensionAbility 名称数组，when 只能填 inuse 或 always）；system_grant 类权限这两项选填。多 HAP 时，在 entry 或 feature 模块里声明过的权限对整个应用生效，不用在另一个模块重复声明。
- 〔做法第 4 步〕声明之后是否就有权限，看权限的授权方式：system_grant 在安装应用时自动授予；user_grant（例如 ohos.permission.APPROXIMATELY_LOCATION）除了声明，还要在运行时弹窗向用户申请，用户允许后才有；manual_settings（API 21 起）不能弹窗申请，只能由用户到系统设置里授权。某项权限属于哪一类，看应用权限列表里该权限的「授权方式」。
- 〔原因 / 做法第 4 步〕应用没有接口要求的权限时，调用在运行时报错误码 201（Permission verification failed）；文档列的原因有三种：配置文件没有声明该权限、敏感权限没有做运行时申请或用户没有授予、应用身份不满足接口的权限约束。
