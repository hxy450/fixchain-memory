# getWindowAvoidArea 与 windowRect 的数值是 px：在 windowStage.loadContent 成功回调里取 UIContext、先 px2vp 再写入供 padding 消费的窗口模型（loadContent 之前调 getUIContext 抛 1300002）

## 何时使用

沉浸式安全区实现阶段，在 EntryAbility 或窗口服务里把避让区、窗口尺寸写进共享窗口模型时；安排 EntryAbility.onWindowStageCreate 中依赖 UIContext 的步骤相对 loadContent 的时机时

## 适用情境

目标用 setWindowLayoutFullScreen(true) 全屏，EntryAbility 通过 getWindowAvoidArea 取状态栏、导航条高度，通过 getWindowProperties().windowRect 取窗口尺寸，写入 AppStorageV2 共享的窗口模型；各页把这些值直接放进 .padding()/.height()，按 vp 解释。 也包括换算或其他依赖 UIContext 的步骤（如 setKeyboardAvoidMode）写在 onWindowStageCreate 中、位于 loadContent 调用之前或在其回调之外同步执行。

## 原因

避让区 Rect 与 windowRect 的数值单位是 px，ArkUI 数字尺寸默认是 vp；原样写入后，高密度屏上的避让量会放大数倍。来源中修复者首次写入时注释已写“这是物理像素、需换算”，读到工程内页面已用 uiContext.px2vp 的样例后，反而删去换算占位，把注释改成“按 vp 消费”，也没写窗口宽高。另一应用基线 EntryAbility 把导航避让区 84px 原样发布，页面按 vp 消费后底部留白过大，修复在发布端统一 px2vp。UIContent 只在 loadContent 成功后建立，之前调用 mainWindow.getUIContext() 会抛 1300002（Uicontent is nullptr），冷启动即闪退；d.ts 签名不写这一时序，只凭成员存在推定此刻可调用就会写错，而不运行应用的编译门发现不了。

## 做法

1. 在 windowStage.loadContent 的成功回调里（err.code 为 0 之后）取 const ui = mainWindow.getUIContext()；top = ui.px2vp(avoid.topRect.height)，bottom 与窗口宽高同理；模型注释标明字段为 vp。onWindowStageCreate 中 loadContent 之前只做不依赖 UIContent 的窗口调用。
2. 一时取不到 UIContext 时保留 px 字段并上报，不把 px 值写进声明为 vp 的字段。

## 可选检查

- 改动 EntryAbility 生命周期后静态核对：onWindowStageCreate 中位于 loadContent 之前或其回调之外同步执行的代码不调用 getUIContext、不依赖 UIContent。

已核实的平台事实（核实时用的是 HarmonyOS 6.1.0（API 23，SDK 6.1.0.105）；安卓 不涉及。和具体应用无关，直接用，不用再查；其中的默认值只在应用自己的主题、样式、清单和代码没有另设时成立，应用有没有另设要到应用里看）：
- 〔原因；做法第 1 步〕getWindowAvoidArea 返回的 AvoidArea 四个矩形（left/top/width/height）、on('avoidAreaChange') 回调里的 area，以及 getWindowProperties() 的 windowRect、drawableRect，数值都是 px 整数；ArkUI 的 .padding()、.height() 等不带单位的数字按 vp 解释。〔成立范围：对象：@ohos.window 的 Rect 类型字段。条件：Rect 文档写明单位为 px、取整数；ArkUI 数值默认 vp 见像素单位文档。不成立：API 23 起的环境变量类型 UIEnvWindowAvoidAreaInfoVP、RectInVP、SizeInVP 等以 VP 结尾的已经是 vp，不能再 px2vp。〕
- 〔适用情境（状态栏、导航条高度）〕AvoidAreaType.TYPE_SYSTEM 是系统默认区域，包含状态栏和三键导航栏区域；TYPE_NAVIGATION_INDICATOR 是底部导航区域，三键导航显示时也始终存在；TYPE_SYSTEM_GESTURE 当前所有设备都没有这类区域。〔成立范围：对象：getWindowAvoidArea 与 avoidAreaChange 的 type。条件：依据是文档说明（TYPE_SYSTEM 的「包含状态栏和三键导航栏」是文档里按产品替换的段落）。不成立：只取 TYPE_SYSTEM 的 bottomRect 当底部避让时，非三键导航下的底部导航区域不在其中，要取 TYPE_NAVIGATION_INDICATOR 的 bottomRect。〕
- 〔做法第 1 步〕Window.getUIContext() 要在 UI 实例创建完成后调用，文档建议放在 windowStage.loadContent 的成功回调里；它声明的错误码 1300002 表示窗口状态异常（窗口未创建或已销毁）。〔成立范围：对象：主窗口 Window 的 getUIContext。条件：依据是文档说明，声明文件只写了 1300002 的「窗口未创建或已销毁」，没写与 loadContent 的时序。不成立：自定义组件里用 this.getUIContext() 取的是该组件所属的 UI 实例，不受这条时序限制（但在异步回调里、组件已销毁后调用会返回 undefined）。〕
- 〔做法第 2 步〕loadContent 或 setUIContent 之前没有 UI 实例：全局 px2vp/vp2px 按默认屏幕的 density 换算并返回结果，fp2px、px2fp、lpx2px、px2lpx 返回 undefined；文档给出的替代是用 display.getDefaultDisplaySync().densityPixels 自行换算。〔成立范围：对象：全局像素换算函数（已不推荐，推荐 UIContext 的同名方法）。条件：依据是文档说明。不成立：多屏时默认屏幕不一定是窗口所在的屏，结果可能与该窗口的 UIContext.px2vp 不一致。〕
- 〔例外与边界〕getWindowAvoidArea 在部分窗口模式下返回空区域：自由窗口状态的悬浮窗口只有固定态软键盘（TYPE_KEYBOARD）避让区；主窗口在非自由窗口状态的悬浮模式下只有 TYPE_SYSTEM；其余场景的主窗口只有在非悬浮模式或设备类型为 Phone、Tablet 时才返回计算后的避让区；子窗口只有位置和大小与主窗口一致时才有。〔成立范围：对象：主窗口、子窗口调用 getWindowAvoidArea。条件：依据是文档说明；全局悬浮窗、模态窗和系统窗口要先调 setSystemAvoidAreaEnabled 使能才有。不成立：手机、平板上全屏的主窗口按正常值返回。〕
