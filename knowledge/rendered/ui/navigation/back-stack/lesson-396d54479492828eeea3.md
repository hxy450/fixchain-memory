# 源端对话框、底部弹层或下拉菜单改成页内覆盖层后，在宿主 onBackPressed 里自顶向下逐层关闭，全部关闭后才进未保存门禁或出栈

## 何时使用

页面转换阶段，把源端 Dialog/AlertDialog/ModalBottomSheet/ExposedDropdownMenu（以及可能存在的 BackHandler）改写成 NavDestination 页内覆盖层、确定系统返回如何处理时

## 适用情境

源页的对话框、底部弹层或下拉菜单以 onDismissRequest 关闭；源页可能另有 BackHandler 处理行内编辑器或未保存门禁，也可能完全没有 BackHandler。目标把这些弹层做成 NavDestination 内 Stack 条件渲染的覆盖层或由 activeDialog 一类状态驱动的组件，而不是自带返回关闭的弹窗机制，系统返回统一交给宿主。也包括源端 ContextMenu 窗口、ActionMode 多选态被改写成页面 @Local 浮层或选择态，页面是嵌入宿主的组件。也包括 View 体系 AlertDialog（默认可取消、带 setOnCancelListener）被写成自带蒙层的共享页内浮层组件，只接蒙层点击，页面的返回拦截不感知弹窗。

## 例外与边界

- 弹层改用自带返回关闭的弹窗机制（openCustomDialog、bindSheet、NavDestinationMode.DIALOG 等）时，由弹窗自身处理返回

## 原因

Compose 的对话框、底部弹层与下拉菜单是独立窗口，系统返回先触发它的 onDismissRequest，BackHandler 只在没有弹层时才收到；例外三种：DialogProperties 设 dismissOnBackPress = false 的对话框（以及 ModalBottomSheetProperties 设 shouldDismissOnBackPress = false 的底部弹层）照样吃掉返回、什么也不做（目标在它可见时 return true 且不关闭），ModalBottomSheet 完全展开且有半展开档位（内容高过半屏、没设 skipPartiallyExpanded）时返回先收回到半展开、不关闭（目标按源端的档位状态处理这一次返回），ExposedDropdownMenu 的锚点是可编辑输入框时弹层不获焦、返回不进弹层，由 ExposedDropdownMenuBox 自带的 BackHandler 调 onExpandedChange(false) 收起（目标在它展开时按这个回调关闭）。搬进页面树后，只翻译显式的 BackHandler 或宿主根本不写返回处理，覆盖层打开时按返回会走到保存或丢弃门禁，甚至整页出栈、退出应用。来源中一个转换者读过源端 BackHandler 和各对话框的 onDismissRequest，onBackPressed 只处理了编辑器和门禁两支；另一应用的源页没有 BackHandler，转换者读到了 onDismissRequest 与给出自带返回关闭方案的映射参考，仍把关闭确认、关于、赞助弹窗和下拉选项写成 Stack 覆盖层，宿主没有返回处理。

## 做法

1. 列出本页所有可叠加的层（页内对话框、下拉或选项浮层、自绘底部弹窗、行内编辑器），onBackPressed 按从上到下判断：最上层可见就只调用它的关闭回调并 return true；没有可见层时 return false 交给默认返回。判断“可见”用的条件与该层实际渲染的条件一致（含渲染时附加的数据条件，如只在有内容时才渲染），不只看打开标志，否则标志为真而层未渲染时会吞掉一次返回。
2. 所有层都关闭后才进入未保存门禁或出栈。
3. 输出前对每个条件渲染的覆盖层（activeDialog 的每个取值、showXxx/pickerVisible 一类标志）和打开的编辑器各模拟一次返回，确认不会触发保存、丢弃或 pop；页内有这类覆盖层而宿主没有 onBackPressed 时先补上再交付。
4. 编排者把某个任务的页内覆盖层写法推广到后续派工时，同时写上“宿主 onBackPressed 按 onDismissRequest 关闭可见覆盖层”的配套要求。
5. 把 ContextMenu、ActionMode 等窗口型临时 UI 改写为页内状态时同步实现其返回语义：浮层打开时先关闭，多选态先退出，并消费本次返回；页面没有自己的返回钩子时，经宿主的回调分发登记。
6. 返回键与点遮罩路由到同一取消处理，按源端各对话框 OnCancelListener 的去向执行（如写首用标记、持久化勾选），不只关闭；共享浮层组件随组件交付返回键契约，消费它的页面逐个验证“弹窗打开时按返回只关弹窗、页面仍在、不叠弹”。

- 〔适用情境 / 做法第 6 步〕android.app.Dialog 的 mCancelable 默认 true；Dialog#onBackPressed 在 mCancelable 为 true 时调 cancel()，为 false 时什么也不做，但这次返回仍被对话框消费（按键路径上 onKeyDown 对 KEYCODE_BACK 一律返回 true；启用 OnBackInvokedCallback 时 onStart 登记的默认回调也只调 onBackPressed）；cancel() 先把已登记的 OnCancelListener 投递到消息队列再 dismiss()，在对话框所在线程上调用时回调在窗口移除之后、OnDismissListener 之前执行；点到窗口外时 Dialog#onTouchEvent 在 mCancelable 为 true 且窗口 shouldCloseOnTouch 成立时同样走 cancel()。AlertDialog.Builder 不调 setCancelable 时 cancelable 为 true，create() 对可取消的对话框显式调 setCanceledOnTouchOutside(true)。应用没有另设 setCancelable(false) 或 setCanceledOnTouchOutside(false) 时，View 体系 AlertDialog 的返回键和点窗口外都经 cancel() 触发 OnCancelListener
- 〔例外与边界〕CustomDialogController 弹出的自定义弹窗：按下返回键和 ESC 键时弹窗退出；CustomDialogControllerOptions.cancel 是返回、ESC 键和点击遮罩层退出时的回调（未设置时不执行任何操作）；autoCancel 默认 true，点遮罩层关闭
- 〔例外与边界〕UIContext 的 PromptAction.openCustomDialog<T extends Object>(dialogContent: ComponentContent<T>, options?: promptAction.BaseDialogOptions): Promise<void>（@since 12；另有 openCustomDialog(options: promptAction.CustomDialogOptions): Promise<number>）打开的弹窗：BaseDialogOptions.onWillDismiss?: Callback<DismissDialogAction>（@since 12）不注册时，点遮罩、侧滑（左滑/右滑）、三键 back、键盘 ESC 直接关闭弹窗；注册后这些操作不立即关闭，回调参数 DismissDialogAction 有 reason: DismissReason 和 dismiss: Callback<void>，由回调决定是否调用 dismiss；DismissReason.PRESS_BACK = 0 表示返回键、左右侧滑或 ESC，TOUCH_OUTSIDE = 1 表示点遮罩，CLOSE_BUTTON = 2 弹窗暂不返回；autoCancel 默认 true（点遮罩关闭）
- 〔例外与边界〕BaseDialogOptions.levelMode?: LevelMode（@since 15，LevelMode 从 @kit.ArkUI 导入）默认 LevelMode.OVERLAY = 0：弹窗显示在所有路由、导航页面之上，页面跳转时不调 close 就不会自动关闭；LevelMode.EMBEDDED = 1 为页面级弹窗，挂在当前 Page 下（levelUniqueId 给了某节点的 uniqueId 时挂在该节点所在的 NavDestination 下），只在 showInSubWindow 为 false（默认）时生效。页面级弹窗打开时侧滑返回先关闭弹窗并结束本次手势，再侧滑一次才返回上一页；点弹窗蒙层默认关闭弹窗。CustomDialogControllerOptions、AlertDialogParam 也有同名 levelMode
- 〔例外与边界〕NavDestinationAttribute.mode(value: NavDestinationMode): NavDestinationAttribute（首段 @since 11，不支持动态修改）；NavDestinationMode.DIALOG = 1：默认透明，进出路由栈不影响下层 NavDestination 的可见性生命周期（onShown、onHidden 等），只触发 onActive、onInactive；API 13 之前默认无系统转场动画，API 13 起支持系统转场动画；默认 STANDARD = 0
- 〔例外与边界〕bindSheet 半模态：用户下拉关闭、侧拉关闭（含左右侧滑、三键 back、键盘 ESC）、点遮罩或点关闭按钮时，SheetOptions 没有注册 shouldDismiss 或 onWillDismiss 就直接关闭；注册了则不立即关闭，由回调决定（onWillDismiss 的 DismissSheetAction.reason 给出关闭操作的类型）
- 〔原因〕Compose 的 Dialog 在 androidx.compose.ui:ui-android 1.10.0 里实现为 ComponentDialog（独立窗口，有自己的 OnBackPressedDispatcher），并在这个 dispatcher 上登记一个始终启用的返回回调：DialogProperties.dismissOnBackPress 为 true（调用方没有另传 DialogProperties 时即为 true）时调用 onDismissRequest，为 false 时什么也不做、这次返回仍被对话框消费；ESC 键抬起同样按 dismissOnBackPress 调 onDismissRequest；dismissOnClickOutside 在调用方没有另设时为 true，点内容区外调用 onDismissRequest。onDismissRequest 只是回调，对话框是否消失取决于调用方改不改显示状态
- 〔原因〕Material3（material3-android 1.4.0）的 DropdownMenu 在调用方没有另传 properties 时用 PopupProperties(focusable = true)；Compose Popup（ui-android 1.10.0）的 dismissOnBackPress 在没有另设时为 true，可获焦时返回键、ESC 抬起调用 onDismissRequest，不可获焦的 Popup 收不到返回键。ExposedDropdownMenu 的锚点是可编辑输入框（PrimaryEditable，或无障碍服务未开时的 SecondaryEditable）时弹层不可获焦，此时由 ExposedDropdownMenuBox 里的 BackHandler(enabled = expanded) 接返回，调用的是 onExpandedChange(false)
- 〔原因〕Material3（material3-android 1.4.0）的 ModalBottomSheet 显示在独立的对话框窗口里，调用方没有另传 ModalBottomSheetProperties 时 shouldDismissOnBackPress、shouldDismissOnClickOutside 为 true；返回时面板若完全展开且存在半展开档位（sheet 内容高度超过容器高度的一半，且 rememberModalBottomSheetState 没有设 skipPartiallyExpanded = true；内容不到一半高时没有这个档位），只收回到半展开、不调用 onDismissRequest；否则先播放隐藏动画，结束后调用 onDismissRequest。shouldDismissOnBackPress 设为 false 时返回回调不启用，这次返回落到对话框自己的 cancel()（空实现），弹层不关闭、返回也不传给下层页面
- 〔原因〕ArkUI 里用 Stack 条件渲染的遮罩浮层是页面树中的普通组件，不拦截系统返回：浮层可见时按返回，宿主 NavDestination 没有 onBackPressed 的整页出栈；这个 NavDestination 是入口压栈的根页时，出栈后只剩空的 Navigation 外壳，或应用直接退出
- 〔做法第 1 步〕NavDestinationAttribute.onBackPressed(callback: () => boolean): NavDestinationAttribute（首段 @since 10，组件属性，不用导入）：与 Navigation 绑定的导航控制器（路由栈）中存在内容时生效，点击返回键时触发；回调返回 true 表示重写返回键逻辑、页面不出栈，返回 false 表示回退到上一个页面
- 〔做法第 5 步〕自定义组件的 onBackPress?(): void | boolean 只在 @Entry 装饰的 router 页面组件上生效：返回 true 表示页面自行处理返回、不做页面路由，返回 false 或不返回值走默认路由返回；非 @Entry 的自定义组件（如嵌在 NavDestination 或宿主页面里的列表组件）写了 onBackPress 也不会被系统调用
- 〔做法第 5 步〕应用（或该 Activity）没有启用 OnBackInvokedCallback 时，框架 ActionMode（主类型）存在期间，DecorView#superDispatchKeyEvent 对 KEYCODE_BACK 先结束 ActionMode（抬起时 finish）并消费这次返回，不交给 Activity；以对话框弹出的 ContextMenu（MenuDialogHelper）在返回键抬起时关闭菜单并消费这次返回。启用了 OnBackInvokedCallback（清单 enableOnBackInvokedCallback 为 true 等）时，返回键在 ViewRootImpl 进入视图树之前就交给顶层的 OnBackInvokedCallback，不经过上面这两段按键处理
- 〔做法第 5 步〕androidx.activity 的 OnBackPressedDispatcher.onBackPressed 按登记的倒序找第一个已启用的回调，只调用这一个；没有已启用的回调时才走构造时传入的 fallback。activity 1.0.0 与 1.13.0 都是这样，差别在随 LifecycleOwner 登记的回调（addCallback(owner, callback)，Compose 的 BackHandler 也是这种）怎么排：1.11.0 及以前每次 ON_START 重新加入（排到最前）、ON_STOP 移除；1.12.0 起只要应用没有把 ActivityFlags.isOnBackPressedLifecycleOrderMaintained 另设为 false（缺省 true），就在 addCallback 时定下位置，只随生命周期启停。1.13.0 的分发交给 androidx.navigationevent 1.0.0，以 PRIORITY_OVERLAY 登记的处理器排在所有普通回调之前
