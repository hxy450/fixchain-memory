# 用 @Monitor 监听数组路径代替 collect 时，生产方按源端以新数组重新赋值发出变更

## 何时使用

状态模型与 ViewModel 实现阶段，把 StateFlow/Flow 的列表或消息队列迁成 @Trace 数组，并由消费方用 @Monitor 监听数组属性路径时

## 适用情境

源端以 StateFlow.update { list + item } 一类写法每次发射新列表；目标生产方准备原位 push（出队却重新赋值），消费方以 @Monitor('model.items') 一类路径模拟 collect。

## 例外与边界

- 这条只管数组本身的增删（入队、出队）。列表项字段的更新不在内：ForEach 的 key 只含稳定 id、行组件以 @Param 接收整个元素时，已有的「原位修改该项的 @Trace 字段」写法保留，不改成生成新对象再重新赋值数组——同 key 的行不会重建，行内显示会停在旧对象上。
- 消费方 @Monitor 监听的是数组长度路径（如 'model.items.length'）时，push 引起的长度变化能被观测到，不属于这条要改的情形。

## 原因

来源中原位 push 没有触发监听数组路径的 @Monitor，提示永远不出现，重新赋值的出队路径却正常；生产方写法与消费方观察方式不配套时 UI 静默失效。这一点与文档一致：@Monitor 监听数组整体时只能观测到数组整体的赋值，无法监听 push 等 Array API 调用引起的变化。

## 做法

1. 源端以新列表发射事件时，目标也重新赋值新数组（this.items = [...this.items, x]），入队和出队用同一种变更信号；不因 @Trace 数组原位 push 能刷新渲染就改成 push。
2. 消费方用 @Monitor 监听数组路径前先读生产方写法；生产方原位修改时，要求其改为重新赋值；监听数组整体路径的 @Monitor 观测不到 push 等原位修改。

## 可选检查

- 有疑问时触发一次入队，确认消费方回调确实执行、提示出现。
