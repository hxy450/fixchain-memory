# 源端“右列 match_parent 跟随左卡等高”在 Scroll 内用实测高度传递实现，不用估算常量

## 何时使用

界面实现与验证期修复阶段，为并排卡片确定跟随等高约束，而整行位于 Scroll 等纵向无界容器中时

## 适用情境

Android 水平行里右列 height=match_parent 随左侧 wrap_content 卡片等高；整行在 NestedScrollView（ArkUI Scroll）中；目标在 Scroll 内用纵向 layoutWeight 或 height('100%') 会被撑高失控。

## 例外与边界

- onSizeChange 从 API 12 起提供；工程最低兼容版本低于 12 时，改在左卡 onAreaChange 里取新区域的 height 写入状态，做法不变。代码里已用这两种回调之一把左卡量得的高度传给右卡的，保留，不改回常量或百分比。

## 原因

Scroll 内纵向百分比或权重没有上界会被撑高，修复时容易改成按字号行高估算的固定高度；左卡内容高随字体度量与内容变化，常量会与之脱钩，两卡仍不等高。

## 做法

1. 在左卡 onSizeChange((_old: SizeOptions, size: SizeOptions) => …) 中取实测高度写入状态，右卡 height 绑定该状态（首帧用估值兜底）。
2. 派修或验收时把“两卡等高”写成验收条件，不只给出“改成固定高度”这类修法。

## 可选检查

- dumpLayout 比对两卡 bounds 高度一致。

来源支持：1 张卡 · 1 次迁移 · 1 个应用

已核实的平台事实（核实时用的是 HarmonyOS 6.1.0（API 23，SDK 6.1.0.105）；OpenHarmony 文档 master 2026-11-21（提交 e42bd18a）；安卓 android-36.1 的源码。和具体应用无关，直接用，不用再查；其中的默认值只在应用自己的主题、样式、清单和代码没有另设时成立，应用有没有另设要到应用里看）：
- 〔做法第 1 步〕onSizeChange（API 12 起）在布局导致组件尺寸变化时回调，重新渲染引起的渲染属性变化不触发
- 〔适用情境〕安卓 LinearLayout 自身高度不是 EXACTLY 时，量完一遍后用自己测得的高度把 height=match_parent 的子项按 EXACTLY 重新测量一次，所以 match_parent 的右列等于最高子项的高度
- 〔原因〕Scroll 内并排行的右卡用纵向 layoutWeight 或 height('100%') 时被撑到约 730vp，不跟随左卡高度
