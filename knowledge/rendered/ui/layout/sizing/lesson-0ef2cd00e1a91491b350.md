# 源端在整数 px 上取整的布局公式：规格写明运算域，实现在 px 域取整、写入布局属性前再换回 vp

## 何时使用

规格提取阶段，把自定义 Layout、MeasureScope 里的测量与整数几何公式翻成目标契约时；界面实现阶段，用 onAreaChange、measureText 等返回值驱动这类公式时；移植自绘 View 的绘制坐标、setBounds 边界、位移与文字基线修正中的 (int) 强转时

## 适用情境

源算法在约束或测量结果（Compose constraints、placeable 宽高等整数 px）上做整数除法、.toInt() 截断或取整；目标布局属性和尺寸回调（onAreaChange）使用 vp 等逻辑单位，回调值通常不是整数；UIContext.getMeasureUtils().measureText 返回 px，画布 CanvasRenderingContext2D.measureText 的结果与画布坐标同单位（默认 vp）。 也包括 Canvas 绘制代码中的 (int) 强转（setBounds 边界、int 位移、文字基线修正），其中的量可能为负。

## 例外与边界

- 公式本来作用于 Dp 常量（固定间距、固定尺寸），不涉及 constraints 或 placeable 时，按原单位保留；View 体系里经 getDimensionPixelSize / getDimensionPixelOffset 或 XML 布局读入的 dp 尺寸已是整数 px（前者四舍五入、后者截断），对它们做的整数运算仍在 px 域，不属于此例外

## 原因

单位缩放与取整不可交换：保留 floor 等函数名却把输入换成 vp，每次截断的小数按 vp 丢弃，槽宽总和铺不满容器、位置偏移；把 MeasureUtils.measureText 返回的 px 先转 vp 再进公式也改变了运算域。规格把 vp 回调值写成“整数”或把“源端余下 W mod n 空白”按 vp 复述时，错误的等价性声明看起来成立，并传给所有照做的实现者。

## 做法

1. 规格提取：写出公式输入输出的单位、整数或浮点类型、取整位置和换算边界，以源测量代码为准；例如源公式为 Wpx/(n+1) 时，契约写成 u_px = floor(Wpx/(n+1))、供布局使用时 u_vp = px2vp(u_px)，不要写成 floor(Wvp/(n+1))。用例至少放一个非整数 vp 宽与对应 px 宽的对照行。
2. 实现：参数名带单位（如 widthPx）；onAreaChange 的 vp 宽（Area.width 声明为 Length，按 number 取用）和默认 vp 画布上 measureText 的结果先 vp2px，MeasureUtils.measureText 的 px 直接使用，公式在 px 域取整，结果写入 width、translate、position 前再 px2vp。规格把回调值写成“vp、整数”时，先用一个真实回调值核对。
3. Java/Kotlin 的 (int)/toInt() 向零截断，用 Math.trunc；量可能为负（反向位移、扩张时的负边界）时不能换成 Math.floor。视觉验收看不出亚像素差也原样保留，偏移被乘倍使用时误差随之放大。

## 可选检查

- 单位或取整顺序有疑问时，代入一个实测宽度比较两种顺序；能 dump 时核对行总宽是否等于容器 px 宽。

- 〔适用情境 / 做法第 1 步〕Compose 的 Constraints 是父布局给出的像素范围，minWidth、maxWidth、minHeight、maxHeight 都是 Int 像素，不限上限时 maxWidth、maxHeight 为 Constraints.Infinity（Int.MAX_VALUE）；Placeable.width、height 是父布局看到的整数像素宽高，子布局没守约束时被夹进 min–max 约束范围，它自己测出的宽高要读 measuredWidth、measuredHeight
- 〔适用情境 / 做法第 2 步〕onAreaChange 回调给出的 Area.width、Area.height 声明为 Length，文档写明单位为 vp；这个回调只响应布局变化引起的尺寸、位置变化，translate、offset、scale 等绘制属性的变化不触发
- 〔适用情境 / 做法第 2 步〕设备上宽 1320px 的容器，onAreaChange 报的宽是 377.14vp（不是整数）；把 Compose 在整数 px 上做的 W/(n+1) 槽宽公式放到 vp 域 floor（floor(377.14/5)）时，布局 dump 里这一行只到 1313px，右侧留空、整体偏左；同一宽度在 px 域 1320/5=264 正好整除
- 〔适用情境 / 原因 / 做法第 2 步〕UIContext.getMeasureUtils() 得到的 MeasureUtils.measureText(options)（API 12 起）返回文本按单行排版的宽度，单位 px，浮点结果向上取整；options 里的 constraintWidth、maxLines 对它没有影响
- 〔适用情境 / 做法第 2 步〕CanvasRenderingContext2D 的单位模式在构造时由 unit（LengthMetricsUnit，API 12 起）指定：DEFAULT 为 vp、PX 为 px，不传时为 DEFAULT，构造后不能改；Canvas 文档说单位模式影响绘制时的坐标和尺寸计算，而 measureText 返回的 TextMetrics 各字段文档没有单独写单位
- 〔做法第 1、2 步〕UIContext.vp2px(value) 把 vp 值换成 px，UIContext.px2vp(value) 把 px 值换成 vp（API 12 起）
- 〔例外与边界〕Resources.getDimensionPixelSize 把尺寸换成整数像素时四舍五入，非零值至少为 1px（负值至少为 -1px）；getDimensionPixelOffset 直接截断成整数；XML 布局里的 layout_width、layout_height 经 TypedArray.getLayoutDimension 读入，layout_margin*、padding 经 getDimensionPixelSize 读入，都已是四舍五入后的整数 px
- 〔适用情境 / 做法第 3 步〕Drawable.setBounds(int left, int top, int right, int bottom) 的四个边界都是 int，Drawable 在 draw() 时画在这块矩形里
- 〔做法第 3 步〕Java 的整数除法按向零截断取整（Math.floorDiv 的注释：普通整数除法是 round to zero，floorDiv 才向负无穷取整，商为负且不整除时两者不同）；double 到整数的窄化转换直接舍去小数部分（BigDecimal.intValue 的注释以此类比）
- 〔做法第 3 步〕Kotlin 的 Float.toInt()、Double.toInt() 舍去小数部分、向零取整（NaN 得 0，超出 Int 范围取边界值）；Int 的除法 div 截断为更靠近 0 的整数
- 〔做法第 3 步〕ArkTS 的 Math.trunc(x) 去掉小数部分、只留整数部分（向零取整）；Math.floor(x) 取不大于 x 的最大整数，x 为负且不是整数时两者相差 1
