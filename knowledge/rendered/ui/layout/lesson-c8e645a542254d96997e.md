# 源布局（含 include 引入的布局）有 layout-land、layout-sw<N>dp 等变体时逐控件对照，在承载组件内按配置条件分支实现

## 何时使用

页面数据提取与规格阶段登记页面布局来源时；界面实现阶段，合并 layout 与 layout-land、layout-sw<N>dp 等变体，或实现替代带变体 fragment 的共享组件时；计划与派工阶段指派变体实现时

## 适用情境

源 res/layout-land/、layout-sw600dp/ 等目录下有同名变体（也可能是被 <include> 或 setContentView 引入的子布局），控件的 background、weight、margin、textSize、排列方向或整体结构与 base 不同；Activity 代码在运行时只对部分控件 setBackgroundResource；页面元数据的布局来源清单只列 base 文件，或计划写“变体随迁”却未点名文件与负责方；布局由另一任务的共享组件承载，派工只写竖屏结构，横屏要求只出现在资源任务或移交登记里。

## 原因

只按 base 骨架实现，或把运行时覆盖推广到所有控件，横屏或大屏下结构与外观都会偏；ArkUI 没有布局资源限定词，未进入布局来源清单或未点名负责方的变体不会被任何任务实现，资源任务也承接不了布局变体。

## 做法

1. 开写前对每个被替代的源布局及其 <include> 引入的布局 ls res/layout-*/<name>.xml，按 android:id 逐控件 diff 各变体的属性；每个差异写成配置条件分支：-land 按窗口宽 > 高，-sw<N>dp 按设备屏幕短边 min(宽,高) ≥ N vp（与方向无关，不用 mediaquery min-width；Android 取两种方向下可用区宽高的最小值，targetSdk 低于 35 时扣除系统栏等插入区，临界值附近按此核），-w<N>dp 按当前窗口可用宽 ≥ N vp（mediaquery 的宽度条件要写 vp 单位，不写按 px）；或在报告注明被哪段运行时代码覆盖。
2. 先列出运行时 setBackgroundResource/setBackground 实际作用的控件变量，只有这些改用运行时背景，其余控件在每个变体里按该变体 XML 取形状与颜色。
3. 布局由共享组件承载时，把变体路径与差异写进该组件的产出与验收，不只放进资源任务；本任务确实不做时登记带负责方、变体路径与关键值的移交，关闭移交前逐条核对横屏要求。
4. 页面数据提取与计划阶段，把每个布局来源（含 include）的限定符变体连同判定语义记入页面元数据或规格，并点名负责的页面规格或切片；写“随迁”而未点名文件与负责方的视为未分配。

已核实的平台事实（核实时用的是 HarmonyOS 6.1.0（API 23，SDK 6.1.0.105）；安卓 Android SDK 源码 android-36.1；Android SDK 平台资源 android-34、android-36。和具体应用无关，直接用，不用再查；其中的默认值只在应用自己的主题、样式、清单和代码没有另设时成立，应用有没有另设要到应用里看）：
- 〔做法第 1 步〕Android 的 -w<N>dp 比较 Configuration.screenWidthDp（多窗口下是应用窗口的可用宽，不是整块屏幕），-sw<N>dp 比较 smallestScreenWidthDp，即竖屏、横屏两种方向下 screenWidthDp 与 screenHeightDp 中的最小值；targetSdk 低于 35 时这两个宽高都扣除了窗口插入区（系统栏等），targetSdk 不低于 35 时与 WindowMetrics 一致、按最接近的 dp 取整。〔成立范围：对象：资源限定词 -w<N>dp、-sw<N>dp 的判定值。条件：应用 targetSdk 是否不低于 35（VANILLA_ICE_CREAM）。不成立：targetSdk 低于 35 时直接拿物理屏幕短边（如鸿蒙 display 的宽高除以 densityPixels）判 sw，会比 Android 的值大出系统栏那一截，临界值附近会判反。〕
- 〔做法第 1 步〕鸿蒙媒体查询的 width、height、min-width 等指应用页面可绘制区域的宽高，比较时不写单位按 px 算（要按 vp 比必须写 vp）；orientation 是屏幕（设备）方向；device-width 只在应用初始化时保存一次，折叠、展开等变化后不更新。〔成立范围：对象：媒体查询条件串（如 matchMediaSync 的参数）里的媒体特征。条件：依据是文档说明。不成立：在 ArkTS 卡片里只支持 height、width 两个特征。〕
- 〔原因；做法第 1 步〕鸿蒙资源的限定词只有移动国家码和网络码、语言/文字/地区、横竖屏（vertical、horizontal，表示设备屏幕方向）、设备类型、颜色模式和屏幕密度，没有与 Android -sw<N>dp、-w<N>dp 对应的宽度类限定词；资源组目录只有 element、media、profile 三类，没有 Android res/layout 那样随限定词切换的布局资源。〔成立范围：对象：resources 下的限定词目录与资源组目录。条件：目录里的横竖屏、设备类型等取值必须与设备当前状态完全一致才参与匹配。不成立：Android 的方向类 -land/-port 有对应目录 horizontal/vertical，但鸿蒙文档写的是按设备屏幕方向匹配，不是按窗口宽高；-sw、-w、-h 等尺寸类限定词都没有对应。〕
- 〔适用情境；做法第 2 步〕Android 旋转屏幕会同时改变 orientation 和 screenSize 两项配置，默认销毁并重建 Activity、重新 setContentView，此时按新方向选用 layout-land 等变体，onCreate/onPostCreate 里的守卫按新布局重新判断；manifest 的 android:configChanges 同时声明 orientation 与 screenSize 时不重建，只回调 onConfigurationChanged，已有视图树保持旋转前加载的布局变体。〔成立范围：对象：Activity 的布局变体选择，以及基类生命周期里依赖布局的守卫。条件：targetSdk 低于 13（HONEYCOMB_MR2）时 screenSize 变化本身不导致重建；screenSize、smallestScreenSize、screenLayout 这类尺寸配置项只在跨过应用资源限定词的分档时才计入是否重建（依据是 SizeConfigurationBuckets 的注释）。不成立：这次变化里还含没声明的其他配置项时仍会重建、不回调 onConfigurationChanged；声明了 configChanges、但在 onConfigurationChanged 里自己重新 setContentView 的页面，会换成新方向的变体。〕
- 〔适用情境（-land 变体是否会被用到）〕manifest 里 activity 的 android:screenOrientation 锁定为 portrait 等方向时，页面按该方向运行、不随设备旋转进入横屏配置，锁竖屏页面的 layout-land 变体在手机上不会被选用。〔成立范围：对象：在 manifest 中锁定了方向的 activity 及其布局变体。条件：依据是文档说明；厂商也可以配置设备忽略这个属性。不成立：应用 targetSdk 不低于 36（Android 16）时，在最小宽度不小于 600dp 的设备上系统忽略 portrait、landscape、reversePortrait、reverseLandscape、sensorPortrait、sensorLandscape、userPortrait、userLandscape，当作 unspecified，此时 -land 变体照常生效。〕
