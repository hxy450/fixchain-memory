# 源端通知迁到 NotificationRequest：按钮与每次构建用不同 requestCode，正文不给空串，builder 默认图标照填

## 何时使用

实现阶段，把源端通知构造（多个 PendingIntent 动作按钮、可为 null 的 setContentText、helper 里 builder 预设的图标）映射为 wantAgent.getWantAgent 与 NotificationRequest 时

## 适用情境

源端每次构建通知都给按钮取不同的 requestCode（如逐次取 elapsedRealtime），按钮 Intent 载荷随运行状态变化；部分通知（完成通知、没有文本的步骤）contentText 为 null。目标用 WantAgentInfo（wants、operationType、requestCode、wantAgentFlags）与 NotificationBasicContent（title、text）发布。 源端通知 helper 的 builder 先设默认 smallIcon/largeIcon，再由调用方按需覆盖。

## 例外与边界

- 目标代码没有设 smallIcon 不算漏：通知左侧图标由系统自动生成，不需要应用配置；第 3 步要补齐的是会显示出来的源端默认值，主要是右侧的 largeIcon。content 用图片型内容（NotificationPictureContent）时 largeIcon 设了也不生效，不必为它补。

## 原因

多个按钮或多次构建共用同一 requestCode、又不设刷新标志时，同一 Want 对应的 WantAgent 可能沿用旧参数，按钮触发的动作与当前状态不符。NotificationBasicContent.text 的声明注释写明内容不可为空，只看签名 text: string 会以为空串可用。这两点来自 SDK 注释与源码对照，来源材料中没有设备上的发布失败日志，也没有按钮串载的复现。

## 做法

1. 每个按钮、每次构建分配不同的 requestCode（递增计数，或沿用源端的取值方式）；需要刷新载荷时，在 actionFlags 加 UPDATE_PRESENT_FLAG（wantAgentFlags 自 API 11 起废弃，由 actionFlags 替代）。
2. 源端正文可为 null 时按“不可为空”处理：用不可见占位字符（如零宽空格），或改用不依赖空正文的内容形态；完成通知和各类无正文的通知分别核对。
3. 源端通知 helper 在 builder 上预设的字段（smallIcon、默认 largeIcon 等）也是通知契约：封装里先按源默认值填齐（资源解码为 PixelMap 后设入 NotificationRequest 的 smallIcon/largeIcon），调用方提供时再覆盖（如附件缩略图）。

已核实的平台事实（核实时用的是 HarmonyOS 6.1.0（API 23，SDK 6.1.0.105）；OpenHarmony 文档 master 2026-11-21（提交 e42bd18a）；安卓 不涉及。和具体应用无关，直接用，不用再查；其中的默认值只在应用自己的主题、样式、清单和代码没有另设时成立，应用有没有另设要到应用里看）：
- 〔原因 / 做法第 1 步〕两个 WantAgent 实例由同一应用用相同的 WantAgentInfo 创建且未被 cancel 时视为相等；通知更新时会比较新旧通知里的 WantAgent，不相等时删除旧通知的 WantAgent 实例
- 〔做法第 1 步〕WantAgentFlags.UPDATE_PRESENT_FLAG：用新 WantAgent 的额外数据替换已存在的 WantAgent 中的额外数据；WantAgentInfo 的 actionFlags（及已废弃的 wantAgentFlags）不设置时没有执行属性
- 〔原因 / 做法第 2 步〕NotificationBasicContent.text 不能为空，超过 3072 字节的部分被截断；title 同样不能为空，超过 1024 字节截断
- 〔做法第 3 步〕NotificationRequest 的 smallIcon、largeIcon 是可选的 PixelMap，图标像素字节总数（getPixelBytesNumber）不能超过 192 KB，建议 128 px × 128 px
