# 源端拉起系统能力前的可用性预检、权限申请与无接收方回退逐段落成目标显式步骤，不用 pick/startAbility 的 catch 代替

## 何时使用

规格提取与服务层实现阶段，把源端拉起相机、外部应用或隐式 Intent 前的能力检查、权限申请与失败回退翻译为目标契约和代码时

## 适用情境

源方法在 startActivity 或拍照前先用 IntentChecker.isAvailable、PackageManager.hasSystemFeature、resolveActivity 判可用，经权限工具申请运行时权限，无接收方时走回退（如 geo: 打不开改走网页地图）或提示；目标用 cameraPicker、startAbility/openLink 的隐式 Want 等实现，参考样例只给“调用 + catch”。目标改用 cameraPicker 这类由用户在系统界面确认的 picker 时，平台不要求应用申请相机权限；源端的权限申请与拒绝分支这时不是第 1 步的必做段，按第 4 步在规格里写明取舍，预检与回退两段仍要落成显式步骤。

## 原因

catch 只覆盖调用失败，替代不了源端拉起前的分支：能力缺失提示、权限拒绝时不创建文件、无接收方时换路径都会丢失。隐式 Want 不预检时，系统可能弹出选择框，不含 // 的 URI（mailto:、geo:）还可能按推断的类型匹配到意外接收方（含本应用），失败不一定以异常返回。规格只留一个分类函数、不给探测与动作的目标符号时，实现者会把探测推给通用 openLink。

## 做法

1. 对照源方法逐段列出“预检 → 权限 → 拉起 → 结果/回退”，每段写出目标符号：能力预检用 canIUse 或对应能力查询；权限在 module.json5 声明并以 abilityAccessCtrl 的 requestPermissionsFromUser 申请，保留拒绝分支；拉起与结果按源分支实现。缺任一段即为未完成。
2. 隐式 Want 拉起外部应用（geo:、mailto:、tel: 等）前用 bundleManager.canOpenLink 探测，并在 module.json5 的 querySchemes 登记所查 scheme；无接收方时走源端的回退或提示分支，不依赖 startAbility 抛错。
3. 规格把源 helper 翻成服务契约时，为源方法里的每个动作（如 ACTION_SENDTO、ACTION_DIAL）与可用性探测各给一个目标符号，不只留 scheme 分类函数。
4. 目标 API 在 d.ts 中不标 @permission、源端却有权限申请与拒绝分支时，在规格写明是否保留申请流程及其对拒绝分支的影响，不静默删除这段可观察流程。

已核实的平台事实（核实时用的是 HarmonyOS 6.1.0（API 23，SDK 6.1.0.105）；OpenHarmony 文档 master 2026-11-21（提交 e42bd18a）；安卓 不涉及。和具体应用无关，直接用，不用再查；其中的默认值只在应用自己的主题、样式、清单和代码没有另设时成立，应用有没有另设要到应用里看）：
- 〔做法第 1、4 步〕cameraPicker.pick 的系统能力是 SystemCapability.Multimedia.Camera.Core；应用调用 CameraPicker 拍照或录像时由用户主动确认，不需要申请相机权限，声明里也没有 @permission
- 〔做法第 2 步〕bundleManager.canOpenLink 能打开链接时返回 true，否则返回 false；链接的 scheme 没有登记在 module.json5 的 querySchemes 里时抛 BusinessError 17700056
- 〔做法第 2 步〕querySchemes 只允许 entry 类型模块配置，每项不超过 128 字节；API 21 起最多 200 个 URL scheme，API 20 及之前最多 50 个
- 〔原因〕隐式 Want 的 uri 不为空、type 为空时，若 skills 的 uri 匹配都失败而传入的是文件路径 uri，系统按文件后缀取 MIME 类型再去匹配 skills 里配置的 type
- 〔做法第 2、3 步〕官方文档从应用拉起邮件应用的写法是 startAbility 传 action 'ohos.want.action.sendToData' 和 uri 'mailto:…'
- 〔原因〕HarmonyOS API 24 设备上，不预检直接隐式拉起 geo: 链接时弹出系统选择框；隐式拉起不带 // 的 mailto: 链接时匹配到了调用方应用自己
