# 源端靠依赖注入或全局静态工具就绪的基础设施改成需显式 init 的封装后，在入口 onCreate 最早处调用，并确认启动期读写都晚于初始化

## 何时使用

网络、键值存储等基础设施实现与入口接线阶段：新建必须先 init 才能用的封装，或改写 EntryAbility.onCreate、宣告基础层完成时

## 适用情境

源端网络 baseUrl 由 DI 模块在注入时带上、键值工具（SpUtils/MMKV 一类）全局静态可用，Application.onCreate 里看不到对应的初始化；目标端改为静态 HttpClient（baseUrl 默认空串）加 NetworkConfig.init()、偏好封装需先传入上下文；入口 Ability 由编排会话维护，Flutter 插件 onAttachedToEngine 等回调里也能拿到上下文。也包括网络层以静态运行期配置承接构建期注入值（configure 写入、未配置即 throw），基础模块不得改入口，启动接线者不知道这条调用义务。也包括源端数据层每次读写都无条件调用的能力（加解密等），目标由基座在 DAO 留 setter 注入接缝并配恒等或空实现默认值，实现由后续切片注入。

## 原因

迁移把“注入即就绪”改成“调用 init 才就绪”，调用义务是新产生的，源端没有可对照的调用点。实现者写了 init 却不接入口，或把唯一的 init 放进较晚的回调、只在某个业务单例首次取用时才执行，启动期的请求和读写就会拿到空 baseUrl、空偏好或未注入的钩子；这类封装在未初始化时常静默返回默认值，表象是网络错误或数据丢失，恒等加解密默认值还会让密文与明文混写。实现者回报“无待接线项”或把占位改成“已兑现”注释后，后续接线者照此认定已完成，不再追问冷启路径。

## 做法

1. 新建需显式 init 的封装时，在同一任务里把调用写进 UIAbility.onCreate（或 AbilityStage.onCreate），早于任何请求和读写；派工不许改入口文件时，在回报里单列待接线项，写明文件、生命周期方法和调用语句。
2. 列出启动期所有读写方（入口里的网络初始化、闪屏的状态恢复、通道回调等），逐个确认晚于初始化；写冷启动即发请求的流程前先确认这一点，以后在 onCreate 新增读写方时再核一次。
3. 未初始化就被调用时抛出或打出明确的错误日志（例如 baseUrl 为空时报“网络层未初始化”），不静默返回默认值，也不把相对路径交给 http.request；注入接缝的恒等或空实现默认值会造成静默写坏时（如加解密钩子未注入即读写），调用方在未注入时显式失败，或在批量读写任务开始前先确保注入。
4. 宣告基础层完成或改写 onCreate 前，grep 各 init 与 setXxxHook 的调用点，确认命中入口 onCreate；只命中业务服务（如环境切换）或业务单例的首次取用（getInstance）时，按未接线处理，在入口启动序列补显式注入。
5. 启动入口接线时列出基础层所有带缺失即抛错守卫的静态 configure/init（检索 static configure(、static init(、configuration is missing 等），逐一确认已在 onCreate 或启动编排中调用，再宣布启动链闭合。

- 〔做法第 1 步〕UIAbility.onCreate 和 AbilityStage.onCreate 都是同步回调，系统不等待其中的异步操作：把 init 写成 async 在 onCreate 里调用而不等待，或把 onCreate 写成 async 再 await，onCreate 都会先返回，系统随即继续 onWindowStageCreate 和其中 loadContent 加载的页面，此时 init 可能还没完成。〔成立范围：对象：Stage 模型的 UIAbility.onCreate、AbilityStage.onCreate（声明返回 void，注释写明同步返回、不支持异步回调）。对照：UIAbility.onDestroy 声明为 void | Promise<void>，注释说明可借返回的 Promise 让后续生命周期等它完成。依据是 SDK 声明注释，实现里看不到。最常见的不成立情形：读写方自己先等待同一个 init Promise（封装把未完成的 init Promise 存下、每次读写前先 await 它），这时先后由封装保证。〕
- 〔做法第 1 步〕AbilityStage.onCreate 在所属 HAP 的第一个组件实例（UIAbility 或 ExtensionAbility）创建之前执行，早于 UIAbility.onCreate；DevEco Studio 默认工程不生成 AbilityStage，要在 module.json5 的 srcEntry 指向自建的 AbilityStage 文件，它才会作为该 HAP 的加载入口。〔成立范围：对象：Module 级的 AbilityStage，按 Module 一一对应，HAP（entry / feature）和 HSP 首次加载时各创建一个实例（API 参考）。条件：ExtensionAbility 的第一个实例创建前也会执行（ExtensionAbility 默认在独立进程，见下一条）。依据是文档说明。最常见的不成立情形：只新建了 AbilityStage 类、module.json5 没写 srcEntry。〕
- 〔做法第 2 步〕应用的 ExtensionAbility（如 FormExtensionAbility）默认按类型运行在与 UIAbility 主进程分开的独立进程里；那个进程不执行 UIAbility.onCreate，主进程里初始化过的静态封装在那里仍是未初始化状态。〔成立范围：对象：三方应用的 ExtensionAbility。例外：ServiceExtensionAbility、DataShareExtensionAbility（仅系统应用）与所有 UIAbility 同在主进程；UIExtensionAbility 及其子类、AppServiceExtensionAbility 可用 module.json5 的 extensionProcessMode 配进程模式。依据是文档说明。最常见的不成立情形：应用没有 ExtensionAbility，启动期读写方都在主进程。〕
- 〔适用情境〕安卓应用进程启动时先安装 ContentProvider 并执行其 onCreate，再调用 Application.onCreate；库可借 provider 自动初始化（如 androidx.startup 的 InitializationProvider 在 onCreate 里调用 AppInitializer.discoverAndInitialize），所以 Application.onCreate 里看不到 init 调用，不代表源端没有初始化步骤。〔成立范围：对象：安卓应用进程冷启动（ActivityThread.handleBindApplication 先 installContentProviders，后 callApplicationOnCreate；Application.onCreate 的注释写明此时 activity、service、receiver 尚未创建，content provider 除外）。例外：受限备份模式下不安装 provider（源码注释）；Android 7.0 起的直接启动模式下，用户解锁前非 directBootAware 的 provider 不运行（Application.onCreate 注释）。最常见的不成立情形：库要求应用在 Application.onCreate 里显式调用 init，那时调用点就在 Application 里。〕
