# 源端返回栈靠框架在进程回收后重建（rememberNavController、savedInstanceState、Activity 任务栈）时，规格单列“回收后重建”分支：只在系统回收后恢复整栈并保留各页原参数，强停、划掉、覆盖安装后按冷启分流；目标显式开启 UIAbility 恢复与 Navigation recoverable

## 何时使用

规格提取阶段为宿主 Activity 生命周期与导航容器编写验收项、为“进程回收后重建”铸平台差异决策时；入口装配阶段实现 UIAbility 与根 Navigation 的恢复路由时

## 适用情境

源 Activity 在 onCreate(savedInstanceState) 接收存档，或用 Compose rememberNavController + NavHost（以及 Fragment 返回栈）承载页面；源码里没有显式保存代码，进程在后台被系统回收后，返回栈与路由参数由框架恢复。也包括 View 体系的 Activity 任务栈（TaskStackBuilder 建出 [主页, X]、页面参数来自 Intent extra）：只有进程被系统回收而任务仍在时框架才重建整栈，重建页拿原始 Intent；强停、从最近任务划掉、覆盖安装、崩溃后任务已清空，再启动走启动页分流。定要恢复哪些页前先看源端清单：声明 android:noHistory 的 Activity 离开即被 finish，不在被重建的栈里；任务根 Activity 声明 android:clearTaskOnLaunch 时，从桌面图标重新进入会把任务清回根页，这条路径也不恢复内页。目标为 UIAbility + Navigation/NavDestination + NavPathStack，页面栈恢复默认不开启；规格可能只写“冷启进入起始页”，或把回收重入合并进每次冷启动。

## 原因

rememberNavController/NavHost、savedInstanceState 与任务栈重建让源应用在后台回收后回到原页面和参数，这是不靠显式代码的用户可见行为；把带存档的重建入口收窄成冷启，目标回收后只会回到起始页。反过来，把“回收后重入”扩成每次冷启都恢复、只恢复最后一页并凭记忆改写参数，强停后再启动会直接进内页、返回露出空白宿主，续局参数也与源端不同（另一来源实测强停与覆盖安装的退出原因分别为 NORMAL、UPGRADE）。来源修复中只开 setRestoreEnabled 与 recoverable 时，APP_RECOVERY 拉起后仍未恢复，补 restoreWindowStage 后才生效。开启恢复后路由参数经序列化还原为同形普通对象，按类实例判断参数的接收端会失效。

## 做法

1. 规格提取时，源宿主用 rememberNavController/NavHost、在 onCreate 接收 savedInstanceState，或依赖任务栈重建，就在生命周期/导航节单列“进程回收后重建”分支：写明要恢复哪些返回栈页面与路由参数、计时等进行中的会话如何接续，以及目标平台的对应决策；不只写“冷启进入起始页”。
2. 铸恢复决策时把触发条件写成“仅系统回收进程且任务仍在”：目标在 EntryAbility.onCreate 按 launchParam.lastExitReason（PERFORMANCE_CONTROL、RESOURCE_CONTROL）或恢复启动标记判定，其余冷启按启动分流；恢复启动标记在 API 26 之前不单看 launchReason APP_RECOVERY，要同时看 want.parameters 里系统合入的 ohos.ability.params.abilityRecoveryRestart（恢复启动时为 true）；恢复时按源端任务栈恢复整栈并保留每页入栈时的参数（写“原始 Intent 值”前对照已读的 putExtra 逐项核对），不只恢复最后一页、不改写参数。
3. 需要页面栈恢复时（来源在 API 24 SDK 上实现）：EntryAbility.onCreate 调用 context.setRestoreEnabled(true)；launchReason 为 AbilityConstant.LaunchReason.APP_RECOVERY 时调用 context.restoreWindowStage(new LocalStorage())，并实现 onWindowStageRestore 加载同一入口页；根 Navigation 设 id 与 recoverable(true)，每个 NavDestination 设 recoverable(true)；自行持久化路由栈时同样持久化整栈。
4. 可恢复页面的路由参数只用可序列化的普通字段，接收端按字段结构识别（如 typeof recipeId === 'number'），不用 instanceof 判断参数类实例。

## 可选检查

- 对恢复链路有疑问时：进入内页后让应用进程在后台被回收再重新进入，确认页面栈与参数都已还原；再分别 aa force-stop 与覆盖安装后启动，核对退出原因并确认走冷启分流、不恢复。来源修复期曾以 aa force-stop 后重启触发 APP_RECOVERY 来验证恢复代码路径，这只用于验证代码，不代表源端强停后会恢复。

来源支持：2 张卡 · 2 次迁移 · 2 个应用

已核实的平台事实（核实时用的是 HarmonyOS 6.1.0（API 23，SDK 6.1.0.105）；OpenHarmony 文档 master 2026-11-21（提交 e42bd18a）；安卓 android-36.1 的源码。和具体应用无关，直接用，不用再查；其中的默认值只在应用自己的主题、样式、清单和代码没有另设时成立，应用有没有另设要到应用里看）：
- 〔原因 / 做法第 1、2 步〕启用 UIAbility 备份恢复后，应用在后台被系统关闭，下次启动时恢复先前的页面栈和 onSaveState 里保存的数据；应用正常关闭时不触发备份，正常启动（startAbility 或点图标）时不触发恢复
- 〔适用情境 / 做法第 3 步〕UIAbilityContext.setRestoreEnabled 是 UIAbility 级备份恢复的总开关，应用没有调用时默认不开启，系统不保存也不恢复任何数据；它要在应用初始化阶段（onForeground 之前，比如 UIAbility 的 onCreate）调用
- 〔适用情境 / 做法第 3 步〕备份恢复依赖任务保留：应用设置 removeMissionAfterTerminate 为 true，或设备不支持任务保留（如 PC/2in1）时备份恢复不生效；UIExtensionAbility 不支持备份恢复；备份数据默认保存 7 天，过期自动删除
- 〔做法第 3 步〕Navigation.recoverable 默认 false，不开启时该 Navigation 的页面栈不参与恢复；开启它必须同时给 Navigation 设置 id，系统按 id 匹配并恢复对应的导航组件
- 〔做法第 3 步〕NavDestination.recoverable 要配合所属 Navigation 的 recoverable 使用；它的默认值两处说法不同：文档 master 写默认 true（Navigation 开启后未显式设置的子页面全部参与恢复），本机 API 23 的声明注释写默认 false；行为默认值以文档为准，显式设置为 true 或 false 时两种说法下结果一致
- 〔原因 / 做法第 4 步〕系统恢复页面时只恢复页面结构与启动参数；不可序列化的信息（不可序列化的参数、用户设置的 onPop 等）在恢复中被丢弃，没做参数为空降级的页面恢复后参数为空，表现为白屏
- 〔做法第 2 步〕LaunchReason.APP_RECOVERY 表示应用从故障中恢复时被自动拉起；文档写明 API 26.0.0 之前的系统里 launchReason 不能单独作为恢复启动的判据（API 26 起可单独成立，超出本机 SDK 的 API 23），全版本可靠的是系统在恢复启动时合入 want.parameters 的 ohos.ability.params.abilityRecoveryRestart（值为 true）
- 〔做法第 2 步〕LastExitReason 的含义：NORMAL（2）是用户关闭应用正常退出，PERFORMANCE_CONTROL（6）是系统性能问题（如设备内存不足）导致退出，RESOURCE_CONTROL（7）是不当使用系统资源（CPU 高负载、内存超阈值、系统低内存等）导致退出，UPGRADE（8）是因更新退出
- 〔原因 / 做法第 2 步〕设备上 aa force-stop 强停之后重新启动，launchParam.lastExitReason 为 NORMAL；覆盖安装之后重新启动为 UPGRADE
- 〔原因 / 做法第 3 步〕UIAbility.onWindowStageRestore 的声明注释写的是多实例 UIAbility 迁移时恢复 WindowStage 的回调；HarmonyOS API 24 设备上，只开 setRestoreEnabled 与 Navigation、NavDestination 的 recoverable 时，APP_RECOVERY 拉起后页面栈没有恢复，同时在 APP_RECOVERY 时调用 restoreWindowStage(new LocalStorage()) 并实现 onWindowStageRestore 的配置下页面栈得到恢复
- 〔适用情境〕安卓 TaskStackBuilder.addNextIntentWithParentStack 先把目标 Activity 在 manifest 里声明的父 Activity 链加入合成的任务栈，再加入这个 Intent，栈里是整条 [父…, 目标] 而不是单页
- 〔适用情境 / 做法第 2 步〕安卓进程被系统回收而任务仍在时，重建的 Activity 拿到的是入栈时的原始 Intent（含原 extras）；新进程里应用的静态字段回到缺省值
