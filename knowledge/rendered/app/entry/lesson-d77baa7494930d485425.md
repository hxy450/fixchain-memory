# 深链 intent-filter 迁移时声明 module.json5 skills（App Links 加 domainVerify），用隐式 Want 验收

## 何时使用

入口与导航接线阶段，把源端 Activity 的 VIEW/BROWSABLE intent-filter 迁成 UIAbility 的 Want 接收与路由解析时；以及规格提取阶段描述深链映射时

## 适用情境

源 AndroidManifest 在启动 Activity 上声明 VIEW+BROWSABLE、http/https 与固定 host 的 intent-filter；目标 module.json5 的入口 Ability skills 仍是脚手架默认的 HOME 一项。 也包括 intent-filter 带 android:autoVerify="true"（App Links），或决策写明 https 由域名校验的 App Linking 承载。也包括导航图 navDeepLink 的 uriPattern 或分享/复制链接由常量拼接（如 "$baseUrl/item/{id}"），深链规格的源码锚点没有列入 AndroidManifest。也包括 scheme 常量定义在外部库里、仓库内看不到取值。

## 原因

只在 onCreate/onNewWant 里解析 want.uri，系统不会把外部链接路由到该 Ability；用 aa start -b/-a 显式拉起会绕过 skills 匹配，把缺声明误判为通过。来源中实现者读到了 Manifest 与深链清单，只写了解析代码；派生规格也只写“启动后解析 URL”；验证用显式启动把这条验收判为通过。带 autoVerify 的链接还要在承载 https 的 skill 中声明 domainVerify；把它与 AGC 域名关联、服务器校验文件一起推到部署期，应用侧声明就缺了这一项，只核 uris 条数的验收拦不住。规格未展开 uriPattern 中的常量、又不以 intent-filter 为依据时，会写出源中不存在的自定义 scheme 并漏掉源中声明的 scheme（如 http），下游按规格注册多余入口、缺少真实入口。

## 做法

1. 把 intent-filter 的 action、category、data 映射到同一 Ability 的 skills：actions 加 ohos.want.action.viewData，entities 加 entity.system.browsable，每个 scheme 一条 uris（scheme、host、pathStartWith 或 pathRegex）；与 want.uri 解析在同一步完成。源 intent-filter 带 autoVerify="true" 或决策要求 App Linking 时，在承载 https 的 skill 中同时写 "domainVerify": true；AGC 域名关联与服务器端校验文件属于部署期，domainVerify 属于应用侧声明。
2. 应用内解析按源端 uriPattern 锚定 scheme、host、路径段和参数类型，不匹配时清空待处理状态。
3. 验收用隐式 Want：aa start -A ohos.want.action.viewData -U <url>，不带 -b/-a，或从外部应用点击链接。
4. 规格描述深链时同时写平台声明（skills.uris，App Links 另写 domainVerify）与运行时解析两部分，并把 AndroidManifest 的 intent-filter 列入锚点：scheme（如 http 与 https 各一项）、host、path 与 autoVerify 只取自 intent-filter；uriPattern 或分享链接由常量拼接时展开常量写出完整 URI；常量来自外部库时按依赖坐标取库源码或字节码核实取值，仍取不到就保留原表达式，在规格写明该 URI 值域未知及其对 skills.uris 的影响，并按 intent-filter 声明的 scheme 前缀匹配（scheme 后不一定带 //，如 hashtag:），不自拟 scheme 或格式。核验时把源 intent-filter 的属性逐项对到 skill 字段（action→actions、BROWSABLE→entities、data→uris、autoVerify→domainVerify）。

已核实的平台事实（核实时用的是 HarmonyOS 6.1.0（API 23，SDK 6.1.0.105）；OpenHarmony 文档 master 2026-11-21（提交 e42bd18a）；安卓 android-36 与 android-37.0 的平台资源；android-36.1 的源码。和具体应用无关，直接用，不用再查；其中的默认值只在应用自己的主题、样式、清单和代码没有另设时成立，应用有没有另设要到应用里看）：
- 〔原因 / 做法第 1 步〕Deep Linking 基于隐式 Want 匹配里的 uri 匹配来查询、拉起目标应用：只在 onCreate、onNewWant 里解析 want.uri 而 skills 里没有能匹配的 uris 时，外部链接不会路由到这个 UIAbility
- 〔做法第 1 步〕skills 下默认的那个 skill 对象（entity.system.home、ohos.want.action.home）用于标识应用入口，跳转链接不能配在它里面，要新建独立的 skill 对象；有多个跳转场景时各建一个 skill 对象，否则配置无法生效
- 〔做法第 1 步〕深链 skill 的 actions 不能为空，actions 为空会造成目标方匹配失败
- 〔做法第 1 步〕App Linking 声明关联域名的 skill 要同时满足：actions 含 ohos.want.action.viewData，entities 含 entity.system.browsable，uris 含 scheme 为 https 且 host 为域名的元素，并把 domainVerify 设为 true
- 〔原因 / 做法第 1、4 步〕skills 的 domainVerify 可缺省，缺省值 false（不开启域名校验）；App Linking 是在 Deep Linking 基础上增加域名校验环节，同一 HTTPS 网址在应用已安装时优先打开应用、未安装时由浏览器打开网页
- 〔做法第 1、4 步〕uris 的 scheme 只在仅配置 type 时可缺省，否则必填；host 只在配置了 scheme 时生效；port 以及 path、pathStartWith、pathRegex（三选一，分别是全匹配、前缀匹配、正则匹配）只在 scheme 和 host 都配置时生效；从 API 18 起 scheme、host 参与隐式 Want 匹配时不区分大小写
- 〔做法第 1、4 步〕uris 里 scheme、host 等字符串标签不支持用资源索引（$string）配置，只能写字面量
- 〔做法第 4 步〕安卓 intent-filter 的 data 里，android:path 要求路径完全匹配，pathPrefix 要求前缀匹配，pathPattern 是简单通配模式（不是正则），另有 pathAdvancedPattern、pathSuffix
- 〔适用情境 / 做法第 1、4 步〕安卓 intent-filter 的 android:autoVerify 只在 action 为 ACTION_VIEW、category 为 CATEGORY_BROWSABLE、data scheme 为 http 或 https 时起作用，为 true 时用 data 里的 URI 逐个向主机发 HTTPS 请求做站点校验
- 〔做法第 4 步〕安卓 opaque URI（如 mailto:nobody@google.com）的 scheme-specific part 不能以 / 开头，形如 scheme:xxx，scheme 后没有 //
- 〔做法第 3 步〕aa start 隐式启动用 -U <URI>、-A <action>、-e <entity> 等参数；成功时打印 start ability successfully.，失败时打印 error: failed to start ability. 并带失败信息，隐式启动找不到匹配应用时错误码为 10103101
- 〔原因 / 做法第 3 步〕设备上用 aa start -b/-a 显式拉起不经过 skills 匹配，module.json5 缺少深链 skills 声明时页面也能被打开
- 〔做法第 2 步〕UIAbility 冷启动时链接随 want 进 onCreate；实例已创建、再次被拉起时链接随 want 进 onNewWant
