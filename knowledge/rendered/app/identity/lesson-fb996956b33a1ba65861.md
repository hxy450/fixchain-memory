# 沿用脚手架 bundleName/vendor 前核对所引部署期决策与签名配置：查不到就按源包名写入，vendor 按源端落地

## 何时使用

资源前置阶段落地应用身份字段、执行编排为该步骤撰写派工、决定 bundleName 与 vendor 是否替换脚手架值时；规格/决策阶段登记模板身份技术项时；以及维护流水线里身份规则与验证门的口径时

## 适用情境

AppScope/app.json5 仍是 com.example.* 包名与 example 厂商，源 build.gradle 给出真实 applicationId；执行规则或身份技能的受限范围（如只写显示名与版本的开发期身份）要求这一阶段把包名、厂商一并留到部署期决策，而验证门对 com.example.* 包名或 vendor=example 判失败。源 applicationId 本身也可能位于 com.example.* 下（教学或示例工程）。源工程有 productFlavors 时，applicationId 按派工或台账选定的那个变体解析（该 flavor 自己写的 applicationId 覆盖 defaultConfig 的值），不在各 flavor 之间混取。 也包括编排者自己写了“bundleName 对齐源 package”的台账技术项，执行规则或身份技能的开发期范围仍引用台账里不存在的部署期决策编号要求跳过，身份步骤只写了版本号。

## 例外与边界

- 工程已有签名配置，或决策台账里确有已批准的部署期身份决策；这只影响 bundleName，且即使延后也不保留通用脚手架名 com.example.myapplication，至少换成由源包名派生的唯一值；vendor 不参与签名，仍按源端落地

## 原因

规则以“部署期决策、签名一致性”为由保留脚手架值，但工程台账里没有该决策、签名配置为空、流水线也没有后续落地步骤，而验证门对模板值直接判失败。vendor 只描述厂商，不参与签名与 profile 校验，与 bundleName 并列延后没有依据。来源中资源阶段 worker 读到了 applicationId，仍按规则保留脚手架值；其他应用里身份技能以开发期范围跳过 vendor（所引台账编号在该工程并非身份决策），执行者照做，验证门判 FAIL，修复只改 vendor 后签名包仍能正常安装。源 applicationId 本身在 com.example.* 下时，忠实映射出的包名和 example 组织段同样会被字面规则判失败；例外不提前登记，就只能在验证期临时裁决。通用脚手架包名在共享设备或模拟器上可能已被其他应用占用，包名修好前产物根本无法安装，不只是验证门判失败。另一应用中身份步骤以开发期范围跳过 bundleName，阶段报告与终报仍称“身份已落地”。

## 做法

1. 保留前在决策台账查规则所引的决策编号（台账里查不到，或同编号指向的是其他事项，都不是已批准的身份决策），同时看台账是否已有“迁移真实身份”的技术项、build-profile.json5 的 signingConfigs 是否为空；编排者自己写过要求替换的台账技术项、而执行规则引用的编号查不到时，以台账为准，身份技能调用参数不写“不碰 bundleName”，派工不把该项拆成只落开发期字段后记为完成；决策不存在、签名为空时，按源端 applicationId 映射 bundleName 与 vendor，或在迁移报告登记“包名/厂商待定、验证门会判失败”的决策缺口并把相关技术项标为未完成，不静默沿用脚手架值。
2. 区分签名绑定字段与描述字段：bundleName 随签名 profile 绑定，可按决策延后；vendor 在开发期就从源端取值（applicationId/namespace 的组织段，或源工程 README、仓库所属的作者或组织），不因 bundleName 延后而一并保留 example。
3. 维护流水线时，让“部署期再落地”的跳过规则与验证门一致：身份规则跳过某字段前逐项比对验证门的模板默认值规则（如 vendor=example、bundleName 匹配 com.example.* 判失败），冲突时在输出中指出；进入验证前安排落地步骤，或让验证门对已登记延后的字段给出 DEFERRED。
4. 源 applicationId 本身位于 com.example.*、组织段为 example 时，仍按源值映射（这是源端真实身份，不是脚手架残留）；在规格/决策阶段登记模板身份技术项时写明由哪个阶段以何种范围写 bundleName/vendor，并同时登记验证门的 com.example.* 例外，不留到验证期才发现规则字面必然判失败。
5. 需要包名的代码运行时从上下文读取 bundleName（如 context.abilityInfo.bundleName），不写字面量常量，也不跨文件复制别处的包名常量；module.json5 的 uris host、快捷方式 wants.bundleName 等只能写字面量的配置，写入前确认 app.json5 的 bundleName 已是最终值，仍是模板值时连同这些位置一起登记，由身份落地步骤回填。落地后检索残留的旧包名（如 com.example）。
6. 身份步骤写完读回 app.json5，与台账技术项逐字段比对；未落实的项在阶段报告与终报标为未完成并写明原因，不以“身份已落地”收口。
7. 按源 applicationId 写 bundleName 时，若源包名只有两段（如 com.x），而构建校验要求至少三段，做最小扩展（如 com.x.app），vendor 仍取组织段，并在决策中记录这一扩展。

已核实的平台事实（核实时用的是 HarmonyOS 6.1.0（API 23，SDK 6.1.0.105）；OpenHarmony 文档 master 2026-11-21（提交 e42bd18a）；安卓 不涉及。和具体应用无关，直接用，不用再查；其中的默认值只在应用自己的主题、样式、清单和代码没有另设时成立，应用有没有另设要到应用里看）：
- 〔适用情境 / 做法第 2、4、7 步〕app.json5 的 bundleName 标识应用的唯一性，不可缺省：必须是点号分隔、至少三段的字符串，每段只允许英文字母、数字、下划线；首段以字母开头，非首段以数字或字母开头，每段以数字或字母结尾；不允许连续的点号；长度 7–128 字节；推荐反域名形式（第一级域名后缀，第二级厂商或个人名，第三级应用名）
- 〔原因 / 做法第 2 步〕app.json5 的 vendor 是对应用开发厂商的描述，取值不超过 255 字节，可缺省，缺省值为空，可用于在关于页面等处展示开发厂商信息；文档的配置示例里写的是 "vendor": "example"
- 〔原因 / 例外与边界〕设备上已装应用与新装应用包名相同而签名不一致时（签名密钥和 Profile 里的 app-identifier 都不同），安装报 9568332 install sign info inconsistent；应用卸载但保留了数据时，再装同包名应用同样要校验签名一致
- 〔原因〕共享模拟器上已有别的应用占用通用脚手架包名 com.example.myapplication 时，用这个包名签名的迁移产物装不上
- 〔原因 / 做法第 2 步〕只改 app.json5 的 vendor、bundleName 与签名配置不动时，签名全量构建通过，重建的签名 HAP 照常安装，没有出现签名不一致
- 〔做法第 5 步〕module.json5 skills 的 uris 里 scheme、host 等字符串标签不支持用资源索引配置，host 只在配置了 scheme 时生效；快捷方式 wants 里的 bundleName 是快捷方式的目标包名，同样是写在配置里的字符串
