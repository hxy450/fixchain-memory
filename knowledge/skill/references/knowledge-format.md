# 知识文件的格式

一条经验一个文件 `lesson-<完整经验号>.json`，UTF-8，`ensure_ascii=False`，缩进 1。进经验库时放 `knowledge/lessons/`。

经验库仓库的 `knowledge/lessons/` 里还有两种旧格式的文件（第三版规则：同样的顶层键，`sdk` 只有 `harmony`、`android`；第七版规则：顶层用 `lesson` 键、条目多一栏 `scope`，规则见 `knowledge/RULES-v7.md`）。新写的一律用下面的新格式；仓库的 `knowledge/check.py`、`knowledge/render.py` 按「没有 `lesson` 键、`sdk` 里有 `verified_on` / `docs_commit` / `docs_date`」认新格式。

## 1 最终文件（交出去、进库的那份）

```json
{
 "id": "lesson-<20 位>",
 "sdk": {"verified_on": "核实日期 YYYY-MM-DD", "docs_commit": "OpenHarmony 文档 master 的提交号", "docs_date": "那个提交的日期 YYYY-MM-DD",
         "harmony": "本机鸿蒙 SDK 版本，写明 API 几", "android": "平台资源、源码、各依赖库的版本；没用到写「不涉及」"},
 "changes": [
  {"where": "正文哪一部分", "before": "经验原文里逐字的一段", "after": "替换后的整段", "basis": "依据（出处写法同条目）", "type": "改错 | 加条件 | 写成明确做法 | 改措辞"}
 ],
 "entries": [
  {"step": "服务正文哪一部分", "fact": "一句平台事实", "source": "出处", "kind": "鸿蒙接口 | 安卓平台 | 依赖库 | 卡里验证", "origin": "沿用并复核 | 新查"}
 ],
 "device_todo": ["要上机才能定的事项（只给维护的人）"],
 "dropped_notes": 0,
 "note": "只在没有条目时写：为什么没有"
}
```

| 键 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 等于文件名 |
| `sdk` | 是 | 五个键（`verified_on`、`docs_commit`、`docs_date`、`harmony`、`android`），见 `sources.md` 第 4 节；鸿蒙、安卓两边都没用到写「未用」 |
| `changes` | 是（可为空） | 对经验正文的改句，按顺序套；`before` 在经验文件里恰好出现一次 |
| `entries` | 是（可为空） | 平台事实；不设条数上限 |
| `device_todo` | 是（可为空） | 要上机才能定的，不交给模型 |
| `dropped_notes` | 是 | 统一时删掉的未核实旁注条数 |
| `note` | 没有条目时 | 写明是流程类、做法不依赖平台事实，以及候选为什么全丢 |

### `step` 和 `where`

写正文的部分名：`标题`、`何时使用`、`适用情境`、`例外与边界`、`原因`、`做法第 N 步`；一条服务几步写 `做法第 2、5 步`；跨部分用「 / 」连，如 `原因 / 做法第 3 步`。条目大致按正文的部分顺序排。

### `fact`

一句能单独读懂的平台事实：什么条件下、平台或库怎么表现、取值是多少。规则见 `rules.md` 第 3、5 节，要点：

- 只写和具体应用无关的事实；
- 默认值带成立条件（「应用……没有另设 X 时」），值照来源；
- 只有随版本变的事实才写版本条件（「自 API 11 起」「android-30 为 0.54、android-33 起为 0.60」）；文档讲的超出本机 SDK 版本的注明；安卓默认值按父主题、库版本范围分别写（`sources.md` 第 4 节）；
- 不放链接（出处只在 `source` 里）；
- 不带返修经过和做法建议（「所以……直接写」「适合……」「改成……后与源端一致」）；
- kind=卡里验证 的写成「什么条件下、设备上（或编译时）看到什么」。

没有统一的字数上限；一句写不下的条件宁可写长，不拆成互相依赖的两条。

### `kind` 和 `origin`

| kind | 用于 |
|---|---|
| 鸿蒙接口 | 鸿蒙 SDK 声明、文档、构建工具里的事实 |
| 安卓平台 | 安卓框架源码、平台资源里的事实 |
| 依赖库 | androidx、material、Compose 等库的资源或字节码里的事实 |
| 卡里验证 | 来源卡里设备上或编译时实测到的平台表现（只留 `rules.md` T1 的甲类） |

| origin | 意思 |
|---|---|
| 沿用并复核 | 来自脚本收的候选，回到来源重核过（可能改了措辞或改正了值） |
| 新查 | 候选里没有，自己查的（读卡另列的「卡补」核过以后也算新查） |

### `changes[].type`

| type | 什么时候用 |
|---|---|
| 改错 | 经验写错或过时（声明、源码、文档能证明） |
| 加条件 | 结论只在某条件、某版本下成立；或拿掉返修条目后补前提 |
| 写成明确做法 | 把「要核对」「留给使用者判断」写成能照做的一句；做法尾巴并进正文；逐个核对改成脚本做法 |
| 改措辞 | 结论不变，说法不准 |

`basis` 必填；写出处（写法同 `source`），或写「从 <哪条> 条删下的做法尾巴；<出处>」「卡里成立的前提：…」。

改句进正文以后（经验库的提案发布了它），知识文件里的改句原样留着：渲染和检查脚本按「新句在正文里、原句不在新句之外出现」认它已发布，不再套、不报错。

## 2 工作稿（核实那一步的中间文件，最终文件里不许留）

核实那一步可以多三个键，统一时清掉（`check.py` 见到 `unverified`、`doubts` 就报错）：

| 键 | 说明 | 统一时去哪 |
|---|---|---|
| `unverified` | 核不到的点（一句一条） | 查到 → 条目；没影响 → 删，计入 `dropped_notes`；做法依赖 → 改句；要上机 → `device_todo` |
| `doubts` | 和经验正文对不上的地方（写明哪句、来源怎么说、影响） | 裁决后写成 `changes`，或在条目里写清、正文不改 |
| `dropped` | 没用上的候选行数（= 候选行数 − 用到的行数） | 最终文件不带；交回时报 |

## 3 交给模型的那一段

见 `rules.md` 第 6 节；由 `scripts/render.py`（写的人预览）或仓库的 `knowledge/render.py`（进库以后）生成，两者对新格式文件逐字节相同。只用 `sdk`、`entries[].step`、`entries[].fact`，正文套上 `changes`；其余的键不交出去，不带出处和链接。段头：「已核实的平台事实（核实时用的是 <harmony>；OpenHarmony 文档 master <docs_date>（提交 <docs_commit 前 8 位>）；安卓 <android>。……）：」，样子见 `examples.md` 例 19。
