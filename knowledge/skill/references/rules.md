# 配知识的规则

给一条经验配「已核实的平台事实」，按下面的规则做。规则分组编号，任务书、检查脚本和例子都按编号引：

| 组 | 管什么 |
|---|---|
| C | 收候选：从哪收、收什么 |
| V | 逐条核实、补查：去哪核、核到什么程度、核不到怎么办 |
| U | 统一：和正文对不上的改正文，没核到的清掉 |
| T | 清理：条目只留「什么条件下平台怎么表现」 |
| P | 交给模型的样子 |
| Q | 检查和验收 |
| N | 去哪查、出处、版本（细则在 `sources.md`） |

经验号写前 8 位（如 `73894333` = `lesson-73894333…`）。每条规则后面的「理由」说明为什么这样定，数字都是以前按这套规则写、再独立抽查得到的。例子在 `examples.md`，格式在 `knowledge-format.md`。

## 1 步骤和规则的对应

| 步骤 | 规则 | 工具（`scripts/`） |
|---|---|---|
| 同步文档 | N1 | `sync_ohdocs.py` |
| 读正文、收候选 | C1–C7 | `candidates.py` |
| 逐条核实、补查 | V0–V11、N2、N3 | `ohdocs_section.py`、`android_res.py`、`dts_lookup.py`、`ohdocs_link.py` |
| 统一 | U1–U9 | — |
| 清理 | T1–T7、N5 | `ohdocs_link.py` |
| 检查 | Q1–Q3 | `check.py` |
| 渲染 | P1–P3 | `render.py` |
| 专门复核 | V6b、Q6 | `../briefs/review.md` |
| 每批抽查 | Q7 | `../briefs/audit.md` |

## 2 收候选（C）

- **C1 候选按「同一张卡的同一条结论」收。** 经验「## 来源」一节每张卡记着它引的结论（`diagnosis`、`recommendation:N`）；只收被引的那几条结论里的东西，来源卡上别的问题不收。
- **C2 现成的候选表怎么来的（只在读旧表时用）。** 旧候选表是按「规矩」配的：规矩的出处里每张卡记着它的做法、例外、取值引了哪些结论；同一张卡、建议编号有交集就配上，经验在这张卡上只引了诊断时才按诊断配；配上的规矩里「已核实的写法和取值」一节的每一行（含后面「针对本应用要查的」各行）按顺序去重收进候选，「未核实：」整行收进未核实。`candidates.py --from-json`、`--from-rules`、`--from-cards` 是这条路。
- **C3 候选只是起点，不是成品。** 用得上的逐条回到来源重核才留（V3），用不上的丢掉，只计条数（`dropped`）。理由：候选是按卡配的，同一张卡上别的问题的事实也会配进来；以前按这套规则写的一批里，候选 1,168 行只用上 611 行（52%）。
- **C4 旧候选规矩不再是前提。** 新卡不用先写成候选规矩再配，照 C5–C7 直接从卡收。
- **C5 引了新卡的经验，直接从卡收候选（脚本）。** `scripts/candidates.py --from-case-files`：按经验「## 来源」引的卡、结论和卡片版本，只收被引的结论——建议 N 里带平台标识符或平台行为词的句子；诊断（卡的 summary）里讲上机或编译现象、修法用到的接口、声明或文档写明的行为的句子；卡的「没核到的点」（进未核实）；卡里记的环境版本（一行，供 `sdk` 和版本条件用，不是候选）。每行标〔卡号·字段·类〕，编号就是「用到的候选」的下标。不收调查图的节点和卡的标题、情境（那是谁读了什么、在哪写错）；讲生成过程的句子、针对经验库本身的建议不收；带历史模型思考字样的整句不收。
- **C6 读来源卡，另列脚本收不到的平台事实（人读）。** 读每张来源卡被引的诊断和建议原文、「没核到的点」，另列这几类：① 只用中文描述、句子里没有接口名的平台行为（某类组件在什么情况下怎么表现）；② 和当时模型怎么想写在同一句里、被脚本整句跳过的平台表现——只写设备、编译器、声明、文档说明的表现，不摘、不转述当时的想法；③ 现象成立的条件：版本、设备、时序（异步、隔多久）、主题、输入格式，常在同一张卡的别的句子里；④ 修法用到的接口在声明、文档里的事实：签名、首段 `@since`、默认值、错误码、同族接口（按参数类型名、枚举名去搜，把同族的一并查）——卡里多半没有，要回来源查；⑤ 源端写法背后的安卓框架或依赖库行为（不是被迁移应用自己的代码）。记法：工作稿里每条写「卡补〔卡号前 8 位·诊断 | 建议 N | 未核到 N〕一句平台事实」（第 ④ 类写「卡补〔卡号前 8 位·修法接口〕」）；核过才进 entries，origin 记「新查」；交回时报另列几条、用上几条。理由：在 6 条老经验上对照，旧候选表 100 行里直接从卡收对得上的只有 37 行；对不上的多是当时去声明、文档、安卓源码查来的（鸿蒙声明 14、文档 13、安卓平台 16），卡里本来就没有，要写的人自己补。
- **C7 旧候选表里的三样，现在各从哪来。** 「已核实的写法和取值」：出自卡的值脚本收得到（C5）；出自声明、文档、安卓源码的值和同族接口归 C6 第 ④⑤ 类和新查（V5）。「针对本应用要查的」：不再收——知识只放和应用无关的事实，做法里缺「去哪查」的写成改句（U3「写成明确做法」）。「未核实」：卡的「没核到的点」脚本收得到；自己核不到的照 V10、U5。

## 3 逐条核实、补查（V）

- **V0 写的人不看评测。** 不看评测用的工程、被迁移应用和它的迁移工程、评测结果和试验记录；只读经验正文、候选、来源卡和 V6 的来源。理由：知识要和具体应用无关；看过评测的人会不自觉地照答案挑条目。
- **V1 一条经验单独配，按正文逐步过。** 过「做法」各步（也包括适用情境、原因、例外与边界），列出照这条经验做要用到的平台事实；每条写明是正文哪一部分用的（`step`）。
- **V2 只放和具体应用无关的平台事实。** 不出现被迁移应用的名字、它的文件名和资源名。
- **V3 用得上的候选，逐条回到来源里重核才留，`origin` 记「沿用并复核」。** 重核时发现候选写错的，照来源改（例 1：候选写 draggable「API 10 起默认 true」，按声明改成「自 API 11 起默认 true（API 9 默认 false）」）。
- **V4 和这条经验的做法无关的候选丢掉。** 不进条目，只计进 `dropped`（例 11）。
- **V5 做法要用、候选里没有的，自己查，`origin` 记「新查」。** 例 3。
- **V5a 新查时要补的两类。** ① 正文某一步要把平台资源引用解析成值的（`@android:color/…`、`@android:dimen/…`、`?android:attr/…` 这类），把这一族里常用的平台常量的取值列成一条：名字、值、原文写法，随 API 级别变的注明。② 鸿蒙接口：条目点到这条经验的做法要调用的接口时，带上能直接照抄的声明——从哪个 kit 导入、完整签名（参数名和类型）、用到的枚举成员、起始版本；行为照文档说，声明照本机 SDK 抄（`scripts/dts_lookup.py`）。只写「回调方法是 X」「须为正整数」这样的散文不够。理由：知识交给模型用时，它每轮多花十几次查询去找导入、声明位置和枚举成员，一部分是知识里只提了名字没给声明；另有一处要按色值找资源键的地方两轮都没做对，缺的就是一个常用平台色值。
- **V6 每条在来源里核过才写。** 去哪查、谁说了算照 `sources.md` 第 1、2 节：鸿蒙接口存不存在、签名、从哪一版有看本机 SDK 声明；行为、默认值看 OpenHarmony 文档最新 master；运行时表现看卡里实测；安卓看源码和平台资源；依赖库看对应版本的库。可以联网，只取一手来源。
- **V6a 核一条事实，把出处的同一小节和同一方法的其他分支一起读完。** 同一小节的「说明」「注意」，同一方法在别的 API 级别的实现、别的重载，源码里 return 之前的 if 条件，注释和实现不一致的地方，都要看到。事实里写了「都」「只」「一律」「总是」，或者只描述了其中一个分支的，要么补上例外，要么写明只说哪一个分支、什么条件下。起始版本看声明里这个符号**首段**注释的 `@since`（后面几段是后来版本重新声明时加的）。理由：第一次独立抽查 48 条里 8 条有出入、0 条写错，8 条里 5 条是范围写宽、写窄或漏了同一小节的例外，1 条把起始版本照文档写而声明首段是另一个数。
  - **读全用工具，让「读全」是默认输出。** 理由：前两次独立抽查（48 条、32 条）都是约两成有出入，大多是同一类——只读了出处的一处；光写「要一起读完」管不住。
    1. 引文档的：用 `scripts/ohdocs_section.py <同步目录> <文件> <小节名>` 取整节来读（到下一个同级或更高级标题为止，「说明」「注意」「警告」块都在内；同名的小节如 deprecated 旧版一并打出；上级小节开头的说明块也打出），再看它末尾列出的「同一文件里别处提到这个关键词的小节」。不只读 grep 到的那几行。
    2. 安卓的 style、主题属性、平台色值和尺寸：用 `scripts/android_res.py`（`style <名字> --item <属性>`、`color|dimen <名字>`、`attr <名字>`）查全部 `values*` 限定目录和整条 parent 链，引用解析到字面值。取值随 API 级别、夜间模式或库版本变的，照它最后的「小结」分别写进事实（哪个 API 范围、哪个版本是什么），不只写其中一段。
    3. 依赖库至少看最旧和最新两个版本（`android_res.py --lib <组:库>` 默认就是这样）；应用依赖的版本已知时再加 `--version` 看那一版。两版不同的，事实里写版本范围。
    4. **顺着 parent 查安卓 style 或主题时，每一层都要看它在 `values-vNN` 等限定目录里有没有重定义，不能只看 `values/` 里那一份。** 重定义的那份可以换掉 parent（例：AppCompat 的 `Platform.AppCompat` 在 `values/` 里自己给了 `textColorSecondary` 等，`values-v21` 把它重定义成另一个 parent，API 21 起取的是框架主题的值）。
    5. 鸿蒙声明用 `scripts/dts_lookup.py`，它默认把同名的每个重载、每处声明都打出来；各处的起始版本各看各的首段 `@since`。
  - 下面三条的理由：第三次独立抽查（40 条）里，用了上面的工具仍有出入的，集中在这三种。
    6. **安卓资源的取值，照 `android_res.py` 小结里「★常见手机竖屏」那一行命中的那一份为主来写，同时写出别的配置下的取值；只写 `values/` 里那一份不行。** 小结四段都要看：参考配置（常见手机竖屏、手机横屏、平板）、各限定变体（`sw`/`w`/`h<N>dp`、`land`/`port`、密度、`night`、`vNN` 及其组合）、按 API 和日夜、「另有以下变体，要逐个看」（语言、运营商等，工具不归纳，逐个打开看）。例：对话框按钮条最小高度 `alert_dialog_button_bar_height` 在 `values/` 是 48dip、`values-h720dp` 是 54dip，竖屏手机的可用高度 `screenHeightDp` 到了 720dp 就命中 54dip、没到的仍是 48dip（targetSdk 35 以下可用高度不含状态栏和导航栏，物理高 760–780dp 的手机正落在 720dp 上下）；只写 48dip 或只写 54dip 都漏了一种常见情形。★ 那一行写「因配置而异」时，照它分的情形逐个写，并写明按什么分。
    7. **写「从某个版本起才有 / 才改」的事实，要把起点找准。** 本机缓存里只有几个版本时，中间没有的版本从官方仓库（Google Maven、Maven Central）取对应版本的 aar 或源码包逐版确认，直到找到「上一版没有、这一版有」的那一对；找不准就写成「至少在 X 版已有，更早未核」。只比了本机有的两个版本就写「X 起」不行（例：某属性写成「1.12.0 起才有」，实际 1.10.0 起就有、1.9.0 没有）。
    8. **核一段代码的行为，要读到调用它的上下游。** 进这个函数之前有没有预处理（裁剪首尾空白、归一化、缺省填充），用到的字段在调用前是不是已经被设过，返回后调用方怎么用；只读被引用的那一个函数不够（例：只看了追加文本的函数，没看到解析器在更前面已经去掉了首尾空白）。
  - 下面三条的理由：第四次独立抽查（专门复核之后的 40 条，中等以上只剩 1 条）里，剩下的轻微出入集中在这三种。
    9. **安卓平台「从某个系统版本起」的事实，要看到后续的补丁标签，不能只比各版的第一个发布标签（r1）。** 有的改动会回移到旧版的后续补丁（例：某个解析行为写成「Android 9 起」，实际 8.1、8.0、7.1.2 的后期补丁标签里已经有）。逐版比时取每一版最后一个发布标签；查不全就写成「至少从 X 起，更早的后期补丁未核」。
    10. **写了「从 X 起是某值」的，要看到本机最新的平台，写明上界。** 后面的版本又变了的，分段写到最新一版（例：一组色值写成「android-35 起」，本机最新的平台里已经是另一组）。
    11. **事实里提到资源名的，解析到取值。** 只写到 dimen、color 的名字不算写完，把它在各配置下的取值照第 6 条写出来。
- **V6b 写完以后，安卓平台和依赖库两类条目加上全部正文改句，交给另一个人专门复核一遍。** 复核的人不写新条目（V5a、T4a、V6a 要求补的除外），只回出处重核、就地改、记日志；每人不超过约 60 条，代码行为类的每条都要自己重读，不能记成沿用。任务书是 `../briefs/review.md`。理由：四次独立抽查——写的人自己照规则、用工具写出来的，鸿蒙接口一类基本准（14 条里 1 条轻微出入），安卓平台和依赖库两类中等以上的出入约三成（20 条里 6 条）；专门复核之后同两类再抽 40 条，中等以上剩 1 条（2.5%），没有写反的。复核大约让每条经验多花三到四成 token。
- **V7 出处写成换机器也找得到的样子。** 不写本机路径和行号；写法照 `sources.md` 第 5 节（文档出处写成文档仓库 master 的链接加小节名）。
- **V8 `kind` 四类。** 鸿蒙接口 / 安卓平台 / 依赖库 / 卡里验证。卡里修好并验证过的做法或观察，`kind` 记卡里验证，`source` 写卡里怎么验证的（T1）。
- **V9 `sdk` 写核实时用的环境。** 核实日期、文档 master 的提交号和日期、本机鸿蒙 SDK 版本（API 几）、安卓平台资源、源码和各依赖库的版本，键和写法见 `sources.md` 第 4 节。
- **V10 核不到的进 unverified，和正文对不上的进 doubts，这一步不改正文。** doubts 写明正文哪句、来源怎么说、对做法有没有影响。这两个键只在工作稿里，统一时清掉（U8）。
- **V11 没有平台事实可挂的经验（流程类），`entries` 为空，`note` 写明理由。** 例 11。

## 4 统一：对不上的改正文，没核到的清掉（U）

- **U1 doubts 逐处裁决，结论写成对正文的「原句 → 新句」（`changes`），不留「有出入」一段。** 谁说了算照 `sources.md` 第 1 节：鸿蒙接口有没有、签名、从哪一版有以本机 SDK 声明为准，行为、默认值、单位、时序以文档 master 为准；安卓的静态事实以源码和平台资源为准；运行起来的表现以卡里实测为准（除非源码能证明相反）；冲突时写清各自说了什么。随版本变的写出条件。卡里验证过的做法不删，只改说错的那句；改动尽量小。理由：交出去的经验只能有一个说法，留着「存疑」模型会自己再查一遍或照错的做。
- **U2 改句的格式。** `where`（正文哪一部分，写法同 step）、`before`（经验原文里逐字的一段，在经验文件里恰好出现一次）、`after`（替换它的整段）、`basis`（依据：出处写法同条目）、`type`。`before` 不跨正文的部分（不连着小节标题、不跨做法的两步）：改句要进正文时，是套进库里这条经验的某一个字段的。
- **U3 `type` 四类。** 改错（经验写错或过时，例 13）；加条件（取值或结论只在某条件下成立，例 14）；写成明确做法（把留给使用者判断的话写成能照做的一句，例 15）；改措辞（结论不变，说法不准）。
- **U4 卡里实测和声明注释说法不同、做法对两种都成立时，正文不改，条目里写清。** 例 17。
- **U5 unverified 再查一遍，四种去向。** 查到的转成条目；对做法没有影响的旁注删掉，删的条数记 `dropped_notes`；做法依赖它的，写成一句明确的做法进正文（changes）；确实要上机才能定的写进 `device_todo`。例 12。
- **U6 正文里不写要上机才能做的话。** 「在设备上核对」「截图对照」「画出后核对」这类不进正文。按这个次序换：先看卡里验证时的条件，写进做法；卡里没有而 SDK 或文档有行为写明的等价写法，就写它；两样都没有，恢复原句；要上机的只留 `device_todo`。经验原文里本来就有的「登记待设备核对」不动。理由：拿经验去做事的模型没有设备，写了它也照做不了；要上机的事留给维护的人。例 15、16。
- **U7 改句里不留本机字样。** 例：原句里的「本机 android-36.1 源码」，新句写「Android 源码」（例 14）。
- **U8 统一之后文件里不再有 unverified、doubts。** 结构固定为 id、sdk、changes、entries、device_todo、dropped_notes（空经验另有 note）。
- **U9 正文里「逐个核对」的做法，能机械做的改写成脚本做法。** 改成「自己写一个脚本批量核、只看报出来的」或「一条命令列出来、只看没写的」；type 写成明确做法，basis 写为什么可以由脚本做；不附现成脚本（由用的人自己写）。理由：逐个核对的范围随工程大小增长，模型逐个看既慢又容易漏，机械的部分交给脚本。例 18。

## 5 清理：条目只留「什么条件下平台怎么表现」（T）

- **T1 kind=卡里验证 的条目逐条分甲乙。** 甲：平台或库在什么条件下怎么表现（设备上看到的现象、编译器的报错），留下，改写成「什么条件下平台怎么表现」的句式，去掉「改成…后与源端一致」这类返修结果；`source` 写「卡里上机实测（case-…）」「卡里编译实测（case-…）」，或「卡里修好并验证过」。乙：某次返修怎么改的、改完的结果（正文已有对应做法），拿掉。例 4、5、9。理由：返修经过对别的应用没有用，还会被模型当成要照抄的做法。
- **T2 拿掉乙之后，正文里这条做法成立的前提没写的，补进正文。** changes，type 加条件，basis 写「卡里成立的前提：…」。例 10。
- **T3 卡里验证的条目不写返修。** fact 里不出现「改为、改成、后一致、不再、修好、返修」（`check.py` 查）。
- **T4 默认值加上成立条件，值不改。** 写明「应用（主题、样式、布局、代码）没有另设 <哪个属性> 时」，尽量点名能覆盖它的那几处（例：「布局、style 和代码都没设 gravity 时」「应用主题与代码都没另设 navigationBarColor、未强制 edge-to-edge、设备 config_navBarDefaultTransparent 为 false 时」「按钮没有另设 style 或下列属性时」）。安卓默认值取决于父主题和库版本的，按「哪个父主题、哪个版本范围下是什么」分别写（`sources.md` 第 4 节）。交出去的知识段开头另有一句总的限定（P2）。例 6。
- **T4a 一条默认值和它最常见的覆写写在同一条里。** 主题来的默认值，把标准父主题的变体（Light、Dark、DarkActionBar 这类覆盖层、DayNight；AppCompat、MaterialComponents、Material3 各自的）会不会改它写在同一条，顺着 parent 查到底；库的默认值随版本变的写版本范围。不要把默认值写在这条经验、把覆写写到另一条经验里。理由：交出去时两条不一定在一起，照做的人会把默认值当结论用；同一处错曾连着两版出现——条目给了一个主题的默认色值，没写它被常见的覆盖层改掉。
- **T5 全部条目扫一遍，句尾的返修经过和做法建议去掉。** 只留「什么条件下平台怎么表现」。去掉的如「所以 Image 的 .width(n).height(n) 直接写换算出的 dp 数」「，适合不参与命中的占位层」「：用于登记和注销」「；用 UIContext.px2vp(…) 换成 vp 再作布局值」。fact 里不出现「改成…后、后一致、修好、撤回、还原、不靠、适合、：用于、仍要、再作、后再」（`check.py` 查）。例 7。理由：做法属于正文；条目里的做法尾巴和正文说法不一致时，模型不知道听哪个。
- **T6 去掉的建议，正文没覆盖的，并进正文。** changes，type 写成明确做法（或加条件），basis 写「从 <哪条> 条删下的做法尾巴；<出处>」。例 8。
- **T7 改写只动措辞。** 条目改写时 origin 不变，事实的值不变。

## 6 交给模型的样子（P）

- **P1 正文。** 经验正文去掉「ID：…」一行和「[本主题](index.md)」一行，截到「## 来源」之前（「来源支持：…」一行留着），把全部改句依次套上：已发布进正文的（新句在、原句不在新句之外出现）不再套；原句逐字出现一次就替换，否则按空白可有可无对上恰好一处再替换，都不是就报出来、这份先不用。由 `scripts/render.py` 做；经验库仓库的 `knowledge/render.py` 对新格式文件的输出和它逐字节相同。
- **P2 知识段。** 有条目时，正文末尾空一行接：

  ```
  已核实的平台事实（核实时用的是 <sdk.harmony>；OpenHarmony 文档 master <docs_date>（提交 <docs_commit 前 8 位>）；安卓 <sdk.android>。和具体应用无关，直接用，不用再查；其中的默认值只在应用自己的主题、样式、清单和代码没有另设时成立，应用有没有另设要到应用里看）：
  - 〔<step>〕<fact>
  ```

  不带 `source`、`kind`、`origin`、`basis`、`device_todo`、`dropped_notes`、`note`，不带出处和链接。没有条目的经验只给正文。旧格式的文件（`sdk` 里没有文档日期和提交）段头没有中间那句。
- **P3 提示词模板里和知识段配套的两句。** 用知识的提示词模板里，讲平台事实去哪查的那一步要有这两句（逐字，或同样意思的话）：

  > 平台这一侧的事实（鸿蒙的 API 名、参数和默认值，安卓框架和依赖库的默认值、默认行为）：先看这条经验后面的「已核实的平台事实」。那里列出的已经在本机 SDK、文档和安卓源码里核过，直接用，不要再去查一遍。那里没有的才去查，不凭记忆：鸿蒙查本地 SDK 的 .d.ts；安卓框架的主题和控件默认值在本机 Android SDK 的 platforms/android-<api>/data/res 里，依赖库的样式在 Gradle 缓存里对应库的 res 里。
  >
  > 这个应用自己的事实（源码怎么写的、资源和配置里的值）不在那一段里，照常从安卓源码和工程里取。源端没写的属性，按「控件 style → 祖先布局的 android:theme → Activity 主题 → 应用主题」找到提供方，再解析到值。

  理由：模板里原来常有「查本地 SDK，不凭记忆」一类的话，和「已核实的直接用」打架，模型会把已核实的再查一遍。这两句属于提示词模板，不属于知识文件。

## 7 检查和验收（Q）

- **Q1 机械检查。** 格式和必填项；原句在经验文件里恰好出现一次；条目和新句里没有本机路径、行号、被迁移应用的名字；新句里提到设备、上机、截图、核对、登记、实测的逐句列出来看；卡里验证条目没有返修的话（T3）；全部条目没有做法尾巴（T5）；新格式的 `sdk` 和文档链接。对应 `scripts/check.py`，错误改到 0。
- **Q2 出处核对。** 鸿蒙声明：文件在、点到的成员名在；安卓源码：类文件在、成员名在；平台资源：文件在、资源名在；文档：对着 `sync_ohdocs.py` 同步的最新 master 找文件和小节名；卡里验证、依赖库、联网来源不核，要人看。对应 `scripts/check.py --sources --docs …`。报出来的逐条看（多半是小节名写成了概括、出处写法脚本认不出）。
- **Q3 人读卡里验证的条目。** 卡里验证条目逐条读，确认都是带条件的平台或库的表现，没有「怎么改」的话，也没有被迁移应用自己的类名、变量名、取值。理由：脚本对「卡里验证」只能查措辞，查不出「是不是和具体应用无关」。
- **Q4 增量更新时新旧逐条比。** 已有知识文件的经验只补做一部分时（`../SKILL.md`「一次归并里三种经验怎么做」），和旧文件逐条比，确认旧改句没有丢、没改的旧条目没有被顺手改措辞。
- **Q5 渲染后看一遍。** 渲染出的那段里套上的改句都在、原句不在新句之外出现；没有残留的「没核到」「有出入」「待核」。
- **Q6 专门复核。** 见 V6b。
- **Q7 每批抽查。** 一批写完、复核完，另一个人按类别抽 40 条左右加 8 处改句，逐条回出处核；只查不改。过线标准：安卓平台和依赖库两类里中等以上的有出入不超过一成，没有和出处相反的。任务书是 `../briefs/audit.md`。不过线的这批先不并入，怎么返工由协调的人按抽查报出的毛病类型定。

## 8 去哪查、出处、版本（N）

细则在 `sources.md`。

- **N1 文档用 OpenHarmony 文档仓库的最新 master。** 每次开工先跑 `scripts/sync_ohdocs.py <同步目录>`（不存在就浅克隆、稀疏检出 `zh-cn/application-dev/**/*.md`，存在就拉到最新 master），打印的提交号和日期填进 `sdk.docs_commit`、`sdk.docs_date`。旧的本机文档副本不作出处。
- **N2 可以联网，只取一手来源。** OpenHarmony 文档仓库；安卓框架源码和平台资源（本机 Android SDK 没有的取 AOSP 源码站）；依赖库的源码包或它在官方仓库里对应版本的源码；安卓官方参考文档。不用博客、问答、第三方教程。`check.py` 只认这些网址前缀。
- **N3 去哪查、谁说了算。** 鸿蒙接口存不存在、签名、从哪一版开始有，以本机 SDK 声明为准；行为、默认值、单位、时序看文档 master；运行时表现以卡里上机实测为准；三者冲突时条目里写清各自说了什么、以哪个为准。
- **N4 文档出处写成链接。** `https://gitcode.com/openharmony/docs/blob/master/zh-cn/application-dev/<路径>.md，<小节名>`，同步目录里的路径用 `scripts/ohdocs_link.py` 换。链接只放在 `source`、`basis`，`fact` 和新句里不放；交给模型的那段不带出处和链接。
- **N5 版本分两层。** 文件一层 `sdk` 记核实日期、文档 master 的提交号和日期、本机鸿蒙 SDK 版本（API 几）、安卓平台资源、源码和各依赖库的版本；条目一层只给随版本变的事实写条件：文档写了「从 API version N 开始」「API version N 起行为变更」的写进事实，文档讲的超出本机 SDK 版本的注明，安卓默认值按父主题和库版本范围写。不设条数上限。
- **N6 检查认新旧两种写法。** `sdk` 里有新键（或加 `--require-new`）的按新写法查；旧格式的文件照旧通过。渲染：旧格式的段头不带文档日期，新格式的带。
