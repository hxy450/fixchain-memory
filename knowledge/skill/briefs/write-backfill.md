## 照什么做

照这份 skill 做：`{skill 目录}/SKILL.md`，先读完它，再读 `references/` 下的 `rules.md`、`sources.md`、`knowledge-format.md`、`examples.md`、`tools.md`。这次走 SKILL.md 的入口 ②（给库里现有的经验补知识），具体到这次：

1. **正文**读 `{库}/memory/<主题目录>/lesson-<id>.lesson.md`（用文件名搜；只读）。改句的原句从这份文件里逐字取，恰好出现一次。不用跑 export。这个工作区里只许读 `memory/` 和 `store/cases/`。
2. **候选从来源卡直接收：**
   `py -3.12 -B -X utf8 {skill 目录}/scripts/candidates.py --from-case-files {库}/store/cases --memory {库}/memory lesson-<id>`
   打印的编号就是「用到的候选」的下标。然后照 `rules.md` C6 读这条经验引的来源卡（正文「## 来源」一节列着；只读被引的结论——诊断是卡的 `summary`，建议 N 是 `recommendations` 第 N 条——和卡的 `unknown`），把脚本收不到的平台事实另列成「卡补」行。卡里引历史会话里模型思考的句子不摘抄、不转述；卡里点到的转录文件、应用源码和迁移工程的路径不去找。
3. **文档同步目录**是共用的：`{文档同步目录}`，协调的人已经拉到最新。你只跑 `py -3.12 -B -X utf8 {skill 目录}/scripts/sync_ohdocs.py {文档同步目录} --show` 读提交号和日期填进 `sdk`，不拉、不改。
4. **条目多的经验另外排个先后。** 条目数不设上限，核得到、用得上的都写。某条经验的条目超过 24 条时，写完以后再给它的全部条目排一个先后，存成 `{产出目录}/{批}/rank/lesson-<id>.json`，内容 `{"lesson": "lesson-<id>", "order": [条目在 entries 里的下标（从 0 起），全部都要在、不重不漏]}`。排法：照这条经验做事的人没有它某一步就写不出来、或会把适用前提判错的排最前；能让结果更准但缺了也能做对的其次；背景性的、能由别的条目推出来的最后。知识文件本身不因此删条目、不加键。

核事实时读全要用工具（`rules.md` V6a）：引文档的用 `scripts/ohdocs_section.py` 取整节读，安卓的 style、主题属性、平台色值和尺寸用 `scripts/android_res.py --sdk {安卓 SDK} --gradle {Gradle 缓存}` 查全部 `values*` 限定目录和整条 parent 链（依赖库加 `--lib`，默认比最旧和最新两版），取值随 API 级别或库版本变的照它的小结分别写；鸿蒙声明用 `scripts/dts_lookup.py`，同名的每处都看。

安卓平台和依赖库两类条目是抽查里出入最多的，写这两类时逐条过下面四件事（V6a 第 6–11 条和 T4a）：

- **取值写哪一份**：`android_res.py` 的小结有四段，四段都要看。以「★常见手机竖屏」命中的那一份为主来写，同时写出横屏、平板和其他限定目录下的取值；只写 `values/` 里那一份不行（例：对话框按钮条最小高度 `values/` 里是 48dip，`values-h720dp` 里是 54dip；竖屏手机的可用高度 `screenHeightDp` 到了 720dp 就命中 54dip，没到的仍是 48dip——两种情形都要写，并写明按可用高度分：targetSdk 35 以下可用高度不含状态栏和导航栏）。★ 那一行写「因配置而异」时，照它分的情形逐个写。
- **版本起点**：写「从某个版本起才有 / 才改」的，要逐版确认到「上一版没有、这一版有」；本机 Gradle 缓存里没有的中间版本，从 Google Maven（`dl.google.com/android/maven2`）、Maven Central（`repo1.maven.org`）取对应版本的 aar 或源码包。找不准就写「至少在 X 版已有，更早未核」。安卓系统版本要比到每一版最后一个发布标签。
- **代码行为**：读到调用它的上下游——进这个函数之前有没有预处理（裁剪、归一化、缺省填充），用到的字段在调用前是不是已经设过——和同一函数的其他分支；只读被引用的那一个函数不够。
- **默认值**：它最常见的覆写（标准父主题的变体、覆盖层）写在同一条里。同一个资源值在你负责的几条经验里出现多次的，写法要一致。

全部条目和改句还要照下面三条写（`rules.md` T4b–T4d）：

- **颜色、尺寸这类取值**（T4b）：写明这个值是哪个主题、哪种模式（浅色 / 深色）、哪种配置下的取值，给出解析链（主题属性或资源名 → 值），浅色和深色两个值都给；应用自己的主题另设时写明以应用的为准；并写明目标侧用跟着主题和深浅色走的资源来承载，不要写死成字面值。带条件的结论把条件写在同一句里。
- **具体值和具体接口**（T4c）：同一句里写出它在什么条件下成立；另一支（别的主题或模式、别的系统版本、别的配置）写明取什么，或者写明到哪里查。来源卡里标成「本例」「这个应用里」的值是这一例的值，不升格成通用做法。写一个接口时写全它对用户看得见的全部效果，不只写达成目标的那一半（例：一个接口同时影响焦点和软键盘的，两样都写）。是补全分支，不是删掉只有一支的值。
- **一个限定语只管一个后果**（T4d）：「配置了 X 的」「在 Y 时」这类限定只修饰紧跟着的那一个动作；几个后果各自条件不同就拆成几句；不受条件影响的后果单写一句「不论是否 X，都……」。

## 不许看的（硬性）

- 评测用的工程和评测结果：被迁移的应用、它的迁移工程、评测和试验的记录与报告。
- 别人已经写好的同一批知识：以前给这些经验做过的知识文件（包括经验库仓库 `knowledge/` 下的一切，里面有这些经验的旧版知识）、这一批别的组的文件和目录、复核和抽查的记录。skill 的例子引用的是别的经验，可以看。
- 凭据：文件名带 key、token、credential 的文件，名叫 `cfg` 的目录，任何存放 API 密钥的文件，都不打开。

## 不许做的

- 不调任何模型 API，不起子代理，不碰模拟器和真机；不读会话转录；不改经验库、SDK、文档同步目录、skill。
- 某个动作被权限机制拒绝了，不换办法绕，记下来交回时说。
- 改 json 用写在文件里的脚本读入、改、写回（`ensure_ascii=False`，缩进 1）；带反斜杠的内容用写文件的方式建，不用 heredoc。
