## 何时使用

页面或组件实现阶段，在禁止编译的转换批次里写组件构造选项、属性方法参数、需实现的 SDK 接口，或 UIContext、状态存储一类调用时；或在可编译的修复轮里准备凭记忆写组件属性名、指望编译门报错兜底时；或因记不清 SDK 是否提供某能力，准备放弃规格或映射指定的组件 API、改用换了结构或交互的替代写法时

## 适用情境

转换派工禁止编译或构建，映射参考与规格只给组件、接口名而不给成员签名；写者准备凭记忆填写选项字段名、参数类型、接口方法名或链式调用，或只看到一行 grep 命中的声明；本机 SDK 的 ets/component、ets/api 下 .d.ts 可以读取。也包括修复或接线 worker 访问平台对象字段（如 BundleInfo 的包名字段）、填写 SDK 回调类型或命令常量时，凭 Android 命名或记忆书写。 也包括派工要求颜色、尺寸一律经 $r 资源绑定，或写者参照同批并发生成、尚未编译的兄弟页与 rg 检索到的零散用法改写参数（如给 blur、Swiper.itemSpace 传 $r，给 onClick 加 ClickEvent.stopPropagation，把 Text 换成 SymbolGlyph 后沿用单值 fontColor）。

## 原因

禁编译只推迟错误，不会消除错误：记忆中的字段名、接口成员名与所属类型常与当前 SDK 不符，写后自检若只核 API 版本号或链尾方法，不存在的字段、错误的接口成员、并不存在的中间一跳和可空返回都会留到编译门；业务页尚未接入可达图时，常规构建还会跳过这些文件。来源同一批并行转换者分别写出菜单项的 startImage、Slider.blockSize(number)、IDataSource.getTotalCount()、UIContext.getResourceManager()、UIContext 上的 openMenu/closeMenu、AlertDialog 参数里的 builder，并直接使用 AppStorageV2.connect 的返回值；其中有人写前已自述没把握，有人 grep 到声明行就按文件名推定了所属类型。另一应用的修复轮凭记忆给 TextInput 写 caretWidth，自述“若不支持编译门会报错”，编译门随即报属性不存在，返工后才查声明改用 caretStyle。

## 做法

1. 对本文件新引入、且未在已编译代码里出现过的每个 SDK 成员，写前在 SDK 的 ets/component/*.d.ts 或 ets/api/*.d.ts 找到声明，确认成员名、选项对象字段与必填项、参数类型和返回类型；有知识核验 skill 时也可以用它。禁止编译不等于禁止读声明。 因没把握而从方案里去掉的 SDK 能力同样要查声明：查到声明就回到规格指定的写法；确实查不到才降级，并在报告里逐项写出与源端的交互差异（拖动起点、点击命中、测量口径），不写“行为等价”。
2. grep 命中声明行后向上找到最近的 class/interface，确认成员属于哪个类型；同一个 d.ts（如 @ohos.arkui.UIContext.d.ts）包含多个类，不按文件名推定归属。链式调用逐跳核对，例如组件内解析字符串资源走 getUIContext().getHostContext()（可能为 undefined，先判空）再取 resourceManager.getStringSync($r(…).id)（Resource 参数的重载自 API 20 废弃），UIContext 本身没有 getResourceManager()。
3. 声明返回 T | undefined 的接口先判空再读写，AppStorageV2.connect 即使传了 defaultCreator 也一样；实现 ambient 接口时按接口体逐个成员实现，例如 LazyForEach 的 IDataSource 用 totalCount()、getData()、registerDataChangeListener()、unregisterDataChangeListener()，调用点统一用接口成员名。
4. 来源已确认的记忆误写可直接对照：MenuItem 选项的图标字段是 startIcon；Slider.blockSize 接受 SizeOptions（{ width, height }）；AlertDialog 参数没有 builder 字段且 message 必填。写后自检按实际输出逐个复核新写的 SDK 调用，不只核 API 版本号。
5. 访问平台对象字段前在 d.ts 核对字段名，只核函数签名不足以证明字段存在（BundleInfo 的包名字段是 name，不是 bundleName 或 packageName）；SDK 常量（回调类型、命令码）从已安装 SDK 的声明读取（如 Command.kCommandPay），或按 skill 用 instanceof 区分响应类型，不凭记忆写数值。
6. 可编译时同样先查声明再写，不把编译门当作 API 查询手段；例如 TextInput 没有 caretWidth，光标宽度与颜色用 caretStyle({ width, color })。
7. 资源绑定惯例只用于声明接受 Resource、Length、ResourceColor 的参数；blur 只收 number、Swiper.itemSpace 收 number|string，保留数值常量。参照同批尚未编译的兄弟页或 rg 到的零散用法时同样回到声明核对，并看清所在回调的事件类型（TouchEvent 与 ClickEvent 不同，ClickEvent 没有 stopPropagation），不用它覆盖自己与已编译页面一致的写法；换组件（如 Text → SymbolGlyph）时逐个核对沿用的修饰器签名，SymbolGlyph.fontColor 接收 ResourceColor 数组。

## 已核实的平台事实

核实时用的是 HarmonyOS 6.1.0（API 23，openharmony ets 6.1.0.105；文档副本含到 API 26 的内容，超出 SDK 的已注明）；安卓 平台资源 android-34；框架源码 android-36.1；androidx Compose 1.10.3（foundation、ui、ui-unit、ui-graphics，按字节码核）。和具体应用无关，直接用，不用再查；其中的默认值只在应用自己的主题、样式、清单和代码没有另设时成立，应用有没有另设要到应用里看；每条下面的「写法」是在 SDK 声明里核过的导入语句、归属、签名和枚举成员，写代码时直接照抄。

- 〔做法第 1 步〕SDK 声明位置：组件与通用属性在 openharmony/ets/component（通用属性在 common.d.ts 的 CommonMethod），@ohos.* 在 openharmony/ets/api，@kit.* 转导出在 ets/kits，HMS 能力在 hms/ets/api 与 hms/ets/kits（出处：鸿蒙 SDK 的 ets/component/common.d.ts，CommonMethod；鸿蒙 SDK 的 ets/api/@ohos.arkui.UIContext.d.ts，UIContext；鸿蒙 SDK 的 ets/kits/@kit.ArkUI.d.ts，UIContext；鸿蒙 SDK 的 hms/ets/kits/@kit.AccountKit.d.ts（HMS 能力的 kit 转导出））

  写法：const ctx = this.getUIContext().getHostContext()  // Context | undefined
