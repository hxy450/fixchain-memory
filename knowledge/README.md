# 经验后面挂「已核实的平台事实」（试验，第五版）

这个分支在 main（369bbbf3）之上只加了 `knowledge/` 一个目录，`memory/` 和 `store/` 没有动，也没有并入 store。

## 是什么

main 上 27 条经验的带知识版本。迁移模型照经验写代码时，要反复去查和应用无关的平台事实：鸿蒙接口从哪个包导入、签名和枚举成员是什么、安卓框架和依赖库的默认值和默认行为是什么。这里把这些事实提前查好、核过，挂在经验后面，模型拿到后直接用。

每条经验做了两件事：

1. **正文对齐**：正文里和核到的事实对不上、或缺条件的句子改掉，交出去的经验只有一个说法。
2. **挂事实**：后面接一节「已核实的平台事实」；鸿蒙接口另带能直接抄的「写法」（导入语句、归属、完整签名、枚举成员）。

## 目录

| 路径 | 内容 |
|---|---|
| `lessons/lesson-<id>.json` | 每条经验的知识源文件 |
| `memory/<主题>/lesson-<id>.lesson.md` | 渲染好的带知识经验，相对路径和 `memory/` 里的原文件一致；来源和证据卡不复制，指回原文件 |
| `render.py` | 从 `memory/` 的原文件和 `lessons/` 重新渲染：`python knowledge/render.py` |

json 的字段：

- `sdk`：核实时用的版本。
- `changes`：对正文的改动，每项有 `where`（哪一部分）、`before`（原句）、`after`（新句）、`basis`（依据）、`type`（改错 / 加条件 / 写成明确做法 / 改措辞）。
- `entries`：平台事实，每项有 `step`（服务于正文哪一部分）、`fact`、`source`（出处，不含本机路径）、`kind`（鸿蒙接口 / 安卓平台 / 依赖库 / 卡里验证）、`origin`（哪一版查的）、`code`（鸿蒙接口的写法）。
- `device_todo`：要上机才能确定的事项，只留给维护的人，不交给模型。

## 规模

- 27 条经验，其中 25 条有事实（2 条纯流程类经验没有可挂的）。
- 事实 418 条：鸿蒙接口 226、安卓平台 120、依赖库 40、卡里验证过的做法 32；带写法的 230 条。
- 正文改动 46 处，涉及 18 条经验。
- 要上机才能定的 15 条。

## 怎么配的

配的人只看经验正文和 SDK，不看任何被评测的应用。规则：

- 只挂这条经验自己的做法用得上的平台事实；默认值写明「应用没有另设时」。
- 同族接口一并带上：做法点到某个类时，把做同一件事要用的成员补齐（构造参数和单位、离屏 / 同步 / 异步版本、成对的读写方法、选项接口的字段、相关枚举）。
- 经验的适用前提取决于某个安卓组件默认怎么做时，把默认行为和成立条件核清楚。
- 从主题来的默认值，把各标准父主题下的取值列全，顺着 parent 查到底。
- 核不到的不写；随版本变的写版本范围。

核实用的版本：鸿蒙 API 23（SDK ets 6.1.0.105）和 2026-05 的 OpenHarmony 中文文档；安卓源码 android-36.1 和 android-30 至 36 的平台资源；依赖库版本写在各条出处里。

## 核对到什么程度

- 出处：安卓平台资源、安卓源码、鸿蒙文档、鸿蒙声明四类共 710 处，用脚本逐处对过，全部对得上。依赖库的出处（100 处）脚本不核，是配的人查的。
- 写法：80 条导入语句和其中的名字全部能在 SDK 声明里对上。
- 人工抽核：正文改动和新增事实抽了几十处对着声明和源码重查，没有发现错的；没有逐条全核。
- 没有上机。

## 用下来的情况

在留出应用上、用 GLM 5.3、按「做完后拿经验逐条核对修改」的方式跑过第二到第四版，每种一到两趟，单趟波动很大：

- 带知识后，查默认值这一类调用明显减少；第四版补了写法后，名字已在知识里还去查的调用基本没有了。
- 修掉的偏差数和不带知识相比没有稳定的差别。
- 第五版比第四版多 98 条（同族接口、依赖组件的默认行为、主题变体），还没有跑过。
- 代价是交给模型的内容变长：第五版比第四版长三到四成。
