# 配知识的规则（第七版规则：只收编译查不出来的、每条写成立范围、少而准）

经验是安卓 → 鸿蒙（ArkTS）迁移用的通用做法。每条经验后面挂几条「已核实的平台事实」，拿着经验去核对代码的模型直接用、不再自己查。配的人只做查、核、写：不调模型，不起子代理。

任务书只需要写：这份文件、负责哪几条经验（完整 id 和正文所在的主题目录）、目标目录、辅助脚本的文件名前缀、`origin` 填什么。

## 输入和输出

- 经验正文（只读）：本仓库的 `memory/<主题目录>/lesson-<完整 id>.lesson.md`。
- 输出：目标目录下每条经验一个 `lesson-<完整 id>.json`（本仓库收在 `knowledge/lessons/`）。目标目录里已有同名文件时，先读懂里面的 `changes` 和 `entries` 再动；没有就新建。
- 只许写自己负责的 json 和自己前缀的辅助脚本。改 json 用脚本文件读入、修改、写回（`ensure_ascii=False`，缩进 2），不用 heredoc 往 Python 里传带反斜杠的内容。

json 的键：

```json
{
  "lesson": "<完整 id>",
  "changes": [ {"where": "做法第 2 步", "before": "原句", "after": "改后的句子", "basis": "依据（哪条事实）", "type": "说错 / 缺条件 / 要上机"} ],
  "entries": [ {"step": "…", "fact": "…", "scope": "…", "source": "…", "kind": "…", "origin": "…", "code": "…（可选）"} ],
  "device_todo": [],
  "dropped_notes": 0,
  "note": ""
}
```

## 收什么（对每条经验一样地过一遍）

一条事实要进 `entries`，必须同时满足下面三条。

**一、是编译查不出来的那一类。** 收：

- 默认值（应用没有另设时取什么）。
- 单位（数值按什么单位解释；同一个接口不同参数下单位不同的要写清）。
- 取值范围和合法取值，尤其是传了别的值会被悄悄忽略、回退或截断的。
- 调用时序、生命周期、回调什么时候触发或不触发。
- 实际行为：接口做了什么、不做什么，和名字或直觉不一样的地方。
- 两个平台之间的差异（安卓这样，鸿蒙那样）。
- 安卓框架、主题、依赖库的默认外观和默认行为（经验的适用情境、例外或做法取决于它们时）。

不收：某个接口、属性、枚举存在不存在；签名（参数名、类型、返回类型、是否可选）；从哪个包导入；枚举有哪些成员；从哪个 API 版本开始有。这些写错了编译会报。

**二、写得出成立范围。** `scope` 一栏必须写，内容是这条事实「对什么成立、什么条件下成立、最常见的不成立情形」：

- 对象：哪类组件、哪种容器里的子组件、哪个接口的哪个参数。属性只对某种父容器的直接子组件生效的，写明是哪种父容器，并写一句「用在别的容器或自定义组件上不生效」。
- 条件：系统或库的版本、应用有没有覆写、取自哪个父主题。主题属性的默认值要顺着 parent 查到底，写明在哪些标准父主题下是这个值；被常见的父主题覆写成别的值的，要把那个父主题和覆写后的值写出来。
- 不成立的情形：最常见的一种，一句话。

写不出成立范围、或者范围要靠具体应用才能定的，不收。

**三、够格占位置。** 每条经验最多 6 条。排法：照这条经验的做法去写或去核代码时，缺了它最容易写出「能编译、但行为不对」的结果的排前面。没有够格的就一条不加，`note` 里写「没有够格的条目」。流程、登记、交接类的经验通常一条都不用加。

## 条目各栏怎么写

- `step`：服务于正文哪一部分（适用情境 / 例外与边界 / 原因 / 做法第 N 步）。
- `fact`：一句能单独读懂的平台事实。默认值写明「应用没有另设时」。不写某次返修的经过，不写做法建议（做法在正文里）。
- `scope`：见上面第二条。
- `source`：换台机器也找得到，**不写本机路径和行号**。写法：「鸿蒙 SDK 的 ets/…/x.d.ts，符号名」「鸿蒙文档 xxx.md，小节名」「android.包.类#成员」「Android SDK 平台资源 data/res/values/xxx.xml，名字」「androidx.组:库 版本，类或资源名」。
- `kind`：鸿蒙接口 / 安卓平台 / 依赖库。
- `origin`：任务书指定。
- `code`（可选）：只有当「怎么写才对」本身就是这条事实的一部分时才写（比如单位参数必须在构造时传）。从声明文件照抄，不凭记忆写。

## 正文和事实对不上时

- 核到的事实和正文某句对不上：在 `changes` 里加一项，把那句改对（静态事实以 SDK 声明和安卓源码为准；随版本或主题变的写成带条件的句子）。交出去的经验只能有一个说法，不留「存疑」「待核实」。
- 卡里验证过的做法不删、不改方向；只改说错的事实和缺的条件。
- 要上机才能定的：不写进 `entries`，也不往正文里加「上机核对」的句子；记到 `device_todo`。

（本仓库里 `changes` 怎么进正文：维护的人照经验库维护流程写提案，把改句 upsert 进 store，再导出 `memory/`；见 `knowledge/README.md`。）

## 写完要复核（必须）

写完要由另一个人逐条独立复核成立范围（对象、条件、最常见的不成立情形），不对的改掉。依据：第七版前三批共 247 条里，独立复核改了 91 条（约四成），没有删的，多数是漏了例外；状态管理类的事实改得最多（新旧两套装饰器混着说）。

## 去哪查（只读）

本机的鸿蒙 SDK 声明、鸿蒙文档、安卓源码和平台资源、Gradle 缓存里的依赖库：

- 鸿蒙 SDK 声明：SDK 的 `openharmony/ets`（`kits` 目录看从哪个 @kit 导出）和同级的 `hms/ets`。
- 鸿蒙文档：OpenHarmony 中文文档。
- 安卓源码：Android SDK 的 `sources/android-<api>`；平台资源：`platforms/android-<api>/data/res`。
- 依赖库：Gradle 缓存里的 aar / jar。取值随版本变的，至少核最旧和最新两个版本，写版本范围。
- 本机没有的（安卓原生层源码、依赖库的源码、官方文档的新版本）：可以联网取公开来源，比如 AOSP 源码站、Maven 仓库里的 sources 包、官方文档站。只读公开资料，请求里不带本机信息；出处写成仓库、路径加标签或版本。
- 本机有构建工具时，也可以写小样例实际编译、导出结果来核（只用 SDK 自带的工具，不用任何应用的资源）；出处写明工具和版本。

核不到的不写。

## 不许看的（硬性）

- 不看任何被迁移的应用、它们的迁移工程和评测材料；也不看评测和试验的报告、记录和别的知识目录。
- 条目里不出现应用名和应用的具体取值。
- 经验库的 `store/`（卡片）可以读，用来弄清一条经验的做法是在什么情况下验证过的；但卡里某个应用的具体取值不许写进条目。
- 文件名带 key / token / credential 的文件不打开。不调模型 API，不碰模拟器。

## 做完自查（必须跑）

在仓库根目录：

`python knowledge/check.py <目标目录> --only <自己负责的 id 前 8 位，逗号分隔>`

留作评测的应用的名字不写在仓库里，用 `--app-name <名字>`（可重复）传给检查脚本。报出来的问题改到没有为止；改不掉的在交回里说明。不改检查脚本。

## 节省上下文

读声明和资源用 grep 加小范围读取，不整文件读。上下文到 25 万 token：把做完的写好、跑自查，交回并说明还剩哪几条。
