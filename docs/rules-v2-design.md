# 规矩库 v2：从卡片重建经验库的设计

分支 `memory/rules-v2-20261115`，2026-11-15 起。这份文档是这次重建的依据，做的人先读它。旧的 `memory/`（经验）和 `store/`（卡）原样保留，不动；新东西都放在下面写明的新目录里。

## 1. 为什么重建

审查和实验的完整记录在评审工作目录的 `REPORT.md`（不在本仓库里）。和这次重建直接有关的结论：

- 经验选对了，影子能从避开 2.5 处到 5–7 处（ColorLines 三个单元，19 处历史缺陷）。现有做法选不准：按关键词取的 10 条只对上 6 处。
- 旧的归并按「条件、机制、动作」比较，机制不同才新增，换一个控件或应用不算新情景。结果是并卡最多的经验全是动作类的（回源码核对、隐式外观写成显式样式），一条里装着几十张卡的不同情景，agent 看到的具体情景和经验的标题对不上。
- 把同一批知识改写成「一个触发对一个做法」的窄规矩并带上查好的知识之后，选得完美时多修 1–2 处，积分少一到两成。
- 只有具体情景的规矩不够：卡里没见过的情景要靠「去哪查、怎么读出值」的通用查法。
- 选好的 13 处里有 5 处无论怎么写都没修对，原因是库里的内容对不上或和判据相反。写法动不了这些，重建时只做到把冲突记下来。

## 2. 三条原则

1. **窄**。一条规矩只讲一件事：一个触发对一个做法。审的人看一处就能判断适不适用；照做之后这条里没有剩下的事。
2. **带知识**。能查清的直接写查清的结果和出处；因为随应用而变查不清的，写怎么查。不把「去查」「以 API 为准」留给用的人。
3. **按触发情景组织**。触发写的是 agent 的视野：它读过的东西里看得到什么，它交回的产物里写错成什么样。索引从触发里长出来，agent 顺着自己看到的东西能走到对口的规矩。

由此定下的具体做法：

- 经验跟子代理完成的任务挂钩，不跟代码挂钩。规格、派工、代码、资源各阶段的子代理都有自己读过的东西和交回的产物，都按同一套写法。
- 用法统一按「任务刚做完、在审计」来设想，不分首写和结束两种触发。
- 出处不能是某台机器上的路径和行号。可以在本机查证，呈现的是结果和换一台机器也能用的出处。
- 上机验证过的结论不动；声明里写死的东西（签名、参数个数、默认值、单位、枚举值）卡里写错了可以改，改了记一笔；拿不准的不改，记成冲突。
- 限定和例外必须出自卡，不许自己加。
- 每条规矩记着出自哪些卡、哪些应用，评测时可以把某个应用的卡拿掉。

## 3. 目录布局（都在本分支根目录下）

```
docs/rules-v2-design.md          本文
skills/memory-rules/             归并 skill：SKILL.md、references/、scripts/
store/candidates/<卡号>.json     每张卡提炼出的候选规矩（留作核对）
store/merge/…                    合并时的分组和理由
store/rules/<规矩号>.json        规矩的结构化原件，含核对用的引文
store/families/…                 归族的提案和决定、理主题的清单和决定（topic_lists/、topic_decisions/）、families.json、topics.json
rules/index.md                   第一层：各产物下的一级主题，每个主题一行（中文名和「agent 手里有什么东西时该进来看」）
rules/<产物>/<主题>/index.md     第二层：主题的一行，主题下的子主题和触发族
rules/<产物>/<主题>/<触发族>/index.md   第三层：这个族的通用查法，加每条规矩的一行（标题和触发）
rules/<产物>/<主题>/<触发族>/<规矩号>.md  第四层：规矩正文
rules/keys.jsonl                 召回用的索引，每条规矩一行
rules/manifest.json              条数、构建信息、所依据的卡库版本
```

目录名用小写英文短横线；中文名字写在各级 index.md 里。产物的目录名固定为 `spec`（规格）、`plan`（计划与派工）、`code`（代码）、`resource`（资源）。

## 4. 一条规矩的格式

结构化原件（`store/rules/<规矩号>.json`）：

```json
{
  "id": "rule-<12 位十六进制>",
  "title": "触发在前、做法在后的一句话，不超过 60 字",
  "product": "规格 | 计划与派工 | 代码 | 资源",
  "triggers": [
    {"read": "这个子代理读过的东西里看得到的写法；没有就写空字符串",
     "wrong": "它交回的产物里写错的样子：出现了什么，或者少了什么；没有就写空字符串"}
  ],
  "scope": "适用范围，一句话",
  "exceptions": [{"text": "卡里写明的不适用情形", "support": ["case-…#recommendation:2"]}],
  "how": [{"text": "一步做法，带确切写法", "support": ["case-…#recommendation:2"]}],
  "values": [{"value": "确切的值或写法", "meaning": "它是什么", "source": "出处，写到文件加符号名，不带本机路径", "support": []}],
  "lookups": [{"what": "要针对这个应用查的是什么", "where": "去哪类来源的哪个文件里、按什么找", "how": "找到之后怎么读出值"}],
  "why": "一句话：不这样做会出什么错",
  "keys": {"read": ["读过的东西里会出现的词"], "product": ["产物里会出现的词"]},
  "probe": null,
  "unverified": ["没能核实的点"],
  "alternatives_unverified": ["知识库里查到、但卡里没验证过的替代写法"],
  "siblings_checked": "搜了什么词、另有几个接口带它；或者「无：」加原因",
  "refs": [{"what": "…", "kind": "harmony-dts | android-sdk | android-lib | oh-docs", "where": "来源里的相对路径（依赖库写 group:artifact:version 加包内路径），加符号名", "quote": "逐字原文，不超过 200 字", "version": "…"}],
  "sources": ["case-…"],
  "general": false,
  "status": "active | disputed"
}
```

要点：

- `product` 说明这条规矩审的是哪种产物。同一张卡可以在几个产物上各出一条：规格里该写明什么，代码该怎么写。
- `triggers` 两栏至少写一栏。代码和资源类的规矩，写了的那一栏里至少有一个代码标识符；规格和派工类的，`wrong` 栏写文档里看得到的说法或缺的那一项。同一件事在不同写法下（View 的 XML、Java 代码、Compose）触发不同，各写一个触发，放在同一条规矩里；只写卡里出现过的写法。
- `keys` 是给召回用的词，只用平台和公共库的词，不用出事应用自己的类名、资源名、控件 id、文件名。每栏 3–12 个。
- `probe` 可选。写错的样子如果能表达成在产物文件里搜一个正则，就写成 `{"pattern": "…", "note": "搜到说明什么"}`；表达不了的写 null。
- `refs` 只给检查脚本核对引文用，不呈现。`values` 的 `source` 是呈现出来的唯一出处：鸿蒙 SDK 写「鸿蒙 SDK 的 ets/component/text.d.ts，符号名」；Android 平台资源写「Android SDK 平台资源 data/res/values/attrs.xml，资源名（按应用的 compileSdk 取对应平台）」；安卓框架源码写「android.widget.TextView#setShadowLayer」；依赖库写「坐标 包内路径，资源名（按应用依赖的版本）」；在线文档写文件名加小节名；出自卡的写「卡里修好并验证过」。
- `general: true` 是触发族上的通用查法：看到哪一类写法，去哪查、怎么读出值，再写成显式的写法。它不列取值表。
- 正文（title、triggers、scope、exceptions、why、how 合计）不超过 800 字，通用查法不超过 600 字。

呈现给 agent 的样子（`rules/…/<规矩号>.md`）：

```
# <title>

审的是：<product>
触发（任一种）：
- 读到：<read>；写错的样子：<wrong>
适用范围：<scope>
不适用的情形：<exceptions>
做法：
- <how>
已核实的写法和取值（核实时用的是鸿蒙 SDK API <N>）：
- <value>：<meaning>（出处：<source>）
针对本应用要查的：
- <what>：<where>；<how>
未核实：<unverified>
来源：<N> 张卡，<M> 个应用
```

没有内容的段不出。第三层索引里每条规矩一行：`- <规矩号>｜<title>｜读到：<第一个触发的 read>；写错：<第一个触发的 wrong>`。

## 5. 流程

五步。前四步里读卡、写规矩的活由子代理做，它们不知道任何评测；脚本负责准备、检查、聚类和落盘。

1. **准备**（脚本）。从 `store/` 当前版本把每张卡渲染成一个工作包（情境、诊断、每条建议原文、与建议有关的节点内容），分批。
2. **提炼**（子代理，一张卡一个输出）。照提炼任务书把一张卡写成若干条候选规矩，写进 `store/candidates/<卡号>.json`，同时记 `left_out`（没写成规矩的内容和原因）、`corrections`（按声明改正的）、`gaps`（没查实的和冲突）。每张卡写完跑检查脚本。
2b. **复核**（子代理，一批卡一个子代理）。照 `skills/memory-rules/references/review-brief.md` 对着卡把每张卡的候选规矩再核一遍、原地改（查什么、怎么改以那份任务书为准），每张卡写一份复核记录 `store/reviews/<卡号>.json`；`review_stats.py` 统计规矩条数的变化、按复核记录里的 `check` 各改了多少处、拆分和挪进 `left_out` 的条数、拿不准的项数，列出还没复核的卡。第 3 步在复核做完之后开始。
3. **合并**（脚本聚类，子代理判断）。脚本按 `keys` 和标题把相近的候选聚成组；单独成组的直接成为规矩；多条的交给子代理判断哪些是「同一个触发、同一个做法」。相同的并成一条：来源都留，取值取并集，说法冲突的把 `status` 标成 disputed 并写明。不同的各自保留。阈值 0.35，同一张卡的候选不连边，每批不超过 40 条候选。
4. **归族和建主题**（脚本聚类，子代理命名）。同一产物下，触发有共同部分的规矩归成一个触发族。子代理给族起名、写一行「agent 会看到什么」、有通用方法的补一条通用查法、给族一个建议的主题，并把族里从标题和触发看是同一个触发、同一个做法的规矩标出来（`same`）。第一次建库时「补并」和「理主题」并行：脚本把标出的每组做成合并组（成员都是已有规矩），交给合并的子代理照第 3 步的标准判断，并出来的沿用排在前面那条的规矩号、删掉其余几条，最后落族时把被并掉的规矩号换成留下的那条——这样补上词面相似度抓不到、用词不同的重复。第一次建库时，族都归完之后再「理主题」：脚本把同一产物下所有的族列成一份清单（族的标识、族名、族的一行、规矩条数、建议的主题），每个产物一个子代理定主题树：按任务对象分、不按动作分，1–2 级，每个节点的直接子项不超过 20 个，每个主题写中文名和一行「agent 手里有什么东西时该进来看」，每个族恰好归到一个主题，族名和族的一行说的是同一类写法的族标出来合并（两个族都有通用查法的不自动合并，列出来给人看）。脚本用这份决定覆盖各族的主题、合并标出的族。增量归并时不理主题，照旧优先用已有主题。
5. **导出和检查**（脚本）。写 `rules/` 目录树、每个产物的一页地图 `rules/<产物>/map.md`（每个主题一行，下面是「短号 族名（条数）」）、`keys.jsonl`、`manifest.json`；每个族在一次导出里有一个唯一的短号（`f001`…）；全量跑检查；出统计。

增量归并（以后新卡进来）走同样的五步，只是第 3 步的聚类是拿新候选去配库里已有的规矩（每一期的组、批次带自己的前缀，不碰已有的），第 4 步只给新规矩出族的提案，并附上最相近的几个已有族；已有的族和主题原样留着。每期增量落完之后检查超限的节点，就地拆：规矩超过 20 条的族，由子代理拆成几个族、留在原主题下；直接子项超过 20 个的主题节点（含产物根），由子代理在它下面加一层新主题、把子项分进去。树的深度就这样按需加深，不限层数。

第一次建库分两期：卡库里在快照 e613047f 里的卡（669 张）先完整走一遍第 3–5 步，得到「基础库」，评测用它，这样和以前几组对照用的是同一批卡；其余 211 张（10 个较新的应用，没有哪个应用一半在一半不在）再按增量归并加进去。

## 6. 任务书必须写进去的规定

**提炼**（一张卡 → 候选规矩）：

- 第 2 节的三条原则和第 4 节的格式。
- 卡里讲了几件不同的事就写几条，一张卡通常 1–4 条，最多 8 条。
- 没有任何产物里看得到的触发的内容（纯流程上的提醒）、要上机或截图才能做的、只对出事应用成立的，不写成规矩，记进 `left_out`。
- 跟具体应用无关：不出现出事应用的名字、文件名、资源名、转录引用，不带它自己的取值。
- 知识库三类来源：本机鸿蒙 SDK 的声明文件；本机 Android SDK 的平台资源和源码、Gradle 缓存里的依赖库资源；OpenHarmony 官方文档（GitHub 镜像原始文件，从目录页顺着链接找）。文档和声明不一致以声明为准。
- 能查清的写结果；随应用而变的写进 `lookups`，可以附一个带条件的例子，不写成让人照抄的答案。
- 每条出处带逐字原文；凭记忆知道但找不到原文的不写进规矩，记进 `gaps`。
- 同族接口一并查，各写各的完整签名并写明是哪个类的。
- 上机验证过的不动；声明里写死的写错了可以改并记进 `corrections`；替代写法记进 `alternatives_unverified`。
- 默认行为成立的条件要写明。卡里的情形带着条件（比如背景不透明、主题是某一族）时，把条件写进触发或适用范围，不要写成无条件的默认。

**合并**：只合并触发和做法都相同的；合并后的规矩要过同一个检查；不借合并扩大适用范围；每组写一句理由。

**归族**：族名和族的那一行用 agent 看得到的东西来写，不用动作来写；通用查法照通用查法的规定写；不改规矩正文。第一次建库时族的主题只当建议。

**理主题**（第一次建库时，每个产物一份）：主题按任务对象分，不按动作分；1–2 级；每个节点的直接子项不超过 20 个；每个主题写中文名和一行「agent 手里有什么东西时该进来看」；每个族恰好归到一个主题；族名和族的一行说的是同一类写法的族标出来合并，两个族都有通用查法的不合并、列出来给人看；不改族名、族的一行和规矩。

## 7. 检查脚本要查的

格式和必填栏；长度上限；`support` 引的卡和结论确实存在；`refs` 的 `where` 是来源里的相对路径（不许本机路径），按本机配的根目录（`work/sources.local.json`）找到的文件里能逐字找到引文（本机没有这个来源、这个库的记作「没能核对」）；呈现的各栏里没有本机路径、盘符、用户目录和行号；触发符合第 4 节的要求；`keys` 每栏的个数；`probe` 的正则能编译；出事应用的名字（名单从卡库的应用清单生成）；`product` 取值合法。汇总：每张卡几条规矩、`left_out`、`corrections`、`gaps` 各多少。

## 8. 召回（两步）

- **粗筛**（脚本，不用模型，不用向量）。输入是某个子代理的视野：它读过的文件和它交回的文件，以及它的产物种类。从这些文件里抽出标识符当 query，对 `keys.jsonl` 里同一产物的规矩按词打分（键和标题里的词，标识符整体和拆开的部分都算，逆文档频率在规矩库上算），`probe` 命中的加分，取前 K 条。目标是不漏，不求排得准。
- **精选**（审计的 agent）。只把候选的第三层那一行（标题和触发）给它，让它对着手里的东西判断触发在不在；在的，再去读正文照做。命中的族的通用查法一并给。它也可以顺着索引自己找：先看一页地图（每个产物几百个族也在几千字以内），再用短号一次取几个族（族的一行、通用查法全文、每条规矩一行）和几条规矩正文，可以只列某几个产物；也认索引节点的路径。
- 粗筛也可以按族打分（族的一行加族里所有规矩的 `keys`），给出前几个族当排序提示。
- 脚本要支持按应用、按卡库版本取视图：评某个应用时去掉只出自它的规矩；和旧库比时只用旧版本里已有的卡产出的规矩。

## 9. 做的时候的规矩

- 提炼、合并、归族的子代理不读任何评测材料，也不去找任何具体应用的源码。
- 只在本分支的工作目录里写。不动主库的工作目录，不动别的分支，不推送。
- 不打开凭据文件；联网只取文档前缀下的文件，请求里不带本机路径和个人信息。

## 10. 已知的缺口

- 评测只有 ColorLines 一个留出应用，而且只有出代码的单元。规格和派工类的规矩做出来现在没法评。
- 库里内容本身的缺和错，重建只能记下冲突，不能补全。
- 三份任务书里有几条规定是看了 ColorLines 上的失败之后定的，换一个应用是否同样有效没有验证。
