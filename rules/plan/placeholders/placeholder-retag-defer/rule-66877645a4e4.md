# 收口裁决本组的占位时先回源确认依赖，能本地实现的就地兑现，不改成无人认领的集成期延迟

审的是：计划与派工
触发（任一种）：
- 读到：登记里某 FWD-REF 的 resolve_by 是某个 Slice，依赖的是仓内可实现的自有 HTTP 端点；账本里有「懒接入」「软前置」这类数据链措辞；写错的样子：closer 把 resolve_by 改成「集成期：……落定」之类的外部延迟，债务闸据此判 EXTERNAL / PASS
- 读到：占位登记里 resolve_by 属于本组的 forward-ref 行；回源查到依赖只是对本地集合的 shuffled() 之类变换；写错的样子：收口时把 resolve_by 改成「集成期：某等价体建立后接线」这类不属于任何切片的外部延迟，状态仍是 registered
适用范围：组收口、集成和占位裁决阶段处理 resolve_by 属于本组（Slice 内）的 forward-ref、决定要不要改成外部延迟时
做法：
- 先回源确认占位依赖的实际内容，看它是否确实在仓外（三方 SDK 或平台 API 缺失）
- 依赖在仓内能实现（自有 HTTP 端点、对本地集合的变换）的，派实现或在本文件就地兑现并撤掉占位标记；不改 resolve_by 绕过债务闸，「懒接入」这类软前置措辞不算功能延后的授权
- 只有依赖确实在仓外才延后；这时改挂「集成期」还是写成有切片认领的具体步骤，两张卡说法相反（见未核实）
未核实：依赖确实在仓外时延后怎么写：case-75784c189c0578d026a6 的建议 4 以依赖在仓外（三方 SDK 或平台 API 缺失）为改挂「集成期」外部延迟的前提，即这时可以改挂；case-77e4e8b4e16c3fc8e030 的建议 3 说不要改成没有切片认领的「集成期」延迟，否则这项债脱离流水线追踪，它的情形是依赖能本地实现，没验证仓外依赖
