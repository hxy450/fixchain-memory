# 已批零权限决策与 API 的 @permission 冲突时，核实级别后上报改判，不挂 deferred

审的是：计划与派工
触发（任一种）：
- 读到：派工写「module.json5 零权限声明」并引一条已批决策，而 d.ts 里所用 API 标了 @permission；写错的样子：交回或占位登记把冲突挂成 deferred，理由是授予级别「未核实」或凭记忆写成 system_basic + ACL；交回写 module.json5 零改动，相关设备验收被列为「裁定前必败」
适用范围：实现期发现已映射 API 的 @permission 与已批零权限决策冲突、要裁定是否补声明时
做法：
- 上报时带 d.ts 出处（@permission 与 201 错误）和已核的授予级别（grantMode、availableLevel），不凭记忆猜级别
- 决策方据此改判并补声明（用户已授权自动决策时直接改判），不以未核实的级别把冲突挂成 deferred，让已知必败的设备验收进入交付
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- ohos.permission.PRIVACY_WINDOW：权限级别 normal，授权方式 system_grant：这类权限补声明即可，不需要签名或 ACL，没有理由挂 deferred（出处：permissions-for-all.md，ohos.permission.PRIVACY_WINDOW）
- 核出 system_grant + normal 后补声明，台账追加「零权限决策就此项不再适用」：修法（出处：卡里修好并验证过）
针对本应用要查的：
- 冲突权限的授予方式和级别：鸿蒙 SDK 的 openharmony/toolchains/lib/PermissionDefinitions.json 按权限名找（文件名检索不区分大小写），或文档 permissions-for-all.md 的同名小节；读 grantMode、availableLevel，写进上报
