# 源端解密函数 catch 回退原文时，规格写明失败回退原文、按业务码判定

审的是：规格
触发（任一种）：
- 读到：源端响应转换钩子（beforeResponse 一类）调用解密工具函数，函数的 catch 分支原样返回传入的 content；写错的样子：规格网络层写「解密失败显式返回错误，不伪造成功」，或只写「与源端等价的解密」而没写失败语义
- 读到：接口清单里有「是否全接口返回密文」的 open 不确定项，没有抓包证据；写错的样子：规格选了更严格的一律解密、失败报错分支，决策台账把不确定项标为 answered，明文兼容和失败分支推到联调
适用范围：规格提取阶段写响应解密 / 解码拦截器的契约时
做法：
- 沿源端钩子追到被调函数的异常分支，把失败时的行为照写进契约：解密失败按原文继续进入信封解析，由业务码判定成败
- 有「是否全接口密文」这类没法核实的不确定项时，保留源端容错路径，不选更严格的分支再延后
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- 生产环境有接口返回明文 JSON（HTTP 200 加业务码），一律解密时报块长度错误：源端靠 catch 回退原文兼容这类接口（出处：卡里修好并验证过）
针对本应用要查的：
- 源端解密失败时的行为：源工程响应拦截或转换钩子里调用的加解密工具函数；读函数体的 try / catch，catch 返回什么（原文、空、抛出）就照写进规格
