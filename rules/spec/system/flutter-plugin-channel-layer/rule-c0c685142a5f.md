# Registry 无 OHOS 包的插件，先写 F3 可行性：底层能力对应的 Kit，找不到才选 F5

审的是：规格
触发（任一种）：
- 读到：插件 pubspec 只联邦 android/ios、Registry 没有 OHOS 包，但原生实现做的是 HTTP 上传、签名这类通用能力；写错的样子：插件的 solution 里 `selected_layer` 写 F5、`status` 写 blocked，evidence 只有「Registry 无 OHOS 包」「只联邦 Android/iOS」，没有 F3 判断，也没写缺失的具体能力
适用范围：Flutter 复用路线下，为 Registry 没有 OHOS 版本的插件按 F1→F5 选替代层级、写 solution 记录时
做法：
- F1、F2 排除后先写 F3 可行性判断：列出原 Android 实现依赖的每项底层能力（如 HTTP PUT、HMAC 签名、文件读取）和对应的 HarmonyOS Kit 接口
- 只有某项能力找不到可用 Kit 时才选 F5，并在 evidence 里写明缺的是哪项能力；「无现成 OHOS 包」只排除 F1、F2，不能当作「功能无法在 OHOS 实现」
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- F3：在 ohos/flutter_plugins/<包名>/ 建本地兼容插件，保持包名、Dart API 与 Channel，用 HarmonyOS Kit 实现真实能力，经 dependency_overrides 接入；F5 只用于功能无法在 OHOS 实现，且须列出缺失能力：两个层级的定义，判 F5 前要先排除 F3（出处：卡里修好并验证过）
- STS 签名的对象存储 HTTP 上传：ArkTS 用 cryptoFramework 做 HMAC-SHA1 签名、http 发 PUT，回调成功/失败事件，真机上传成功：曾被判 F5 的上传插件实为 F3 可行（出处：卡里修好并验证过）
- function createMac(algName: string): Mac；HMAC 的摘要算法名可取 SHA1、SHA224、SHA256、SHA384、SHA512 等：HMAC 签名对应的 Kit 接口，HMAC-SHA1 写 cryptoFramework.createMac('SHA1')（出处：鸿蒙 SDK 的 ets/api/@ohos.security.cryptoFramework.d.ts，cryptoFramework.createMac；crypto-compute-mac-overview.md，HMAC）
- function createHttp(): HttpRequest；request(url: string, options?: HttpRequestOptions): Promise<HttpResponse>；HttpRequestOptions.method?: RequestMethod，RequestMethod.PUT = "PUT"：HTTP PUT 上传对应的 Kit 接口（出处：鸿蒙 SDK 的 ets/api/@ohos.net.http.d.ts，http.createHttp、HttpRequest.request、RequestMethod.PUT）
针对本应用要查的：
- 原 Android 实现依赖的底层能力：本机 pub 缓存里该插件的 *_android 实现包源码，看平台侧方法处理里每个方法调用的 SDK 或三方库；每个方法列出所用能力（网络请求方法、签名算法、文件读取等），再到鸿蒙 SDK 的 ets/api 下按模块名找对应接口，写进 F3 判断
