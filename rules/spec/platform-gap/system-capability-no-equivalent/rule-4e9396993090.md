# 规格判定平台没有对等能力前先查 SDK 声明；elapsedRealtime 对应 getUptime(STARTUP)

审的是：规格
触发（任一种）：
- 读到：源端用 `SystemClock.elapsedRealtime()` 计算后台偏移；写错的样子：规格把它映射为墙钟（Date.now()），并写「平台未开放跨休眠单调时钟」一类边界，没有引 SDK 声明作依据；或写成运行期验证项「若平台提供」
适用范围：规格阶段写平台差异、断言「目标平台无对等能力」时
做法：
- 判定前当场查项目 SDK 的 d.ts，记下 API 名和 @since 并对照 compatibleSdkVersion：elapsedRealtime 写成 systemDateTime.getUptime(systemDateTime.TimeType.STARTUP)
- 查不到时写成待查疑点，不写成已知边界
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- function getUptime(timeType: TimeType, isNanoseconds?: boolean): number：取系统启动以来的时长，默认毫秒；声明里最早一段注释是 @since 10（出处：鸿蒙 SDK 的 ets/api/@ohos.systemDateTime.d.ts，systemDateTime.getUptime）
- TimeType.STARTUP = 0：启动以来时长，含深度睡眠；TimeType.ACTIVE = 1：不含深度睡眠：对应 elapsedRealtime 的是 STARTUP（出处：鸿蒙 SDK 的 ets/api/@ohos.systemDateTime.d.ts，systemDateTime.TimeType）
- elapsedRealtime()：返回开机以来的毫秒数，含睡眠时间：源端的单调时钟语义（出处：android.os.SystemClock#elapsedRealtime）
- 锚点改为 systemDateTime.getUptime(STARTUP)：修复后的做法（出处：卡里修好并验证过）
针对本应用要查的：
- 目标工程允许用的最低 API：目标工程 build-profile.json5 的 compatibleSdkVersion；和声明里该 API 最早的 @since 比，不低于才可直接用
