# 移植多条件能力门时逐条对照源条件写目标表达式，不用相近的设备能力位代替

审的是：代码
触发（任一种）：
- 读到：源端 supports… 一类能力门函数里有多重条件：是否由拍照 Intent 启动、大堆内存阈值、陀螺仪是否存在、预览是否支持连拍或曝光时间，用 && 连在一起；写错的样子：目标的能力判断少了源端的某些条件（只剩内存阈值），或用 canIUse('SystemCapability.Sensors.Sensor') 这类设备能力位代替陀螺仪是否存在；注释写着陀螺仪，实现却不是
适用范围：把安卓端的能力门函数（决定某个模式或功能是否可用）翻译成 ArkTS 的能力判断时
做法：
- 动笔前把每个能力门的全部源条件逐条列成「源条件 → 目标表达式」对照表，代码按表逐条实现，一条不删
- 具体硬件（如陀螺仪）是否存在，用传感器查询来判断，不拿 canIUse 的系统能力位或自动水平之类的相近能力代替
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- canIUse(syscap: string): boolean：判断某个 SysCap 对应的 API 集合在目标设备类型上能不能调用，不是判断某个传感器硬件在不在（出处：鸿蒙 SDK 的 ets/api/@internal/full/global.d.ts，canIUse）
- 同一设备类型的不同型号软硬件规格可能不同，要用 canIUse 加能力查询接口判断；能力查询机制并非 canIUse：设备上有没有某个硬件，要用对应模块的查询接口，canIUse 判断不了（出处：syscap.md，SysCap的用途；单设备应用开发场景下的适配开发）
- 能力类改用陀螺仪服务的 hasSensors 判断全景，并补回启动方式条件后，两套能力判断一致：修好的做法（出处：卡里修好并验证过）
未核实：卡里修好时用的陀螺仪服务内部怎么查传感器，卡里没写
