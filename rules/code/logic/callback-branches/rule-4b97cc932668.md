# 源端登录拦截成功后会继续原操作时，目标暂存待执行动作，页面重新可见时续做

审的是：代码
触发（任一种）：
- 读到：源端需登录的操作带结果回调：未登录拉起登录页并 observe 登录结果，仍未登录才 result.on(false)，登录成功则 result.on(true) 继续原操作（如应用所点的选项）；写错的样子：目标端拦截处只调登录守卫跳转登录页然后 `return` / return false 中止，没有暂存所点的动作，从登录页回来后原操作丢失
适用范围：把源端「需登录才能继续」的操作回调迁成目标端登录拦截、而目标登录守卫没有成功回调时
做法：
- 把源端回调拆成「未登录拉起登录 → 登录成功后继续原操作 → 失败/取消才中止」逐项对照，源端成功分支执行原操作时不能只中止
- 拦截处暂存待执行动作（类型和参数）；在页面重新可见（如 NavDestination 的 .onShown(...)）或登录态广播时一次性消费：已登录就重查权限并执行，仍未登录就丢弃；先检索工程里已有的登录回流写法并复用
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- onShown(callback: Callback<VisibilityChangeReason>): NavDestinationAttribute：NavDestination 页面显示时回调，从登录页返回时在这里消费暂存动作（出处：鸿蒙 SDK 的 ets/component/nav_destination.d.ts，NavDestinationAttribute.onShown）
- 门控分支暂存所点的种类和键，在详情页 onShown 里调用消费函数：已登录则重查权限并应用暂存选择，未登录则丢弃：修好的写法（出处：卡里修好并验证过）
针对本应用要查的：
- 工程里已有的登录回流做法：目标工程里搜登录守卫的调用处，以及登录态变化的广播或时间戳状态；看别的页面怎么暂存、在哪个回调里消费，照同一做法接入
未核实：卡里的 SDK 是 API 16；本机 API 23 的 onShown 从 @since 21 起回调带 VisibilityChangeReason 参数
