# 单线程写执行器改成 Promise 队列时，任务体内嵌套写调内部版本，不 await 同队列方法

审的是：代码
触发（任一种）：
- 读到：源端用 Executors.newSingleThreadExecutor() 串行执行写任务，提交方法按 Thread.currentThread().getName() 判断已在执行线程就 runnable.run() 内联、否则 submit；任务体内还会调用同类的公开写方法；写错的样子：目标端执行器只有 tail = tail.then(task) 的链式 Promise，没有重入判断；入队的任务体内 await 同一队列的公开写方法；注释声称单线程事件循环下重入天然成立
适用范围：把源端单线程写执行器（带同线程重入内联分支）移植成 ArkTS 异步串行队列时
做法：
- 为任务体内会被调用的公开写方法拆出不经队列的内部版本（源端已有的 *Synchronous 写法），公开方法只做入队并调用内部版本
- 入队的任务体内只调用内部版本，不 await 经队列的公开方法；对照源码里依赖重入分支的调用点逐一改
- 写完逐个扫描入队任务体，找出对本类经队列方法的 await，作为最小检查
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- newSingleThreadExecutor：任务保证顺序执行，任一时刻最多一个任务在跑：源端串行语义；它的重入内联靠调用方自己判断线程，不是执行器自带（出处：java.util.concurrent.Executors#newSingleThreadExecutor）
- Promise 状态改变时回调加入微任务队列，在当前宏任务执行完成后执行：嵌套任务入队后排在当前任务之后，当前任务 await 它就永远等不到（出处：async-concurrency-overview.md，Promise）
- 任务体内 await 同队列公开方法时外层任务永不完成、后续写入全部冻结；改成调用内部版本后恢复：验证过的写法；执行器本身仍是无重入判断的 Promise 链（出处：卡里修好并验证过）
针对本应用要查的：
- 源端哪些调用点依赖重入分支：源工程里写仓库类：提交到执行器的每个任务体（Runnable / lambda）；找任务体里对本类其他经执行器提交的公开方法的调用；这些调用点在目标端都要改成内部版本
