# 串行化的同步服务不给全量同步加「返回在途 Promise」捷径，用请求版本号补跑尾随请求

审的是：代码
触发（任一种）：
- 读到：源端每次同步触发 launch 新任务，在 Mutex.withLock 后排队执行，不合并在途任务；写错的样子：目标端用 Promise 链 / 串行队列统一调度后，全量同步入口在有在途 Promise 时直接 `return await` 它，运行中新到的请求不再获得推送轮次
适用范围：目标端用单一同步服务和 Promise 串行队列统一调度全量同步、定向拉取与状态推送时
做法：
- 去掉「返回在途 Promise」的捷径；需要合并时给全量同步记请求版本号，本轮结束时比较，有新请求就补跑一轮；修一个入口的「等待后 return」时同步排查其他入口的同类写法
- 前一轮失败而后面仍有请求时继续补跑，只在最后一个请求仍失败时发布失败
- 补测试：同步越过推送阶段、尚未结束时入队并再次触发，断言推送次数增加且 pending 为 0；fail 项在下一次触发时被重推
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- 全量同步记请求版本号、本轮结束时比较并补跑尾随请求，只在最后一次请求失败时发布失败：返修的合并方式（出处：卡里修好并验证过）
