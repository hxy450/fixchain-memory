# BlockingQueue 常驻消费改写成 Promise 泵时，先入队启动泵，逐请求 try/catch

审的是：代码
触发（任一种）：
- 读到：源端保存线程 while(true) 里 queue.take() 常驻消费，生产者 put 后按成本追加占位请求；规格写「满队等待空位」「等待入队与计数分离」；写错的样子：按需启动的消费泵：入队方法先 await 全部占位请求才启动泵；泵循环不对单个请求 `try/catch`，运行标志只在循环正常退出时复位
适用范围：把 Java 有界 BlockingQueue 和常驻消费线程改写成 ArkTS Promise 泵时
做法：
- 先入队并启动 / 保持泵，再等待成本占位；或同步预占整组成本、入队后立即启动泵，不让消费者是否运行取决于生产者能否完成入队
- 泵循环对每个请求 try/catch，失败也递减计数并通知等待者，运行标志在 finally 里复位
- 至少两条单测：容量 1、成本 4 的请求能排空；单个任务抛错后等待排空的方法仍返回、后续请求继续处理
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- E take() throws InterruptedException：取队头，必要时等到有元素：源端消费者常驻等待，不依赖生产者先完成入队（出处：java.util.concurrent.BlockingQueue#take）
- 改为串行入队、同步预占整组成本、入队即启动泵；泵逐请求 try/catch；销毁时先关闭接收，再投递哨兵并等待排空：修好后的写法（出处：卡里修好并验证过）
