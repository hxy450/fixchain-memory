# 多路请求聚合写 TTL 缓存时，全失败不写新时间戳，命中同时校验载荷非空

审的是：代码
触发（任一种）：
- 读到：安卓源码按刷新时间加 TTL 判定缓存，用 viewModelScope.async 并发两路请求、各路可单独失败；规格验收条目写「成功后写入缓存」「不把空模型等同网络成功」；写错的样子：代码在 Promise.allSettled 的结果全是 `rejected`（或各路载荷全为 null）时仍以 Date.now() 写入载荷为空的缓存记录；缓存命中只比较保存时间与 TTL
- 读到：安卓源码在请求全部失败的分支也用空对象和当前时间写 SharedPreferences 缓存，而规格验收条目或决策台账写成功后才写入、网络失败读有效缓存；写错的样子：代码照搬源码在全失败分支写入新 Date.now() 时间戳加空载荷，交回的报告里没写与源码的差异
适用范围：迁移带 TTL 的多路并发请求缓存（各路结果合成一条缓存记录）的数据层时
做法：
- 用 Promise.allSettled 聚合各路；写缓存前先判断至少一路 status === 'fulfilled' 且载荷非空。全部失败时不写新时间戳：有未过期且载荷非空的旧缓存就返回旧缓存，否则抛出（或向页面暴露）分支错误
- 缓存命中条件写成「保存时间在 TTL 内」且「至少一路载荷非空」同时成立，只看时间戳不算命中
- 安卓源码失败也写空缓存、而规格验收条目或决策台账要求成功后写入时，按规格和台账实现，并在交回的报告里写明与源码的这处差异，不以忠实复刻为由静默照搬
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- allSettled<T>(values: Iterable<T | PromiseLike<T>>): Promise<PromiseSettledResult<Awaited<T>>[]>：PromiseConstructor.allSettled：各路不论成败都回来，结果数组与入参一一对应（出处：鸿蒙 SDK 的 ets/build-tools/ets-loader/node_modules/typescript/lib/lib.es2020.promise.d.ts，PromiseConstructor.allSettled）
- PromiseFulfilledResult<T> { status: "fulfilled"; value: T }；PromiseRejectedResult { status: "rejected"; reason: any }：每一路结果的两种形状：按 status 区分，成功取 value，失败取 reason（出处：鸿蒙 SDK 的 ets/build-tools/ets-loader/node_modules/typescript/lib/lib.es2020.promise.d.ts，PromiseSettledResult）
未核实：改后的缓存命中条件在冷启动场景下是否单独上机复测过，卡里只写了单飞修复后的复测
