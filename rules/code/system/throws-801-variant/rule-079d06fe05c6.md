# 共享封装在 d.ts 同名变体间选接口时，对比 @throws，带 801 的不用作共享封装

审的是：代码
触发（任一种）：
- 读到：d.ts 里同一能力有几个变体（同步、Promise、带 ID 参数），其中某个变体的注释单独写了 @throws { BusinessError } 801 - Capability not supported；写错的样子：所有调用方共用的封装选了带 801 的变体（如 RdbStore.beginTrans），理由只是「签名存在、异步写法更简洁」
适用范围：在鸿蒙 SDK 声明里给多处共用的封装（事务、存储、设备能力等）挑选接口变体时
做法：
- 逐个对比各变体注释里的 @throws：共享封装选不带 801 的变体；带 801 的变体只在确认目标设备和当前库模式支持之后才用
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- 801：Capability not supported. Failed to call the API due to limited device capabilities；该设备已支持 API 所属的 Syscap，但不支持此 API：签名存在不等于能调用（出处：errorcode-universal.md，801 该设备不支持此API）
- 处理步骤：避免在该设备上使用此 API，或在代码中判断规避：共享封装不要建在带 801 的变体上（出处：errorcode-universal.md，801 该设备不支持此API）
- RdbStore 的 beginTrans 声明带 801、beginTransaction 不带；共享事务封装用 beginTrans 时单元测试一调用就抛 801：按 @throws 取舍的一个验证过的例子（出处：卡里修好并验证过）
针对本应用要查的：
- 各变体是否声明 801：鸿蒙 SDK 的 ets/api 下对应模块的 .d.ts，按方法名找到每个重载最后一段注释；看注释里的 @throws 列表有没有 801；有就记为能力受限变体，再查同名文档小节里是否写了适用条件（如只支持某种库模式）
