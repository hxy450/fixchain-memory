# 源端解密失败返回原文时，目标解密失败回退按原文解析，解析也失败才报错

审的是：代码
触发（任一种）：
- 读到：源端解密工具在 catch (Exception e) 里 printStackTrace 后 return 原文，响应转换器解密后直接交给 Gson TypeAdapter；写错的样子：目标响应中间件在解密的 `catch` 里直接 `throw` 解密错误，不再按原文 JSON.parse
- 读到：源端解密工具函数用 Cipher.getInstance("AES/CBC/PKCS5Padding") 的 doFinal 解密，catch (Exception) 里 printStackTrace 后返回原文 content；写错的样子：目标解密函数 catch 里 `throw` 一个解密错误，响应解码对非 DEBUG 构建的所有响应一律调用它
适用范围：翻译响应解密 / 解析管线、实现网络层的响应解密或解码拦截器时
做法：
- 逐个对照源工具的异常分支：解密失败时返回原文，照常进入解析（信封解析、由业务码判成败），只有原文解析也失败才返回错误；或先判断响应体是不是 JSON，是就直通，不是再解密
- 规格的失败语义和已读源码冲突时按源码行为等价实现，并在报告里写明冲突
- 补一条最小回归：Release（非 DEBUG）构建收到明文 JSON 响应，解密失败后仍能解析出业务码
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- doFinal 在解密模式下、数据不符合填充时抛 BadPaddingException（输入长度不是块长整数倍时抛 IllegalBlockSizeException）：明文输入会走到源函数的 catch，由它回退原文（出处：javax.crypto.Cipher#doFinal）
- 解密失败回退按原文解析后，明文响应恢复正常：修好后的写法（出处：卡里修好并验证过）
- 解码先判 JSON 直通、非 JSON 仍解密后，明文接口恢复：修复后保留的写法（出处：卡里修好并验证过）
针对本应用要查的：
- 源端解密工具每个异常分支的返回：源工程的加解密工具类里 decrypt 方法的 try/catch，和调用它的响应转换器；catch 里返回什么（原文、空串、null 还是抛出），目标端照同样的结果走后续解析
