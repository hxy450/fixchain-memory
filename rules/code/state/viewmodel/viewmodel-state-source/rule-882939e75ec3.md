# 替代源端 WorkInfo 聚合时，作业结束写成 COMPLETED 留在状态表里，不删 key

审的是：代码
触发（任一种）：
- 读到：源端宿主观察 WorkManager 的 WorkInfo 列表（LiveData），把作业状态映射成 url→状态 表并 postSticky 粘性广播；查询面专门排除完成态，订阅方遍历事件里的全部 url 再过滤；写错的样子：目标下载服务的作业收尾写成 map.delete(url) 后再发事件；查询方法在判断 COMPLETED，但全文件没有写入 COMPLETED 的地方
适用范围：目标端没有 WorkManager 等价框架、由服务自己维护作业状态表并直接发事件，订阅方按 url 是否在事件里过滤时
做法：
- 作业结束时写 map.set(url, { state: COMPLETED, progress: -1 }) 再发事件，不删 key；状态映射照源端聚合：RUNNING→RUNNING，ENQUEUED / BLOCKED→QUEUED，其余→COMPLETED
- 写完逐个核对状态域：QUEUED、RUNNING、COMPLETED 各有写入点；查询方法检查的状态在文件里找不到写入，就是收尾写法偏了
- 按订阅方的过滤方式（如按 url 是否在事件载荷的 key 里）核对最后一次事件：完成时这个 url 仍在载荷里
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- 结束作业以完成态保留在表里；改成 set(url, COMPLETED, -1) 后再广播，详情页在下载完成后刷新：修好后的收尾写法（出处：卡里修好并验证过）
- 删 key 后完成那次事件不含该 url，按 url 在不在载荷里过滤的订阅方丢弃事件，页面停在 RUNNING：删 key 的后果（出处：卡里修好并验证过）
针对本应用要查的：
- 源端的状态映射：源工程里观察 WorkManager 的宿主（Activity）源文件，按 WorkManager 的 LiveData observe 回调和 WorkInfo.State 的分支找；每个 WorkInfo.State 映射到哪个状态常量就照写；结束态（SUCCEEDED、FAILED、CANCELLED）写成哪个就保留哪个
