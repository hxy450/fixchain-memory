# rcp 用 baseAddress+相对路径建请求时，拦截器里不直接读 context.request.url

审的是：代码
触发（任一种）：
- 读到：rcp.createSession 的 SessionConfiguration 写了 baseAddress，请求用 new rcp.Request('相对路径', …) 构造；写错的样子：Interceptor.intercept 或其中的刷新/重试分支里无保护地读 context.request.url（如 hilog(…, context.request.url.toString())）
适用范围：HarmonyOS rcp 的 Session 配了 baseAddress、Request 以相对路径构造，拦截器里要用请求地址（日志、判断）时
做法：
- 日志要的地址用 baseAddress 与原始 path 自行拼接，不读 context.request.url
- 或安全读取：let urlForLog: string; try { urlForLog = String(context.request.url) } catch (e) { urlForLog = '<unresolved-url>' }，日志只用 urlForLog
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- url: URL：Request.url 声明为 URL 类型；构造时传的 string 要转换成 URL（出处：鸿蒙 SDK 的 hms/ets/api/@hms.collaboration.rcp.d.ts，Request.url）
- constructor(url: URLOrString, method?: HttpMethod, headers?: RequestHeaders, content?: RequestContent, cookies?: RequestCookies, transferRange?: TransferRange | TransferRange[], configuration?: Configuration)：Request 的构造接受 URL 或 string，可以传相对路径（出处：鸿蒙 SDK 的 hms/ets/api/@hms.collaboration.rcp.d.ts，Request.constructor）
- baseAddress?: URLOrString：Request.url 不是绝对地址时，在发送到服务器时才前置 baseAddress；拦截阶段的 Request 仍是构造时的相对值（出处：鸿蒙 SDK 的 hms/ets/api/@hms.collaboration.rcp.d.ts，SessionConfiguration.baseAddress）
- request: Request：RequestContext.request 就是被拦截的那个 Request（出处：鸿蒙 SDK 的 hms/ets/api/@hms.collaboration.rcp.d.ts，RequestContext.request）
- 以相对路径构造的 Request 读 url 即抛 'Cannot convert to URL'：单独构造的相对路径 Request 上观察到的行为，修复后用 try/catch 读并给占位值（出处：卡里修好并验证过）
未核实：没有真实 rcp Session 下 401 刷新链的运行记录，未实测生产拦截器收到的 Request.url 是否已拼上 baseAddress；卡里的行为出自 HarmonyOS 6.1.1(24)，本机按 API 23（HarmonyOS 6.1.0）的声明核对；声明没写 getter 对相对路径会抛错
