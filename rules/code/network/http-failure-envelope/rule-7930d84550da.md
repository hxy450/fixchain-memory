# 源 catch 承载 HTTP 失败而目标客户端永不 reject 时，先写 status!==200 分支

审的是：代码
触发（任一种）：
- 读到：源端请求包在 try/catch（或 Promise/Observable 的错误回调）里，catch 中 `error instanceof HttpErrorResponse` 时取 error.error?.message 设错误并 return false，成功路径才改 hasMore/游标；写错的样子：目标端请求返回后直接取 res.data 走成功路径，没有 res.status !== 200 分支，只留了一个 catch
- 读到：目标网络层客户端注明返回的 Promise 永不 reject，非 2xx 和传输异常归一成失败信封，调用方按 `envelope.status === 200` 判成功；写错的样子：catch 上注释写着在契约下不可达、仅作防御；或同一服务里别的方法有 `res.status !== 200` 判定，分页/列表方法没有
适用范围：把源端靠异常分支处理请求失败的代码，翻译到以信封 status 表示失败、永不 reject 的 HTTP 客户端上时
做法：
- 先列出哪些失败会进源 catch（如非 2xx 以 HttpErrorResponse 进入），再按目标契约把每种失败对到实际的失败信号
- 在消费 res.data 之前写 if (res.status !== 200) { this.error = res.message 或兜底文案; return false }，不改 hasMore、游标和首拉完成标记
- 看到「此 catch 不可达」类注释时，核对源 catch 的语义已迁到这个分支；同一服务里的分页/列表方法逐个对齐已有的 status 判定
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- if (res.status !== 200) { this.error = res.message（空则兜底文案）; return false }，hasMore 不动：失败信封的处理写法，放在取 res.data 之前（出处：卡里修好并验证过）
针对本应用要查的：
- 目标网络层把哪些失败以什么信号交回：目标工程网络层客户端的文件头注释和返回类型；读出非 2xx、传输异常、解析失败各自是 reject 还是失败信封、判成功的字段和值（例：注明永不 reject 时按 status === 200 判成功）
- 源端 catch 会接到哪些失败：源工程里这个请求所用 HTTP 客户端的调用处，catch 或错误回调里判断的错误类型；列出每种失败（非 2xx、网络异常）进的是哪条分支、分支里设了什么状态、返回什么
未核实：源端是 Web 框架，非 2xx 以 HttpErrorResponse 进 catch 的行为没在知识库核实
