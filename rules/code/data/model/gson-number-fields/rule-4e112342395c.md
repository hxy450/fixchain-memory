# 源端 Long 的服务器 id、hash、userId 字段，ArkTS 模型写 bigint，不写 number

审的是：代码
触发（任一种）：
- 读到：源端 bean 或接口里有 val id: Long、Long?、Java 的 long userId、@Query("userId") userId: Long；写错的样子：目标模型写成 id: number = 0、userId: number、number | null，fromJson 里 (json['id'] as number)，服务方法参数 (userId: number)
适用范围：源端用 Long 承载服务器生成的 id、hash、userId，迁成 ArkTS 数据模型和各层参数时
不适用的情形：确认取值不超过 2^53 的 Long（如 13 位毫秒时间戳、时长）可以用 number，并在注释写明理由
做法：
- 逐个列出源端 bean 和接口里的 Long 字段与参数，服务器生成的 id、hash、userId 在模型字段和各层方法参数上都写 bigint
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- long 的最大值是 2^63-1（Long.MAX_VALUE = 0x7fffffffffffffffL），SIZE = 64：源端 Long 是 64 位整数（出处：java.lang.Long#MAX_VALUE、java.lang.Long#SIZE）
- 绝对值超过 2^53 – 1 的整数要按 BigInt 才能保精度：ArkTS 的 number 只能精确表示到 2^53 – 1，19 位 id 会被舍入（出处：鸿蒙 SDK 的 ets/api/@ohos.util.json.d.ts，json.BigIntMode.PARSE_AS_BIGINT）
- UserBean 一类模型的 id、hash 和各层 userId 改成 bigint：改后 19 位 id 不再丢精度（出处：卡里修好并验证过）
未核实：卡里没核到生成者当时知道 id 有 19 位，只按源端声明为 Long 归因
