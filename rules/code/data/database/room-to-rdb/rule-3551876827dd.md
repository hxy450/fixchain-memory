# Room @Database 带版本和迁移链时，RdbStore 设 store.version 并写升级分支

审的是：代码
触发（任一种）：
- 读到：源端 @Database(entities = …, version = N)，Room.databaseBuilder(...).addMigrations(...) / AutoMigration，再加 .fallbackToDestructiveMigration()；或规格写 explicit versioned migration、retain source schema history；写错的样子：目标 relationalStore.getRdbStore 之后只执行无版本的 CREATE TABLE IF NOT EXISTS，没有读写 store.version，也没有旧版本的升级分支
适用范围：把 Room 数据库落成 relationalStore、源端有版本号和迁移链时
做法：
- getRdbStore 后读 store.version：为 0 时按最终 schema 建表；不为 0 且小于 N 时按源端 Migration 的顺序逐个写升级分支（如 1→2 重建临时表后 RENAME）；最后 store.version = N（N 取源 @Database 的 version）
- 建库、升级放在一个事务里执行
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- version: number（设置时必须是大于 0 的整数）：RdbStore 的库版本，可读可写（出处：鸿蒙 SDK 的 ets/api/@ohos.data.relationalStore.d.ts，RdbStore.version）
- 新建的库 store.version 默认是 0：用 0 判断是首次建库还是需要升级（出处：data-persistence-by-rdb-store.md，开发步骤）
- function getRdbStore(context: Context, config: StoreConfig): Promise<RdbStore>：打开或创建库（出处：鸿蒙 SDK 的 ets/api/@ohos.data.relationalStore.d.ts，relationalStore.getRdbStore）
- executeSql(sql: string, bindArgs?: Array<ValueType>): Promise<void>：执行建表和升级的 SQL（出处：鸿蒙 SDK 的 ets/api/@ohos.data.relationalStore.d.ts，RdbStore.executeSql）
- 库版本设为源端的 N，prepareSchema 在事务内按旧版本重放 1→N 的迁移：返修的做法（出处：卡里修好并验证过）
针对本应用要查的：
- 源库的版本号和迁移链：源工程里带 @Database 注解的类，以及 Room.databaseBuilder 链上的 addMigrations 参数和各 Migration 对象；version 取注解里的值；每个 Migration(from, to) 的 migrate 方法体就是一条升级分支的 SQL
