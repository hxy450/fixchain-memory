# 移植按屏幕配置计算的框架算法时，屏幕尺寸放进 @Local 状态并随转屏刷新

审的是：代码
触发（任一种）：
- 读到：源端用 ActionBarPolicy.getMaxActionButtons 这类读 Configuration 屏幕 dp 的框架算法，Activity 没声明 android:configChanges，转屏重建后重算；写错的样子：目标在普通方法里直接读 display.getDefaultDisplaySync() 计算，结果不依赖任何 @Local/@State，转屏后上栏数不变
适用范围：返修或实现阶段把源端依赖屏幕配置、靠转屏重建重算的逻辑移植到 ArkTS 时
做法：
- 把屏幕宽高（vp）放进 @Local 状态，在方向和窗口变化时刷新；算法读这两个状态，状态变了组件自动重算
- 算法结果决定列表子集时，同时核对这个列表 ForEach 的键含项身份
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- getMaxActionButtons 读 config.screenWidthDp、screenHeightDp、smallestScreenWidthDp 决定上栏最多几个：结果随当前方向的宽高变化（出处：com.android.internal.view.ActionBarPolicy#getMaxActionButtons）
- @Local 装饰的变量变化时，会刷新使用该变量的组件：屏幕尺寸放进 @Local 才能触发重算（出处：arkts-new-local.md，概述）
- function on(type: 'add' | 'remove' | 'change', callback: Callback<number>): void：屏幕变化的回调，可在 'change' 里重读宽高写回状态（出处：鸿蒙 SDK 的 ets/api/@ohos.display.d.ts，display.on）
- 新增 @Local 屏幕宽高并在横竖屏变化时刷新后，转屏上栏数正确重算：卡里修好的结果（出处：卡里修好并验证过）
未核实：卡里没写刷新用的是哪个事件，display.on('change') 是按声明补的
