# 源端 startActivity 前先写播放队列等共享状态时，目标在 push 前按同序写入

审的是：代码
触发（任一种）：
- 读到：源端列表项点击处理在 startActivity(Intent) 之前，先把当前列表（过滤掉广告等项）和新位置交给共享播放器 / ViewModel 的队列写入方法，再带 id 类参数启动播放页；写错的样子：目标只构造页面参数（id、type）后 pushPathByName(...) 或 router.pushUrl(...)，跳转前没有调用工程已有全局引擎的队列写入方法
适用范围：把源端「列表项点击→启动详情或播放页」的链路迁成目标导航调用，且源端在启动页面前有状态写入时
做法：
- 把源端 startActivity 之前的每个副作用逐条列出，目标在 pushPathByName 之前按同一顺序调用工程已有的对应接口；播放队列写给全局播放引擎（全量列表、新位置、自动播放标志照源端），列表的过滤和位置换算照源端
- 跳转参数不是完整契约：目标页若从引擎的当前曲目或队列取数，调用方必须先写队列再 push，不能假定目标页按参数自行加载
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- pushPathByName(name: string, param: unknown, animated?: boolean): void：param 是交给要压栈的 NavDestination 的参数（出处：鸿蒙 SDK 的 ets/component/navigation.d.ts，NavPathStack.pushPathByName）
- 跳转前按源端列表构造全量条目、调用全局播放引擎的队列写入（条目、下标、true）再 push，播放页曲目和列表与源端一致：修好后的写法（出处：卡里修好并验证过）
针对本应用要查的：
- 目标页的数据从哪来：目标工程里目标页的 .ets（按 onReady / aboutToAppear 里读参数和读引擎、store 的代码找）和全局播放引擎模块；目标页只用参数初始化 id、曲目和列表从引擎或 store 取的，调用方就必须先写队列
- 源端跳转前的副作用：源工程里列表点击处理所在的 Fragment / Activity 源文件，按 startActivity 往前找；startActivity 之前对共享对象的每次调用都是要在目标端按序落地的一步
未核实：卡里的鸿蒙 SDK 是 6.1.1(24)，pushPathByName 签名照本机 API 23 核实
