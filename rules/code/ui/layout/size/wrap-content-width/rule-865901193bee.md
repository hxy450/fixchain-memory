# wrap_content 容器定宽只累加非 match_parent 子项，再用该宽排其余子项

审的是：代码
触发（任一种）：
- 读到：PopupWindow#setWidth(WindowManager.LayoutParams.WRAP_CONTENT)，弹层内容是纵向 LinearLayout，子项有的 android:layout_width="match_parent"、有的是固定 dp 宽；写错的样子：弹层宽写成 Math.max(各子项宽) + padding，把 match_parent 子项（含自绘控件的偏好长度）也算进去，弹层比源端宽
- 读到：纵向 LinearLayout 的 android:layout_width="wrap_content"，子项里 match_parent 与固定宽混排；写错的样子：容器宽取了 match_parent 子项自己测出的宽（如自定义 View 的偏好长度加装饰）参与 Math.max
适用范围：安卓 wrap_content 宽的 PopupWindow 或纵向 LinearLayout 里同时有 match_parent 子项和定宽子项，迁成 ArkUI 时容器宽要自己算
做法：
- 容器宽 = 非 match_parent 子项（连 margin）宽的最大值 + 容器左右 padding；match_parent 子项不参与这一步
- 容器宽定下后，match_parent 子项（含自绘的滑杆类控件）一律按这个内容宽测量和绘制，不用它自己的偏好长度：自定义 View 的偏好长度只在约束是 AT_MOST / UNSPECIFIED 时才生效
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- 宽不是 EXACTLY 时，lp.width == MATCH_PARENT 的子项在 alternativeMaxWidth 里只计 margin；只要不是全部子项都 match_parent，容器宽就取 alternativeMaxWidth：源端 match_parent 子项不参与定宽（出处：android.widget.LinearLayout#measureVertical）
- 定宽后 forceUniformWidth 以 MeasureSpec.makeMeasureSpec(getMeasuredWidth(), MeasureSpec.EXACTLY) 重量每个 match_parent 子项：match_parent 子项最后按容器内容宽 EXACTLY 测量（出处：android.widget.LinearLayout#forceUniformWidth）
- 弹层宽 = 定宽子项的宽 + 2×容器 padding，滑杆按该定宽子项的宽测量后，与参照机一致：按源端测量规则算出的宽，和把偏好长度算进去的写法相比更窄（出处：卡里修好并验证过）
未核实：自定义 View 的偏好长度只在 AT_MOST / UNSPECIFIED 时生效，出自卡对依赖库控件 onMeasure 的反编译，本机没有该库源码；卡里上机的行为出自 HarmonyOS 6.1.1（API 24）
