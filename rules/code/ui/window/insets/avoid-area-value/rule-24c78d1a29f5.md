# 避让区和窗口尺寸写进供 .padding 用的模型前先 px2vp，不把 px 原值当 vp

审的是：代码
触发（任一种）：
- 读到：UIAbility 里 getWindowAvoidArea(...) 取到 avoidArea.topRect.height / bottomRect.height，或取窗口的 windowRect 宽高，要写进各页 .padding 消费的共享模型；写错的样子：topRect / bottomRect 的原值直接写进共享模型，没有经过 px2vp；注释写成「consumed as vp」，或留着空的换算占位
- 写错的样子：入口 Ability 把 getWindowAvoidArea(...).bottomRect.height 原样 AppStorage.setOrCreate 发布，页面直接放进 .padding({ bottom: … }) 当 vp 用；或发布端、使用端各换算一次
适用范围：取窗口避让区高度或窗口尺寸、供页面 .padding 按 vp 消费时（含经共享模型或 AppStorage 传递）
做法：
- 写入共享模型或 AppStorage 前统一换算：const ui = mainWindow.getUIContext()；top = ui.px2vp(avoidArea.topRect.height)，bottom = ui.px2vp(avoidArea.bottomRect.height)，窗口宽高同样 px2vp 后再写；改在使用端换算的，发布端就不换，只换一次，另一端直接当 vp 用
- 一时找不到换算入口时保留「这是 px」的注释并在报告里上报，不把注释改成按 vp 消费后原样写入
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- getWindowAvoidArea(type: AvoidAreaType): AvoidArea：Window 上取避让区的接口，返回的 topRect、bottomRect 是 Rect（出处：鸿蒙 SDK 的 ets/api/@ohos.window.d.ts，Window.getWindowAvoidArea）
- Rect 的 left、top、width、height 单位为 px：避让区和窗口矩形都是物理像素，进 .padding 前要换成 vp（出处：arkts-apis-window-i.md，Rect）
- px2vp(value: number): number（UIContext 的方法；全局 px2vp 自 API 18 废弃）：UIContext 上把 px 换成 vp（出处：鸿蒙 SDK 的 ets/api/@ohos.arkui.UIContext.d.ts，UIContext.px2vp）
- getUIContext(): UIContext：Window 上取 UIContext，UIAbility 里没有组件上下文时用它（出处：鸿蒙 SDK 的 ets/api/@ohos.window.d.ts，Window.getUIContext）
- getMainWindowSync(): Window：WindowStage 上取主窗口，再调 getUIContext()（出处：鸿蒙 SDK 的 ets/api/@ohos.window.d.ts，WindowStage.getMainWindowSync）
- getWindowAvoidAreaIgnoringVisibility(type: AvoidAreaType): AvoidArea：同族接口：Window 上取避让区、不管当前是否可见（@since 22），返回值同样是 px（出处：鸿蒙 SDK 的 ets/api/@ohos.window.d.ts，Window.getWindowAvoidAreaIgnoringVisibility）
- mainWindow.getUIContext().px2vp 换算顶部、底部避让和窗口宽高后写入：换算后各页 padding 与状态栏、导航条高度一致（出处：卡里修好并验证过）
- 避让高度不换算时被当成同样数值的 vp，底部留白过大；在入口 Ability 统一 px2vp 后正常：改前改后的现象（出处：卡里修好并验证过）
未核实：卡里环境是 API 24（6.1.1），本机按 API 23 的声明核对
