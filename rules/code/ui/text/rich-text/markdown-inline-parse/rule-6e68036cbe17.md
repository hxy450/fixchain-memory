# 自写行内标记解析时，长分隔符未闭合要整段写入字面缓冲，不落进短分隔符分支

审的是：代码
触发（任一种）：
- 读到：源端用 ReactMarkdown + remarkGfm（react-markdown、remark-gfm）渲染 Markdown；规格要求子集外或不成对的标记按字面文本输出、内容不丢失；写错的样子：自写的行内解析里 `**`（或 `~~`、```）分支只在 indexOf('**', i + 2) 命中时产出粗体，未命中时没有字面回退，直接落进后面共享首字符的 `*` 分支
适用范围：用手写的单趟扫描解析器替代 CommonMark 渲染器（react-markdown、remark 一类），且有共用同一首字符的长短分隔符时
做法：
- 长分隔符分支找不到闭合时显式回退：写成 buffer += '**'; i += 2; continue;（`~~`、``` 同理按各自长度），不让它往下走到短分隔符分支
- 写完后逐一推演或单测只有开头标记的输入：`**b`、`*a`、`` `c ``、`[x`，并断言同一行所有 span 的文本拼起来等于原始行
- 子集内的畸形输入以源渲染器的处理为参照：不成对的分隔符按字面文本输出，不只覆盖规格列举的子集外构造
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- buffer += '**'; i += 2; continue;：粗体分支未闭合时的字面回退（出处：卡里修好并验证过）
针对本应用要查的：
- 源渲染器对不成对分隔符的具体处理：源工程 package.json 里 react-markdown、remark-gfm 的版本，及 node_modules 下 micromark 处理强调分隔符（attention）的那个文件；看未配对的分隔序列最后是不是作为文本节点输出，以此定目标解析器的回退
未核实：源端 micromark 的 attention 处理把未匹配的分隔序列转成字面文本：卡里是修复者注释里引的依据，不是修法本身，三类来源里也查不到原文
