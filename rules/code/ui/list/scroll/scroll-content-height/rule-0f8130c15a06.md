# 右列 match_parent 随左卡等高时，用左卡 onSizeChange 的实测高绑右卡 height

审的是：代码
触发（任一种）：
- 读到：水平 LinearLayout 里右列 android:layout_height="match_parent"，随左侧 wrap_content 的卡片等高；右列内子卡 wrap_content + layout_weight，兄弟容器 android:visibility="gone"；整行在 NestedScrollView 里；写错的样子：右卡在 Scroll 内写纵向 .layoutWeight(1) 或 .height('100%')（被撑到整屏），或者改成按字号行高估算的常量 .height(<常量>)
适用范围：源端兄弟跟随等高（右列 match_parent 等于左侧内容高），目标位于 Scroll 等纵向无界父链里时；onSizeChange 声明里是 @since 12
做法：
- 左卡写 .onSizeChange((_old: SizeOptions, size: SizeOptions) => { <左卡高状态> = size.height as number })，状态用 @Local / @State；右卡写 .height(<左卡高状态>)，首帧可以用估值兜底
- 不用按字号行高估算的常量顶替，也不在 Scroll 内用纵向 layoutWeight 或 height('100%') 表达跟随等高
已核实的写法和取值（核实时用的是鸿蒙 SDK API 23）：
- onSizeChange(event: SizeChangeCallback): T：布局导致组件尺寸变化时回调；@since 12（出处：鸿蒙 SDK 的 ets/component/common.d.ts，CommonMethod.onSizeChange）
- type SizeChangeCallback = (oldValue: SizeOptions, newValue: SizeOptions) => void：回调的两个参数都是 SizeOptions（出处：鸿蒙 SDK 的 ets/component/common.d.ts，SizeChangeCallback）
- LinearLayout 高度不是 EXACTLY 时，对 match_parent 子项在量完后按自身测得高度（最高子项）重新量一遍：源端右列等于左侧内容高的来由（出处：android.widget.LinearLayout#forceUniformHeight）
- Scroll 内 height('100%') 撑满整屏；估算常量与左卡实测高差几 vp；左卡 onSizeChange 实测高绑到右卡 height 后两卡等高：几种写法的实测结果（出处：卡里修好并验证过）
未核实：卡里的观察出自 HarmonyOS 6.1.1(24)，本机核对声明用的是 API 23
